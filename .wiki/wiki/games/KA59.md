# KA59

> Multi-piece placement + momentum-push. NOT classic box-to-goal Sokoban — validated 2026-07-15.

## Mechanic reconciliation (validated 2026-07-15, task #49)

The old "two agents push blocks into goal cells" (classic Sokoban) framing is
INACCURATE. Reading the game source + a live probe shows:
- ACTION1-4 directly move the ONE active ring PIECE by one cell (blocked by
  walls); ACTION6 clicks to switch which piece is active. WIN = every hollow
  FRAME target is filled by a piece exactly centred inside it — a PLACEMENT
  condition, not boxes-to-goals.
- The "push" is a MOMENTUM-SLIDE LAUNCH (`explode-*` projectile in the source):
  moving the active piece INTO another launches a multi-tick slide that shoves
  pieces along the lane — used to cross an otherwise-impassable wall (measured
  col 27→42), NOT a 1-cell Sokoban push.

Consequence for kernels: the new generic `plan_push`
(`src/admorphiq/kernels/paths.py`) models CLASSIC 1-cell Sokoban push
reachability (route a box to a target, repositioning the pusher to the
opposite side each push) — a reusable primitive for TRUE box-to-goal Sokoban
games, validated on synthetic scenarios (`tests/test_kernels_paths.py`). It
does NOT match ka59's ring-placement win or its momentum-slide push, so ka59
was deliberately NOT rewired to it (that would mis-model the game and risk
regressing the careful existing adapter). ka59's real lever is joint-planning
coordination + a momentum-slide-specific successor model — a distinct
follow-up, banked honestly here.

## L0 clearing recipe VALIDATED live (2026-07-15, task follow-up) — reopen, not banked-as-unclear

A joint-placement pass PROVED L0 is clearable (reproduced `levels_completed → 1`
live) — turning the vague "joint planning gap" into a demonstrated recipe with
the exact composition:
- **Detect**: 2 ring PIECES (small class) at (30,18),(30,27); 2 FRAME targets
  with inner top-lefts (33,12) and (27,45). Fill = piece outer-bbox top-left ==
  frame inner top-left. Pieces move a FIXED 3px step (ACTION1=up3, 2=down3,
  3=left3, 4=right3); only the ACTIVE piece moves; ACTION6 clicks a piece's
  top-left to select it (measured reliable).
- **The wall**: the frame at (27,45) is across an impassable band (~col 30-33).
  A piece walking right stalls at (30,30) — it needs a LAUNCH.
- **The launch (measured)**: colliding the active piece into another piece
  shoves the STRUCK piece a fixed momentum distance along the lane — piece
  (30,27) launched to (30,42), crossing the wall (a multi-tick slide; both
  rings go undetectable mid-animation, positions then re-read).
- **Winning sequence (measured live)**: (1) collide piece1 into piece2 → piece2
  at (30,42); (2) select the far piece, walk it up+right to (27,45) → frame
  filled; (3) select the near piece, walk it (left-then-down; down is blocked
  from (30,27), so route left to col 12 first) to (33,12) → both filled → WIN.

Assignment (`assign_pairs` by Manhattan) pairs (30,18)→(33,12) and
(30,27)→(27,45). A greedy adapter composing this (launch-first when a frame is
a cross-board move, then select+greedy-walk each piece) was PROTOTYPED but hit
a select-orchestration loop and was reverted (the sophisticated existing
adapter is preserved, no regression). **Reopen (now feasible, not
speculative)**: a focused joint planner — launch-first (detect the far frame,
collide pusher into the launch piece), settle + re-identify, then select +
greedy-walk each assigned piece to its frame. The mechanic risks are all
retired (fill win, fixed step, select point, launch momentum all measured);
what remains is robust select/re-identify orchestration.

## Observations

## Lessons Learned

- Current solver is brittle — v1 works, v2 fails.
- v2 hash (38d34dbb) added ACTION6 to the action set (v1 was dir-only),
  confirming that solver obfuscation is accompanied by mechanic
  variation. Any brittle v1 solver is structurally dead on v2.
- R19 direct probe confirms frame-hash BFS cannot clear even L1 in
  50k budget on 2-player Sokoban: the `{dir × 2 players × click}`
  branching is ~16-24 and depth-10 solutions exceed BFS's 15k-state
  cap by 10 orders of magnitude. A specialist `_plan_push_bfs` with
  (player, block_set) state + Manhattan-A* is required.
