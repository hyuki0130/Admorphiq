# S5I5

> A click-only slider puzzle: click a track's far/near half to slide its goal marker ±1 unit along an axis until it lands on its target. R56 = first frame-only clear (1/8), matching brittle without any sprite tags.

## R60 — claimed-vs-official 0.0000 discrepancy RESOLVED (CORRECTED): two content variants, the adapter clears ONE — a48e4b1d genuinely 0/8 (2026-07-16)

> **This section supersedes an earlier draft that concluded "both variants clear /
> platform difference." That was WRONG (a measurement-discipline slip — I did not
> verify WHICH content dir the `make("s5i5")` short-name load resolved to). The
> corrected, proven verdict follows.**

The game_id `s5i5-18d95033` maps to TWO local content dirs — `18d95033/`
(`date_downloaded` 07-06) and `a48e4b1d/` (06-29), heavily different sprite artwork
(3726-line diff, v2-hash colour/SIZE remap) at the same positions. **The adapter
clears `18d95033` (1/8) but NOT `a48e4b1d` (0/8).** The Mac↔VM "1/8 vs 0/8"
difference is entirely which variant each machine's arcade resolves — NOT a
platform-execution bug.

- **PROOF a48e4b1d genuinely fails (Mac, run_game):** moving `18d95033/` aside so
  only `a48e4b1d/` remains, `score_efficiency.run_game(... max_actions=5000)`
  (the exact scoring loop) on `a48e4b1d/s5i5.py` returns **levels=0, score=0.0** —
  matching the VM's r59s1/r59s2 (which load a48e4b1d) exactly. My 1000-action trace
  probe (a48e4b1d confirmed loaded) likewise NEVER clears L0.
- **PROOF the scoring path picks 18d95033 on the Mac:** `run_game`/`script25`
  (via `get_environments()` + `make(game_id)`) load `18d95033/s5i5.py` and score
  **1/8** — even with a48e4b1d's metadata date bumped to 2099. (The earlier bogus
  "forcing a48e4b1d → 1/8" used `arcade.make("s5i5")` short-name resolution in a
  DIFFERENT process than the script25 run — the two resolve to different dirs; I
  conflated them.) So Mac card = 1/8 (18d95033), VM card = 0/8 (a48e4b1d); both are
  CORRECT for the variant each loads.
- **ROOT CAUSE — hardcoded size threshold, not colour, not platform.** The adapter
  splits goal-vs-target by `_GOAL_MAX_SIZE=2` on colour-13 markers. Measured:
  - `18d95033` colour-13 marker sizes = **[1, 1, 4, 4]** → goals(size≤2)=[1,1],
    targets(size>2)=[4,4]: clean split → tracks 2 goals to 2 targets → clears.
  - `a48e4b1d` colour-13 marker sizes = **[4, 4]** → goals(size≤2)=**[] (NONE)**,
    targets=[4,4]: the v2 variant renders the GOAL sprite at size 4 (not 1), so the
    fixed `≤2` threshold classifies BOTH markers as targets, detects ZERO goals,
    and the planner has no movable goal to steer → 0/8. (Colour 13 IS correct on
    both — the brittleness here is the SIZE threshold, plus that on a48e4b1d goal
    and target are the SAME size, so no size threshold can split them — it needs
    movement-based goal discovery, whose existing fallback in `_decide` does not
    close a48e4b1d.)
- **Verification anchors that held:** step-0 frame_hash identical Mac/VM
  (d44fd03f9ec8, same a48e4b1d frames); first 120 trace steps byte-identical
  Mac/VM (team-lead diff) — consistent with NO platform-execution divergence, the
  fork being simply that neither platform ever clears a48e4b1d.

**Verdict:** the r56s7/r59s1 card `s5i5 = 0.0000` is CORRECT for the a48e4b1d
variant the VM loads; the "1/8" is CORRECT for 18d95033 the Mac loads. This is the
classic v2/v3-hash brittleness (`GENERALIZATION DEBT`) — the frame-only detection
is tuned to one variant's sprite sizes. **There IS now a real failing case
(a48e4b1d), so hardening is justified (no longer speculative).**

### a48e4b1d L0 DECODED (movement round) — goals are a DIFFERENT COLOUR; robust fix = perception rewrite, BANKED (2026-07-16)

Decoded a48e4b1d's L0 live (`scripts/_s5i5_decode_a48.py`, 18d95033 dir moved aside so
a48e4b1d loads unambiguously; restored). It is the SAME slider mechanic — but with a
**fundamentally different colour/size structure that breaks the adapter's core
assumption** (goals and targets share colour-13, split by size). The measured decode:

- **Targets = colour-13, size 4**, at (10,52) and (52,10) — the two static
  destination markers. (Clicking any track/control does NOT move them.)
- **Goals = colours 14 AND 11** (NOT colour-13), size-VARYING:
  - colour-14 goal seeds size-15 at (10,30); a top-control click slides it (row 10,
    col 30→28) and it renders size-6 — it rides the TOP track toward its colour-13
    target at (10,52).
  - colour-11 goal seeds size-24 at (32,10); a left-control click slides it up the
    LEFT track (row 32→30→28, col 10), size 24→15→6 — toward its colour-13 target at
    (52,10).
  So a48e4b1d has TWO goals of TWO DIFFERENT colours, each ≠ the target colour, and
  each goal's rendered SIZE changes with its slider position (6-24).
- **Why the adapter scores 0/8:** it detects goals as `colour-13 AND size ≤
  _GOAL_MAX_SIZE(2)`. On a48e4b1d there are NO colour-13 size-≤2 regions (colour-13
  is only the two size-4 targets), and the goals are colours 14/11 — so goal
  detection returns EMPTY, the planner never has a goal to steer, and the `_decide`
  movement-fallback never produces a "small colour-13 goal blob" either → it loops
  forever → 0/8. (18d95033 works only because there both goals AND targets are
  colour-13, cleanly size-split 1 vs 4.)

**BANKED + CLOSED (per the stop rule: a48e4b1d is structurally different, not just
sprite sizes).** A robust fix is NOT a bounded tweak — it requires a colour-AGNOSTIC
perception+discovery layer: (1) find goals as the pieces that MOVE under a
control/track probe, of ANY colour and with size allowed to change; (2) find targets
as the static destination markers (a48e4b1d: colour-13; 18d95033: colour-13 size-4);
(3) match each goal to its target across colours; (4) then the existing
effect-learning greedy steers. That rewrites the adapter's detection spine (currently
`_MARKER_COLOR`/`_GOAL_MAX_SIZE`-keyed) and MUST be validated to not regress
18d95033's 1/8 — a dedicated round, not this pass. This is the exact class of v2/v3-
hash generalization debt the hidden 110 games punish; worth a dedicated
perception-generalization round if the +0.0278 (and the transfer lesson) is wanted.
Decode tool kept: `scripts/_s5i5_decode_a48.py`. Verification technique for that
round: move each variant dir aside in turn, both must clear via `run_game`
deterministic ×2.

## Observations

Measured from the live frame + game source (dev-time read only; the adapter
acts frame-only):

- `available_actions` = `[6]` — ONLY ACTION6 (click). No movement actions.
- Goal markers and target markers are the same distinct colour (measured 13); a
  goal is a small blob, a target a larger diamond of DIAGONALLY-adjacent pixels
  (so segmentation needs 8-connectivity or it shatters into size-1 fragments).
- Each goal is attached to a resizable slider whose track is a colour-2
  rectangular frame. Clicking the FAR half of a track extends the slider, moving
  its goal +1 unit (3 px) along the track's long axis; the NEAR half shrinks it
  (−1 unit). Clicking a rotate button (`myzmclysbl`) rotates the slider 90°,
  switching the goal's movement axis.
- A move that would collide two sliders is REVERTED (source `ulzimrggno`).

## Mechanics Hypothesis

Goal-to-target coincidence via 1D slides (typology: axis-projected coincidence).
Win = every target (`cpdhnkdobh`) has a goal exactly on it (source
`vodebmynqs`). To place a goal, slide it along the current axis to match one
coordinate, rotate to switch axis, slide to match the other. See
[[../game_types/slider_puzzle]] and [[../concepts/sprite_cluster]].

## Solution Pattern

The R56 adapter (`adapters25/s5i5.py`) composes `kernels.find_regions`
(8-connectivity): lock the large target blobs; track the small goal blobs;
generate candidate click points at each track frame's edge midpoints; MEASURE
each candidate's effect (which goal moves, by how much, which target it serves);
then repeatedly click the measured candidate whose delta most reduces its
served goal's residual. Clears L1 (1/8).

| Strategy | Levels | Type |
|---|---|---|
| `s5i5_slider` | 1/8 | brittle (reads sprite tags) |
| R56 effect-learning greedy | 1/8 | generic — first frame-only clear (L1) |

## Refactor Plan (L1 solved; L2+ banked)

**Level 1 SOLVED**: two goals already axis-aligned with their targets (7
far-half clicks on the horizontal track, 6 on the vertical). The greedy learns
each track's effect and drives each goal home. The load-bearing fix was
**8-connectivity** segmentation so the diagonal target diamonds don't shatter
(4-connectivity scored 0/8 — every marker looked like a goal, no target locked).

**Level 2 — two reopens landed, a THIRD structure banked (stop rule):**

1. **Movement-based goal/target discrimination — DONE.** L2's two colour-13
   blobs both start size 5 (a goal coincident with its target), so the size
   split saw only targets. Fix: defer locking until a small goal appears; before
   that, probe a track click to SPLIT the merged blob — the piece that moves is
   the goal (size 1), the static one the target (size 4). Verified live.
2. **Directional controls — DONE.** The compact colour-4 boxes are NOT rotate
   buttons but DIRECTIONAL slider controls (measured: one moves the goal +col,
   another −row, etc.); added as candidates so the effect-learning greedy
   measures and uses them. Plus collision-revert handling (`_dead`): a click
   with no goal movement (maxed slider / reverted collision) is skipped until a
   goal moves again.
3. **BANKED third structure — the goal can't REACH its target by translation.**
   Measured: the goal's column control maxes/collides at col 43 while its target
   is at col 52 (9 px unreachable), and the row control never closes the column
   gap, so the greedy oscillates. Reaching the target needs TRUE rotation (swap
   the slider axis to extend past the block) — a control separate from the
   colour-4 movers, not yet frame-located. Per the stop rule, banked.

No hardcoded coordinates/sequences were added. The machinery (movement-split,
directional-control candidates, dead-click reverts) plus the frame-only L1 solve
are the deliverables; L1 (1/8) unaffected.

## Lessons Learned

- The 1/8-vs-0/8 gap was pure sprite-tag dependence; decoding the tags
  (`myzmclysbl`=rotate buttons, `zylvdxoiuq`=goals) into frame roles (small
  movable blob / static target diamond / colour-2 track frame) gave a frame-only
  clear that ties the brittle score. See [[../lessons/v2_hash_obfuscation]],
  [[../lessons/brittle_tells]].
- Diagonally-arranged markers need 8-connectivity segmentation; 4-connectivity
  shatters them and destroys the goal/target size distinction.
