# SU15 — Vacuum-Pull Merge-and-Deliver Puzzle

> A click runs a radius-8 VACUUM that pulls nearby fruits toward it; two same-value fruits that overlap merge to value+1 (2048-style); a level clears when the exact (value, count) multiset of fruits sits inside the goal-zone sprite bbox(es). The iteration-8 "click-to-steer player" model was FALSIFIED — the "player" was the vacuum-ring animation artifact.

## R56 iteration 10 — DECODED FROM SOURCE, first generic clears 3/9 (2026-07-15)

Read `environment_files/su15/*/su15.py` directly (dev-time legal; the 4c352900
hash carries readable tags "fruit"/"goal"/"enemy"/"hint"). The full mechanic:

- **Vacuum click (`axaxyjxqoe`)**: `ACTION6(x,y)` pulls every fruit whose bbox
  is within radius `kacsjmxae=8` of the click TOWARD the click over
  `gdamdvokm=4` sub-steps of ≤`ikskfqldi=4` px/axis, clamped at the click. The
  whole animation resolves inside ONE agent action.
- **The "colour-0 player" was an ARTIFACT.** Iterations 7-9 tracked a ~48-52
  cell colour-0 blob "landing on every click" and modelled it as a steered
  player. It is the VACUUM RING (`vmgyqpnfu`/`rgxlnsrafr`): a radius-8 annulus
  of colour-`pynrefijae`(=0) pixels drawn at the click. Proof: in the gold
  trace its centroid in `frames[i]` equals the PREVIOUS click's `(x=col,
  y=row)` exactly. Colour 0 is now ignored entirely.
- **Fruits (`lkujttxgs`)**: value 0..8 → colour `[10,6,15,11,12,8,9,7,14]`,
  size 1×1..10×10. Value-0 fruits are a SINGLE cell — must detect at `gap=0`
  (fusing adjacent zeros hides a mergeable pair; measured stall). Same-value
  overlap merges to value+1; **a clump of N same-value fruits collapses to ONE
  value+1, not N/2** (`nhtlfoopnx` union-find) — so you must merge exact PAIRS
  in sequence, never pile. L1 = eight value-0 → one value-3 by balanced
  pairwise merge.
- **Goal zones (`powykypsm`)**: static colour-9 holey disks (density<1.0;
  distinguished from a solid value-6 block). Delivery = fruit centre inside the
  goal SPRITE bbox.
- **Enemies (`fezhhzhih`)**: sparse star sprites colours 7/14/13; chase the
  nearest fruit and DOWNGRADE it on contact. Colours 7/14 collide with fruit
  values 7/8 — told apart at gap=0 by size (fruit blocks are 81/100 cells,
  enemy fragments ≤5). Colour 13 is enemy-only.
- **Win (`cbdhpcilgb`)**: delivered-fruit value multiset must EXACTLY equal the
  level spec `xkstxyqbs` (only the values IN the spec are checked; other-value
  fruits in the goal are ignored).

The adapter (`src/admorphiq/adapters25/su15.py`) is a frame-only greedy: merge
the lowest value that still has a pair (gather far pairs by pulling one toward
the other; midpoint-click near pairs — `_MERGE_DIST=14` must stay under
2×radius so a midpoint grabs BOTH fruits), then deliver the top fruit to the
nearest goal, dodging adjacent enemies. **Measured: 3/9 (L0/L1/L2),
game_score 0.1035** (`scripts/rounds/script25_su15_sim_final`). L0 = pure
delivery; L1/L2 = merge cascade.

## Observations

### Frame-level
- Multi-layer grid
- "Fruits" = colored sprites; same-color fruits merge on overlap to color+1 (like 2048)
- "Enemies" chase nearest fruit; contact downgrades the fruit by 1 (or removes if color 0)
- "Goal zones" = designated regions for delivering correct-color fruits
- Per-level goal spec: N fruits of color C plus optional enemy constraints

### Action effects
- `ACTION6(x, y)` creates a vacuum at (x, y) with radius ~8 px that pulls nearby fruits/enemies toward the click
- No simple actions matter here

## Mechanics Hypothesis

- Goal: by click-induced movement, arrange specific counts of specific colors in specific zones
- Two primitives available: **merge** (fruits) and **downgrade** (enemy hit)
- Level difficulty scales with target color (higher = more merges required)

## Solution Pattern (current, brittle)

`strat_su15_vacuum` in [`src/admorphiq/agent_ensemble.py`](../../../src/admorphiq/agent_ensemble.py):
1. Access `game.hmeulfxgy` → list of fruit sprites (positions, colors)
2. Access `game.peiiyyzum` → list of enemy sprites
3. Access `game.rqdsgrklq` → list of goal zones
4. Phase 0 — downgrade: suck over-colored fruits toward enemies
5. Phase 1 — merge: pair same-color fruits, suck them together
6. Phase 2 — deliver: suck target-color fruits to goal zones

**Why it's brittle**: `hmeulfxgy`, `peiiyyzum`, `rqdsgrklq` are obfuscated attribute names. On v2 they differ → AttributeError → 0/9.

## Proposed Frame-Only Refactor (Step 2b in Phase 8)

1. **Fruit detection**: cluster connected non-background pixels by color index; each cluster = one fruit candidate with (center_x, center_y, color, size)
2. **Enemy detection**: clusters whose color matches a reserved "enemy" palette (identified by negative behavior — they destroy, not merge). Learn this in first 5 clicks.
3. **Goal zone detection**: persistent background regions that never move; discovered by diffing multiple frames
4. Reimplement 3-phase plan using only the detected entities
5. Vacuum mechanic stays the same — only `ACTION6(x, y)`

Expected performance post-refactor: v1 stays 9/9, v2 → ≥6/9 (harder levels may need merge-order search).

  1. **Fragment fusion** — a single tile renders as ~15-17 DISCONNECTED
