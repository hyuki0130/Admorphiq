# SU15 — Click-to-Steer Merge Puzzle (was mis-modelled as "vacuum merge")

> A single PLAYER blob follows clicks exactly (gold-replay + live-verified); the level clears via a stateful tile MERGE/CONVERSION swept out along the player's path — NOT a click-attract "vacuum", and NOT reaching a goal tile.

## R56 iteration 8 — gold-replay RESOLVES the source-identity reopen (2026-07-15)

The prior 7 iterations modelled SU15 as a "vacuum" (click near a tile to pull
it). **Gold-replay divergence proves that is WRONG — SU15 is CLICK-TO-STEER
NAVIGATION.** Method: replayed `data/traces/su15.npz` frame-by-frame and
confirmed live.

- **A single PLAYER follows clicks EXACTLY.** In every gold level the moving
  entity is ONE blob (colour 0, ~48-52 cells) whose centroid lands AT the
  click each step (click-distance → 0). A live follow-test (5 clicks 7px
  apart) reproduced it: one colour-0 size-48 region on each click, dist 0.
  The small static tiles near a click (e.g. `(53,10)` colour-0 size-5, the
  iteration-7 "target") are DECOYS — they never move. So the reopen's guess
  that the ~50-cell blob is the controlled entity was RIGHT, but there is no
  vacuum: the player simply moves to wherever you click.
- **Gold TRANSFERS to the live env**: replaying gold's exact 101 clicks on the
  live `su15-1944f8ab` env (gold recorded on `su15-4c352900`) clears ALL 9
  levels — su15 layouts are identical across hashes (cosmetic hash). Gold is
  a valid per-level oracle.
- **The WIN is a stateful MERGE/CONVERSION, not "reach a goal tile"
  (falsified two ways):** steering the player ONTO the largest colour-9 tile
  does NOT clear L0; steering it to gold's exact winning cell `(19,44)` and
  holding does NOT clear L0. Gold cleared L0 on the click that moved the
  player `(24,39)→(19,44)` while the histogram shifted `{9:−8, 5:+11, 3:−1}`
  — the player's diagonal SWEEP converts tiles as it passes, and the level
  clears when the swept configuration meets the goal spec, not when the player
  reaches a position.
- **Enemies cause GAME_OVER**: steering toward a colour-3 tile GAME_OVERed in
  ~5 steps (matches the wiki's "enemies chase / downgrade").

**Reopen (redirected):** REPLACE the vacuum model with player-steering — (i)
player = the colour-0 blob landing on the last click; (ii) decode the
merge/conversion rules (what the sweep does per tile colour + the goal-spec
target configuration); (iii) plan a collecting sweep path that reaches it
while avoiding enemy tiles; (iv) steer via `point_toward` (already correct).
The steering primitive is trivial; the depth is the merge-decode + path plan.
Gold (9/9 live) is the validation oracle.

## (Superseded) Original vacuum-merge model — kept for provenance

The sections below describe the pre-iteration-8 "vacuum merge" model, now
falsified (see above). 2048-style color merging via click-attract radius, with
enemies as downgraders; the brittle solver reads internal fruit/enemy/goal
lists and fails on v2.

## Observations

### Frame-level
- Multi-layer grid
- "Fruits" = colored sprites; same-color fruits merge on overlap to color+1 (like 2048)
- "Enemies" chase nearest fruit; contact downgrades the fruit by 1 (or removes if color 0)
- "Goal zones" = designated regions for delivering correct-color fruits
- Per-level goal spec: N fruits of color C plus optional enemy constraints

### Action effects
- `ACTION6(x, y)` creates a vacuum at (x, y) with radius ~8 px that pulls nearby fruits/enemies toward the click
- No simple actions matter here

## Mechanics Hypothesis

- Goal: by click-induced movement, arrange specific counts of specific colors in specific zones
- Two primitives available: **merge** (fruits) and **downgrade** (enemy hit)
- Level difficulty scales with target color (higher = more merges required)

## Solution Pattern (current, brittle)

`strat_su15_vacuum` in [`src/admorphiq/agent_ensemble.py`](../../../src/admorphiq/agent_ensemble.py):
1. Access `game.hmeulfxgy` → list of fruit sprites (positions, colors)
2. Access `game.peiiyyzum` → list of enemy sprites
3. Access `game.rqdsgrklq` → list of goal zones
4. Phase 0 — downgrade: suck over-colored fruits toward enemies
5. Phase 1 — merge: pair same-color fruits, suck them together
6. Phase 2 — deliver: suck target-color fruits to goal zones

**Why it's brittle**: `hmeulfxgy`, `peiiyyzum`, `rqdsgrklq` are obfuscated attribute names. On v2 they differ → AttributeError → 0/9.

## Proposed Frame-Only Refactor (Step 2b in Phase 8)

1. **Fruit detection**: cluster connected non-background pixels by color index; each cluster = one fruit candidate with (center_x, center_y, color, size)
2. **Enemy detection**: clusters whose color matches a reserved "enemy" palette (identified by negative behavior — they destroy, not merge). Learn this in first 5 clicks.
3. **Goal zone detection**: persistent background regions that never move; discovered by diffing multiple frames
4. Reimplement 3-phase plan using only the detected entities
5. Vacuum mechanic stays the same — only `ACTION6(x, y)`

Expected performance post-refactor: v1 stays 9/9, v2 → ≥6/9 (harder levels may need merge-order search).

### Frame-Only Scaffold (2026-04-21, WIP)

`strat_su15_frame_only` landed as an L1-L3 fallback that runs after `strat_su15_vacuum` returns 0 (typical v2 collapse path). Implemented:

- 4-connected flood-fill cluster detection over the 64×64 frame → `(cx, cy, color, size)` tuples (generalizable; will be lifted into `utils.py` once S5I5/RE86 reuse it).
- Probe click at `(2, 62)` to classify static vs dynamic colors by diffing cluster inventories.
- Greedy merge loop: for each same-color pair of dynamic clusters within ~2× vacuum radius, click the midpoint.

**Deliberately out of scope** (deferred to LLM hypothesis engine / BFS planner):
- Enemy avoidance and timing (L4+ require anticipating enemy movement).
- Multi-merge chaining to reach color `c3+` (needs lookahead).
- Hardcoded L7-L9 replacement (the existing brittle solver hardcodes these; a frame-only replacement is a Gate B target, not 2b).

Coverage target: v2 → 1-3 levels. The scaffold's main value is reuse, not raw score.

## Lessons Learned

- **2026-07-15 — R56 iteration 7 (`src/admorphiq/adapters25/su15.py`,
  commit `26ebeb6`): candidate-detection layer fixed via gold-replay
  divergence, four real bugs closed, STILL 0/9 — BANKED with a named
  next-hypothesis, not resolved.** Replayed `data/traces/su15.npz`'s L1
  gold block against the script25 adapter's own `_next_target`/
  `_candidates` (distinct from the `merge_drag.py`/`WorldModelAgent`
  path the earlier lessons below cover — a different, quarantined
  kernel-only adapter). Four bugs found and fixed:
  1. **Fragment fusion** — a single tile renders as ~15-17 DISCONNECTED
     same-colour regions (a symmetric bowtie sprite), not one connected
     blob; `_candidates` had no fusion step. Fixed via
     `kernels.find_regions`'s own `gap` parameter — a 9-level offline
     acceptance table (every opening frame in `su15.npz`) found `gap=2`
     fuses every measured bowtie while never merging genuinely distinct
     same-coloured tiles (L9's 4 separate colour-9 tiles, 61px apart,
     stay 4 distinct through `gap=4`).
  2. **Scatter-detection stray contamination** — one unrelated
     same-coloured region far from a real tile could inflate the whole
     colour group's density bbox, silently deleting the real tile's
     every fragment from candidates (not mis-ranked, gone). Fixed via
     spatial subgrouping (single-linkage chaining) before the density
     test, computed on the fine-grained (`gap=0`) pass specifically.
  3. **First-click pair-preference** — on the zero-evidence first
     decision, the adapter defaulted to a same-colour PAIR guess and
     couldn't distinguish two coincidentally-same-coloured STATIC
     decorations from a genuine mergeable pair; measured directly, it
     targeted two never-moving decorations where gold targeted the one
     colour-unique, genuinely movable tile. Fixed: a colour-unique tile
     is preferred on click 0 only, every level.
  4. **Pool-exhaustion re-enabling dead tiles** (found via live-smoke
     diagnostic on the fixes above) — the "unless that empties the pool
     entirely" fallback reverted to the FULL unfiltered tile list once
     every candidate went dead/fatal, re-enabling tiles already PROVEN
     useless (measured live: an infinite retry loop on a decoration
     dead-bucketed at step 8, re-picked at step 19). Fixed: degrade to a
     harmless centre re-probe instead of ever resurrecting a dead
     bucket.

  Acceptance: click 1's source now matches gold's exactly (centroid
  `(53, 10)`, the colour-unique tile), not the static decoration pair;
  the 9-level candidate table shows correct fusion everywhere with zero
  over-merging. **Live smoke (2x500 + 1x3000a): still 0/9.** The
  candidate-detection layer is now verified correct end-to-end — the
  wall moved from perception to mechanic understanding.

  **NEXT HYPOTHESIS (explicit reopen pointer, not yet built):** a live
  diagnostic traced the correctly-identified click-1 target (`(53, 10)`,
  colour 0, size 5) across ~15 further steps post-fix — it is STATIC
  (unchanged across steps 6, 8, 10, 11 despite repeated clicks) while a
  SEPARATE, larger (~48-54 size) colour-0 blob is the one whose position
  actually changes every step. This suggests the "vacuum" mechanic may
  PULL a distant object toward the click point rather than DRAG the
  region nearest the click: the moving ~50-cell blob is likely the
  controlled/pulled entity, and small static tiles like `(53, 10)` may
  be targets/receptacles/anchor markers, not the thing being dragged. If
  so, the adapter's entire source-tile IDENTITY model — "the region
  nearest the click point is the thing being moved," used throughout
  dead-click/fatal-click/useful-shift tracking — needs re-deriving from
  gold with THIS frame specifically before any further policy work; the
  click-POSITION fix above is directionally correct (matches gold) but
  may be built on the wrong object-identity assumption. See
  [[../rounds/r56_generic-kernels]] for the round-level provenance of
  this pass (kernel library + adapter quarantine architecture).

- **2026-07-13 — L3 stall traced under the R49+ `merge_drag.py` path.** Live
  instrumented run past L1+L2 (cleared normally, 9+7 clicks) into L3's
  merge/gather sequence: 16 clicks progress normally (tile merges
  `(6,4)`→`(15,9)`→`(11,16)`), then two leftover DIFFERENT-color tiles
  (11/size16, 15/size9) go permanently unresponsive to `ACTION6` — confirmed
  by testing both the walk-step target AND a click directly on the tile's
  own center, neither moves it. Consistent with the same downgrade-then-merge
  gap [[../lessons/su15_l1_singleton_colors_20260423]] found at L1 under the
  older architecture: some tiles need an enemy-interaction step before
  they're mergeable/gatherable, which no current frame-only plan implements.
  Repeating the dead click was found to accumulate toward `GAME_OVER` (not
  neutral) — see [[../lessons/merge_drag_stall_causes_game_over_20260713]]
  for the measured trigger, the landed stall-limit fix in
  `WorldModelAgent._merge_drag_step`, and the correction that GAME_OVER does
  **not** reset `levels_completed` on this game (confirmed: reads unchanged
  across GAME_OVER→RESET). Two static color-9/size-69 objects present
  throughout the L3 trace (never moved) are the leading unconfirmed
  candidate for the missing "enemy"/trigger entity — open for a follow-up
  session, not yet investigated further. Current frame-only ceiling remains
  L2 (2/9) on this path; L3+ needs the downgrade primitive.
- Canonical merge-puzzle solver was the first brittle solver to score 9/9 on v1 (commit `b84839e`, 2026-04-10). Four attribute reads (`hmeulfxgy`, `peiiyyzum`, `rqdsgrklq`) guaranteed v2 collapse — confirmed in 2026-04-20 Round 1 regression (0/9 on v2).
- R21 loosened entity_phase's `merge_items` detection from "same-
  color pair only" to also accept singletons in the fruit-size
  window (size 8..150). SU15 L1 previously surfaced only 2
  merge_items because most fruit colors appear once per level;
  after the fix, 4 merge_items surface and `goal_phase` classifies
  the env as `merge`. But `_plan_merge` still fails L1 because it
  requires ≥ 2 same-color clusters per pair to click a midpoint —
  SU15 L1 has no same-color fruit pairs visible. Cross-color merge
  or a downgrade→merge→deliver 3-phase sequence is the path
  forward; that crosses into game-specific territory and is
  deferred.
