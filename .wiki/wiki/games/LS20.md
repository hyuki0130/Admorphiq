# LS20

> A shape/color/rotation-MATCHING maze: the avatar carries a token
> (shape+color+rotation) that must MATCH each goal cell; changer cells cycle
> the token's attributes, and goal cells are BLOCKING until matched. Both the
> original "shape/rotation matching" note and the 2026-07-13 "pure maze"
> correction were half-right — the mechanic is the COMBINATION (source-read +
> live-verified R56 2026-07-15).

## Current Status

- **script25 adapter** (`adapters25/ls20.py`, R56 2026-07-15): **1/7**, clears
  L1 in **606 actions** (human baseline 22 → per-level RHAE 0.0013, game_score
  4.7e-05). Generic frame-keyed transition-graph BFS-from-start — no hardcoded

- **Legacy** `strat_ls20_grid` (`agent_ensemble.py:3831`): generic

  Round 5 removed its L1 hardcoded path.

## Mechanics (corrected R56 2026-07-15 — source read + live verified)

The avatar carries a **token** with three attributes: SHAPE, COLOR, ROTATION.
The maze contains:

- **Changer cells** — three kinds, each cycles ONE token attribute (shape /
  color / rotation) when stepped on.
- **Wall cells** — blocking.
- **Goal cell(s)** — each requires a specific (shape, color, rotation). A goal
  is BLOCKING while the token does not match, and level-completes the instant
  the avatar stands on it WITH a matching token.

So a level = route through the right changers to transform the token, then
stand on the goal. `available_actions = [1,2,3,4]` (up/down/left/right; no
interact). **L1** starts already matching in shape+color but one ROTATION step
off (start 270°, goal 0°), so L1 reduces to "pass one rotation-changer, then
reach the goal" — which is why blind navigators cleared it and mislabelled the
whole game as pure maze navigation. Gold L1 solution is 13 actions
(`3,3,3,1,1,1,1,4,4,4,1,1,1`).

A per-level **step counter** (shrinking colour-11 bar, bottom two rows)
decrements each action; on exhaustion the avatar loses one of 3 lives and
repositions to start — **resetting position, token, AND goal progress**.
Longer levels (L2 human baseline 123 > a ~21-42-step life) are only solvable
by collecting step-REFILL cells mid-run to extend the life.

### script25 adapter design (R56 2026-07-15)

State = the multiset of live-region signatures `(color, size, bbox)`,
EXCLUDING thin bands pinned to a frame edge (the step-counter bar / HUD).
MEASURED counter-invariant: a move-and-reverse (up then down) returns to the
exact same key while the counter has advanced two steps — so the key captures
`(avatar position, token appearance)` with no avatar-identity tracking, no
attribute decoding, and no changer-cell semantics hand-coded. Every observed
`(from_key, action, to_key)` edge is stored; exploration is **BFS FROM THE
START key** (`configuration_path` over the discovered edges) — the start is
where every life-loss returns for free, and the win is shallow, so
BFS-from-start finds it while DFS-order gets lost deepening one branch of the
large (position × token) space (measured: DFS found 147 states in 1000 actions
without clearing; BFS-from-start clears at ~600). Composes
`find_regions` + `configuration_path` only. Banked L2 wall + reopen order in
the adapter module docstring.

## Lessons Learned

- **2026-07-15 (R56) — L2 reopen step 1 (key-augmentation) MEASURED and
  REJECTED; the real gate is refill-gated search, not determinism.** The bank
  proposed fixing obstacle 1 (hidden-counter non-determinism) by folding the
  last K actions into the graph key (dealias-style). Measured on L2: the plain
  key's repeated (from,action)→to-region consistency is **83.3%** (~17% collide
  from the hidden counter); K=3 augmentation lifts it to **93.9%** — so it DOES
  improve determinism (the stop-rule's own gate). BUT it is COUNTERPRODUCTIVE:
  augmenting fragments the state space (L2 distinct nodes **33 → 3676**) and
  destroys the frame key's SELF-LOCATING property, which is what BFS-from-start
  depends on — so with K≥2 even **L1 stops clearing** (K=0 clears L1 @601; K=3
  never clears, floor regressed). Reverted; default stays the plain key.
  **Conclusion: determinism was never the L2 bottleneck — TRACTABILITY (a
  small, self-locating graph) is, and augmentation trades it away.** The real
  L2 gate is obstacle 2 (refill-gated long solutions): a ~21-step life can't
  reach L2's ~123-action goal without collecting step-refill cells first, so
  the reopen is a REFILL-AWARE BFS (detect the vanish-on-collect refill regions,
  route through them before the goal), NOT key augmentation. See
  [[../concepts/probe_signature]] and the adapter's obstacle table.
- **2026-07-15 (R56) — the mechanic is token-MATCHING, not pure maze; both
  prior notes were half-right.** Reading the game source (offline, for
  understanding) settled it: the avatar carries a shape/color/rotation token,
  goal cells are blocking until the token matches, and changer cells cycle the
  token — see Mechanics above. L1 clears by navigation ALONE only because its
  start token is one rotation step from matching; that coincidence produced
  the stale "pure maze" note. The frame-keyed BFS-from-start adapter clears L1
  generically (606 actions) without needing to decode any of this — the token
  appearance lives in the avatar's own pixels, so a region-signature state key
  captures it for free. Lesson for similar games: a frame-keyed transition
  graph sidesteps mechanic-decoding entirely when the full game state is
  visible in the frame; the only craft is masking per-action HUD noise (here
  the step-counter bar) so the key doesn't fragment. See [[TU93]] for the
  sibling design (slide-maze, same transition-graph approach keyed on player
  cell instead of the whole region set).
- **2026-07-13 — L2 blocker traced and one real bug fixed.** Live-traced why
  the agent falls straight to undirected `interact` on L2 instead of
  attempting navigation: `infer_goal` remembers which colour changed at a
  PAST level's completion (`EffectModel.completion_target_colors()`) and
  prefers that colour as the goal target on the NEXT level too. Measured:
  L1 completed via a colour-0 event, so L2's goal got force-set to
  `target_color=0` — but L2's only colour-0 cluster is a 3px decorative
  speck, not a goal. The original code computed exactly ONE plan with this
  forced (wrong) target and, on failure, fell through WITHOUT ever trying
  `_execute_step`'s existing multi-candidate rotation system
  (`enumerate_goal_cells` / `_advance_goal`, which carries no target_color
  bias and was already built for exactly this kind of situation — see the
  "multi-target navigation" bookkeeping in `world_model_agent.py`). **Fixed**:
  the initial nav-attempt now enters EXECUTE unconditionally on a navigate
  goal and lets `_execute_step`'s own rotation build the plan, so a bad
  single guess can no longer stop the whole candidate list from being tried.
  Regression test:
  `test_nav_attempt_recovers_via_goal_rotation_when_remembered_target_is_unreachable`
  in `tests/test_world_model_agent.py` (confirmed to fail on the pre-fix code).
- **This fix alone did NOT unlock L2** (live smoke: still 1/7, 88-89
  actions, no L2 clear observed 2026-07-13). Deeper trace: even with the
  correct floor-colour-aware walkability model
  (`floor_colors_from_probes`, not the naive background-only fallback), L2's
  multi-room maze structure genuinely defeats BFS reachability for most/all
  of the 12 enumerated goal candidates in the run traced — a SEPARATE,
  deeper connectivity issue from the completion-colour bug, not yet root-
  caused. Candidates for a future session: verify whether some "walls" in
  the learned model are actually openable doors requiring an interaction
  first (a static walkability grid can't represent that), or whether the
  floor-colour learning itself needs a longer discovery budget on this
  specific multi-room layout.
- **2026-07-13 follow-up — discovery-budget hypothesis FALSIFIED.** Tried
  `MOVE_PROBE_BUDGET` 16→40 (2.5x more per-level movement-discovery probes)
  and re-ran the live smoke: result was BYTE-IDENTICAL (`1/7, 89 actions`,
  same as the un-bumped baseline), not even a partial improvement. This is
  stronger evidence than "still failing" — if under-sampled floor colour
  were the issue, more probes should have shifted at least one candidate's
  reachability. An identical result instead points AWAY from budget and
  TOWARD the door/gate hypothesis: a static walkability grid can't
  distinguish a permanent wall from an interactive door, so no amount of
  passive floor-colour sampling would change the classification. Reverted
  the budget change (confirmed no diff remains); the stale-completion-colour
  fix above is independently committed regardless of this outcome. **Door/
  gate is now the confirmed-by-elimination recovery lead** for whoever picks
  this up next — needs an active probe (try interacting with/moving into a
  candidate wall cell, re-check walkability after), not more passive
  discovery budget.
- **2026-07-13 — door/gate hypothesis DIRECTLY FALSIFIED; the true goal
  structure found precisely.** `available_actions` at L2 is `[1,2,3,4]`
  only (no interact/click action exists at all), and live-tested moving
  the player into the exact candidate wall cell that separates the
  reachable region from a 1-cell isolated pocket: zero effect across 3
  attempts (player didn't move, the cell's pixels didn't change). A
  genuine static wall, not a door. Separately, walking to every REACHABLE
  `enumerate_goal_cells` candidate (4-5 of the 12) confirmed none of them
  trigger completion — the rarest-colour heuristic is landing on
  decorative clusters. Pixel-dumped the actual "frame with hole"
  structure precisely: a colour-3 (learned floor) 9x9-pixel frame around
  a colour-5 interior with a colour-9 marker inside — but the frame is
  wider than one `cell=5` grid block, so `frame_to_cells`'s coarse
  dominant-colour classification misclassifies parts of the frame's own
  floor-coloured border as wall. Exact win-trigger not yet confirmed
  (touching the frame's border did not clear the level). See
  [[../rounds/r53_unified-harness]] "LS20 L2: door/gate hypothesis
  FALSIFIED" section for the full trace. Next-best: either detect this
  frame-shape directly as a goal candidate (higher priority than plain
  rarest-colour), or extend a corridor/edge-aware walkability model
  (mirroring TU93's `corridor_color_from_probes`/`edge_grid_bfs`) to this
  frame boundary specifically.
- Current legacy solver is generic (post-Round-5 BFS, no game-id / internal
  reads) — see [[SB26]] for the contrasting case where a similarly-named
  "legacy solver" turned out to encode load-bearing mechanic knowledge
  (portal graphs) that DID need mining before any live fix attempt.
