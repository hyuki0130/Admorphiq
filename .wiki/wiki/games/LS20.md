# LS20

> A straightforward multi-room maze/navigation game — earlier notes
> describing "shape/color/rotation matching" were stale and did not match
> either the current legacy solver or the live board; corrected 2026-07-13.

## Current Status

- **Frame-only** (`WorldModelAgent`, R28+): 1/7, clears L1 in 88-89 actions
  via the `execute` (movement/navigation) phase. L2 traced live 2026-07-13 —
  see [[../rounds/r53_unified-harness]] "ls20 build cycle" section for the
  full diagnosis and a fixed bug that didn't fully unlock it.
- **Legacy** `strat_ls20_grid` (`agent_ensemble.py:3831`): fully GENERIC
  brute-force BFS (full reset-and-replay per candidate, frame-hash dedup) —
  its own docstring says "Round 5 removed the L1 hardcoded path. Every level
  is now BFS'd from scratch." **This page's older `hardcoded_levels: L1 move
  sequence` note is STALE** — describes a pre-Round-5 state that no longer
  exists in the code. No portal/shape/rotation complexity of any kind; ls20
  is NOT a sb26-style hidden-mechanic trap (mining this solver confirmed
  that, in contrast to SB26 — see [[SB26]]).

## Observations (corrected 2026-07-13)

- Simple maze: a player marker + movement actions (ACTION1-4), BFS-solvable
  goal-seeking. NOT a shape/rotation/colour-matching puzzle (correcting the
  original 2026-04-20 note below).
- L2's board is a substantially more complex MULTI-ROOM maze than L1 (several
  separated rooms connected by narrow corridors) with multiple candidate
  goal-marker shapes (small "frame with hole" cross patterns) rather than a
  single obvious target.

## Mechanics Hypothesis

Pure grid-maze navigation: a player sprite must reach a goal-marker cell,
found via BFS over the learned walkable-floor model. No shape/rotation
attributes are involved (the original hypothesis below was never re-verified
against the actual board and turned out to be wrong).

## Lessons Learned

- **2026-07-13 — L2 blocker traced and one real bug fixed.** Live-traced why
  the agent falls straight to undirected `interact` on L2 instead of
  attempting navigation: `infer_goal` remembers which colour changed at a
  PAST level's completion (`EffectModel.completion_target_colors()`) and
  prefers that colour as the goal target on the NEXT level too. Measured:
  L1 completed via a colour-0 event, so L2's goal got force-set to
  `target_color=0` — but L2's only colour-0 cluster is a 3px decorative
  speck, not a goal. The original code computed exactly ONE plan with this
  forced (wrong) target and, on failure, fell through WITHOUT ever trying
  `_execute_step`'s existing multi-candidate rotation system
  (`enumerate_goal_cells` / `_advance_goal`, which carries no target_color
  bias and was already built for exactly this kind of situation — see the
  "multi-target navigation" bookkeeping in `world_model_agent.py`). **Fixed**:
  the initial nav-attempt now enters EXECUTE unconditionally on a navigate
  goal and lets `_execute_step`'s own rotation build the plan, so a bad
  single guess can no longer stop the whole candidate list from being tried.
  Regression test:
  `test_nav_attempt_recovers_via_goal_rotation_when_remembered_target_is_unreachable`
  in `tests/test_world_model_agent.py` (confirmed to fail on the pre-fix code).
- **This fix alone did NOT unlock L2** (live smoke: still 1/7, 88-89
  actions, no L2 clear observed 2026-07-13). Deeper trace: even with the
  correct floor-colour-aware walkability model
  (`floor_colors_from_probes`, not the naive background-only fallback), L2's
  multi-room maze structure genuinely defeats BFS reachability for most/all
  of the 12 enumerated goal candidates in the run traced — a SEPARATE,
  deeper connectivity issue from the completion-colour bug, not yet root-
  caused. Candidates for a future session: verify whether some "walls" in
  the learned model are actually openable doors requiring an interaction
  first (a static walkability grid can't represent that), or whether the
  floor-colour learning itself needs a longer discovery budget on this
  specific multi-room layout.
- **2026-07-13 follow-up — discovery-budget hypothesis FALSIFIED.** Tried
  `MOVE_PROBE_BUDGET` 16→40 (2.5x more per-level movement-discovery probes)
  and re-ran the live smoke: result was BYTE-IDENTICAL (`1/7, 89 actions`,
  same as the un-bumped baseline), not even a partial improvement. This is
  stronger evidence than "still failing" — if under-sampled floor colour
  were the issue, more probes should have shifted at least one candidate's
  reachability. An identical result instead points AWAY from budget and
  TOWARD the door/gate hypothesis: a static walkability grid can't
  distinguish a permanent wall from an interactive door, so no amount of
  passive floor-colour sampling would change the classification. Reverted
  the budget change (confirmed no diff remains); the stale-completion-colour
  fix above is independently committed regardless of this outcome. **Door/
  gate is now the confirmed-by-elimination recovery lead** for whoever picks
  this up next — needs an active probe (try interacting with/moving into a
  candidate wall cell, re-check walkability after), not more passive
  discovery budget.
- Current legacy solver is generic (post-Round-5 BFS, no game-id / internal
  reads) — see [[SB26]] for the contrasting case where a similarly-named
  "legacy solver" turned out to encode load-bearing mechanic knowledge
  (portal graphs) that DID need mining before any live fix attempt.
