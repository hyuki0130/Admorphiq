## Mechanics (corrected R56 2026-07-15 — source read + live verified)

The avatar carries a **token** with three attributes: SHAPE, COLOR, ROTATION.
The maze contains:

- **Changer cells** — three kinds, each cycles ONE token attribute (shape /
  color / rotation) when stepped on.
- **Wall cells** — blocking.
- **Goal cell(s)** — each requires a specific (shape, color, rotation). A goal
  is BLOCKING while the token does not match, and level-completes the instant
  the avatar stands on it WITH a matching token.

So a level = route through the right changers to transform the token, then
stand on the goal. `available_actions = [1,2,3,4]` (up/down/left/right; no
interact). **L1** starts already matching in shape+color but one ROTATION step
off (start 270°, goal 0°), so L1 reduces to "pass one rotation-changer, then
reach the goal" — which is why blind navigators cleared it and mislabelled the
whole game as pure maze navigation. Gold L1 solution is 13 actions
(`3,3,3,1,1,1,1,4,4,4,1,1,1`).

A per-level **step counter** (shrinking colour-11 bar, bottom two rows)
decrements each action; on exhaustion the avatar loses one of 3 lives and
repositions to start — **resetting position, token, AND goal progress**.
Longer levels (L2 human baseline 123 > a ~21-42-step life) are only solvable
by collecting step-REFILL cells mid-run to extend the life.

### script25 adapter design (R56 2026-07-15)

State = the multiset of live-region signatures `(color, size, bbox)`,
EXCLUDING thin bands pinned to a frame edge (the step-counter bar / HUD).
MEASURED counter-invariant: a move-and-reverse (up then down) returns to the
exact same key while the counter has advanced two steps — so the key captures
`(avatar position, token appearance)` with no avatar-identity tracking, no
attribute decoding, and no changer-cell semantics hand-coded. Every observed
`(from_key, action, to_key)` edge is stored; exploration is **BFS FROM THE
START key** (`configuration_path` over the discovered edges) — the start is
where every life-loss returns for free, and the win is shallow, so
BFS-from-start finds it while DFS-order gets lost deepening one branch of the
large (position × token) space (measured: DFS found 147 states in 1000 actions
without clearing; BFS-from-start clears at ~600). Composes
`find_regions` + `configuration_path` only. Banked L2 wall + reopen order in
the adapter module docstring.

- **2026-07-16 (R60) — L6 (multi-goal) DECODED + MODEL/SEARCH GT-VALIDATED to a
  LIVE WIN; BANKED (not shipped) — the runtime gap is 3-mover incl. 2D-region
  detection, not a small planner change. Floor holds 5/7 @ 0.5357.** Probed L6
  ground truth (`scratchpad/ls20_l6_*`, engine `pbznecvnfr`/`bejndxqqzf` lines
  2039-2058):
  - **Win condition = EITHER-ORDER multi-goal coverage.** L6 has **2 goals**, each
    with its OWN required token (A@(54,50) req (sh5,co1,ro1); B@(54,35) req
    (sh0,co3,ro2); start token (0,2,1)). `pbznecvnfr` marks a goal satisfied the
    instant the avatar stands on it with THAT goal's matching token, then REMOVES
    the goal sprite (it stops blocking); the level completes only when ALL goals
    are satisfied. Order is free. In the search this is a `satisfied-goals`
    bitmask in the state; a goal blocks (`txnfzvzetn`) only while unsatisfied AND
    the token mismatches — a satisfied goal is passable floor.
  - **THREE moving changers, advancing SYNCHRONOUSLY.** rot- and shape-movers
    patrol horizontal 5-cell tracks; the **color-mover patrols a 2D 2×3 region**
    (track `(19,20)` w11 h11 → 8 on-track cells) via `dboxixicic.npdjlrkhsg`
    (try dir, dir-1, dir+1, dir+2 over the region cells). `step()` advances ALL
    `wsoslqeku` before the avatar moves and UNDOES ALL on a blocked move, so the
    three movers share a single phase = the successful-move count — which keeps
    the joint search tractable (no independent mover dimensions). Landing on a
    mover's NEW cell applies that mover's kind (rot+1 / color+1 / shape+1).
  - **decrement=1 on L6** (vs 2 elsewhere): life = 42 actions (`StepCounter`/
    `StepsDecrement`), plus 2 push-walls and 3 refills.
  - **MODEL + SEARCH ARE PROVEN.** A multi-goal + 3-synchronous-mover pixel sim
    (reusing the L5 push-carry + refill-snap + the general `npdjlrkhsg` mover
    step) joint-BFS found a **71-action plan that replays to a LIVE L6 WIN**
    (`ls20_l6_sim.py`, 5.2M expansions, ~1-2 min from GT maze). So the physics and
    the search are correct and tractable — the collision/carry/mover/goal logic is
    not the open problem.
  - **THE REMAINING GAP is runtime FRAME DETECTION** (why this is banked, not a
    small change): (a) relax the parser to N goals + decode each goal's req
    preview (small); (b) detect all THREE movers frame-only and learn each one's
    track CELL SET + current (pos,dir) — associable BY KIND (rot=colour-1 icon,
    shape=colour-0, color=multi-palette), and inherently phase-synced because all
    three are read from the SAME frame; the hard part is the **2D color-mover
    region** needs enough observation moves to see all its cells before its motion
    model is faithful. The `mover_step(track_cells, pos, dir)` handles the visiting
    order, so only the cell SET + current state must be observed. Recipe for a
    future pass: multi-goal parse → observe ~10 moves recording the three kind-
    icons → build the sim with observed tracks → joint-BFS (satisfied-goals
    bitmask) → open-loop, gated on the MULTI-GOAL signature (≥2 goals, which
    L1-L5 lack) with explorer fallback so the 5/7 floor is preserved on any
    detection/search failure. Target 6/7 ≈ 0.75. See [[../concepts/rotation_state]].
- **2026-07-16 (R60) — L5 CLEARED: pixel-faithful push-carry model + moving-changer
  joint BFS, ls20 4/7 → 5/7, game_score 0.3571 → 0.5357 (all five per-level 1.0).**
  The banked R59/R60 passes had the mechanic source-confirmed but blocked on
  `_detect_pushwalls` fidelity. Resolution — build a SEPARATE pixel-level L5 path
  rather than patch the lattice detector (which correctly clears L3/L4 and must
  not change). Load-bearing facts, all measured:
  - **The physics is a pixel-level simulation, and it is now exact.** A
    `_l5_step` replicating the engine's `step`/`txnfzvzetn`/`prpxgfxlcm`/
    `ullzqnksoj` at the pixel level (bounding-box `collides_with`; carry distance
    = wall-widths until a `fjzuynaokm` cell; carry delta = `dir*width*dist`) plus

    push-walls + a rot-changer, so a single-frame gate can't separate it from L5.
    Instead, while the static plan drains, the adapter WATCHES the rot-changer
    cell (`_detect_rot_cell`): if it moves within a few checks it is L5 (abandon

- **2026-07-15 — PUSH-WALL MODEL BUILT + MEASURED: L3 + L4 clear, ls20 2/7 → 4/7,
  game_score 0.1071 → 0.3571.** The prior probe banked push-walls as needing a
  "separate build"; that build turned out to be small because a push-wall is a
  deterministic TRANSITION RULE, exactly what the joint BFS absorbs. Findings:
  - **Push direction is frame-derivable from the edge line.** A push-wall
    (`gbvqrjtaqo`/`twkzhcfelv`) renders as a 5-pixel colour-1 LINE on one edge of
    its cell; the sprite body extends past that edge, so the push goes TOWARD the
    edge and the avatar collides in the neighbour cell one step over
    (`_detect_pushwalls`: right-edge→push right, bottom-edge→push down, etc.).
    Validated vs engine ground truth: L3's two push-walls (right@(9,5),
    down@(54,5)) and L4's eight all decode correctly.
  - **The push is a slide until the next wall OR GOAL.** In the joint BFS,
    stepping onto a collision cell slides the avatar in the push direction until
    the next cell is impassable or the goal, then the landing cell's effect
    applies. The "or goal" is load-bearing: the engine's push-stop set includes
    goal cells, so a push STOPS one cell before the goal — the avatar must then
    step onto the goal with a normal move (this was the one bug: an early model
    slid onto the goal and mis-declared a win; L3's down-push stops at (54,45),
    one above the goal (54,50)).
  - **Measured:** L3 39 actions (human 73), L4 52 (human 84) — both super-human,
    both replay to live wins; with L1 (13) + L2 (45) that is 4/7 @ game_score
    0.3571, deterministic ×2. No hardcoding — push-walls are detected and
    simulated purely from the frame. Regression tests pin the direction decode
    and the slide-stops-before-goal rule.

- **2026-07-15 (R56d) — ACTION-PREFIX keying PROTOTYPED + MEASURED: banks too,
  CLOSING the L2 investigation for the frame-keyed paradigm. L2 rests at 1/7.**
  The R56c reopen proposed keying state by the agent's action prefix (alias-free
  in a deterministic env) so open-loop prefix replay reaches every life-reachable
  state. Prototyped it against the live L2 engine:
  - Prefix-keying is SOUND in principle — replaying a stored prefix from root is
    deterministic, so it reaches its frontier reliably where the aliased graph

  - But the prototype exposed the compounding blocker: to replay ANY prefix the
    agent must first be cleanly AT ROOT, and reaching root goes through the

    so replays never land on their frontier (`reached=False`); coverage 11
    states, max avatar x=34 (changer at x=49). Behind that sits the irreducible
    cost: every frontier must be RE-REACHED from root each 21-action life

    O(states×depth) ≈ >1000 actions before the deep 45-action solution can even

- **2026-07-15 (R56) — L2 reopen step 1 (key-augmentation) MEASURED and
  REJECTED; the real gate is refill-gated search, not determinism.** The bank

  depends on — so with K≥2 even **L1 stops clearing** (K=0 clears L1 @601; K=3

  small, self-locating graph) is, and augmentation trades it away.** The real
  L2 gate is obstacle 2 (refill-gated long solutions): a ~21-step life can't
