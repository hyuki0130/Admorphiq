# LP85 — Ring-Rotation Permutation Puzzle (NOT click-rare)

> **Mechanic corrected R56 (2026-07-15, from the game source):** LP85 is a
> ring-rotation puzzle. The board holds many BUTTONS; each button press
> cyclically ROTATES a defined ring of cells (moving the pieces in it one step,
> L/R = inverse directions). You win by rotating rings until the target pieces
> land on their goal cells. The old "click the one rare pixel" reading was a
> coincidence of L1's tiny size — it does NOT describe the game.

## Current Status

- **v1** (lp85-305b61c3): **3/8, game_score 0.1637** — L1 18a/17human = 0.892
  (rare-colour sweep), **L2 17a/38human = 1.0** and **L3 24a/31human = 1.0** (both
  capped super-human, the ring-permutation planner). See the L2/L3 SOLVED sections.
- **L2 BANKED then SOLVED (2026-07-15)** — a deep ring-rotation permutation puzzle,
  out of the click-sweep's reach (see the L2 Divergence section). Even the gold
  trace (`data/traces/lp85.npz`) never solves L2 (`levels_completed_after` maxes at
  1); the frame-only ring planner does.
- **L3 SOLVED (2026-07-15)** — same ring machinery, generalized to TWO marker
  colour classes (see the L3 SOLVED section).
- **L4 BANKED (2026-07-15, new structure)** — detection + ring-learning both run
  (20 controls, classes {11,12}), but the per-ring self-test fails 8× because
  single-press cyclic reconstruction breaks on L4's denser overlapping rings; the
  planner fails closed to the sweep and the 3/8 floor holds. Next increment is a
  stronger ring learner, not a parameter tweak (see the L4 section).

## Observations

- `available_actions = [6]` only — pure click game, no movement.
- The internal grid grows per level (L1 32×19, L2 41×41; the canonical layer
  renders 64×64). L2 has ~38 regions and dozens of button sprites.
- Clicking a BUTTON sprite rotates a ring of pieces (a frame-visible
  rearrangement); clicking a non-button pixel is inert (`vctdsvnwjd=False` →
  no state change). On L2, only 3 of 36 rare-colour region-probes moved
  anything — the rare-colour heuristic mostly clicks decorative pixels.

## Mechanics (confirmed from the game source, dev-time only)

- `step` (ACTION6): the clicked cell's sprite must carry a tag
  `button_<id>_<L|R>`. If so, `chmfaflqhy(level_name, id, is_R, maps)` returns
  a list of (piece, new_position) pairs and repositions them.
- `chmfaflqhy` is a **cyclic rotation** of the ring numbered 1..max for that
  button in that level's map: R → each occupant at position `n` moves to `n+1`
  (wrap max→1); L → to `n-1` (wrap 1→max). L and R are exact inverses. Rings
  overlap (a cell can belong to several buttons' rings), so this is a
  Hungarian-rings-class permutation group.
- **CORRECTED 2026-07-15 (driven live via the real engine — see below): the
  moving object is the `goal` sprite, NOT the target.** The `bghvgbtwcb`
  (color 11, a 4×4 four-CORNER sprite) and `fdgmtkfrxl` (color 12) are FIXED
  destination markers. What rides the rings and rotates is the `goal` sprite
  (color 11, a 2×2 SOLID block) — plus the `tile` sprites that tile every
  other ring cell. Win `khartslnwa` = every `bghvgbtwcb` has a `goal` at
  `(x+1, y+1)` (i.e. the moving 2×2 goal lands centered inside a fixed target's
  4-corner frame) AND every `fdgmtkfrxl` has a `goal-o` there. So you rotate
  rings to bring each moving GOAL to its fixed target's centre.
- **L1 = 1 target + 1 goal + 1 ring (A, 26 cells)**; won in **4 button presses**
  (verified: goal rides ring A one cell/press, (21,3)→(18,3)→…→(6,3)=target+1).
  **L2 = 2 targets + 2 goals + 3 rings**: A (26 cells), B (10), C (10); B and C
  each overlap A at exactly 2 cells, B∩C = ∅. There is NO `fdgmtkfrxl` on L2
  (that type appears on later levels) — the prior bank's "2 bghvgbtwcb + an
  fdgmtkfrxl" was wrong. Both goals ride ring A; both targets' destinations are
  on ring A too — the classic Hungarian-rings coupling (rotate A moves both
  goals together; use B/C, which overlap A, to desync one goal).
- Budget: `StepCounter` per level (L1 13, L2 60) — a hard press limit, so a
  blind sweep runs out (probe measured GAME_OVER-class exhaustion).

## Why the click-rare sweep solves L1 but not L2

L1 is tiny (13-press budget, one target piece, few rings) — the per-pixel
rare-colour sweep with round-robin + local-focus (promote a region that just
showed a frame diff) stumbles onto the productive button in 18 presses, matching
the 17-action human. That is a genuine near-human clear, but it is luck of scale,
not a solver: it has no model of which ring to rotate, in which direction, or
how far, to bring a target to its goal.

## L2 SOLVED (2026-07-15): frame-only ring-permutation planner SHIPPED

L2 needs a PLANNED sequence of ring rotations, and a frame-only planner now
produces it. Measured through the real scoring harness (`scripts/script25.py
--games lp85 --max-actions 1000`): **2/8 levels, game_score 0.0803** — L1 + L2
both cleared, up 3.2× from the sweep's **1/8 @ 0.0248** (L1 preserved).

**How the planner works** (`Adapter._planner_step` in `adapters25/lp85.py`,
composed from the generic `kernels/permute.py`), tried first on every level with
the rare-colour sweep as fallback:

1. **Detect** (frame-only, adapter-declared semantics): moving goal tokens =
   color-11 SOLID 2×2 blocks; fixed destinations = the centres of the hollow
   color-11 FOUR-CORNER target frames; rotation controls = color-8 / color-14
   button regions.
2. **Learn each ring** by pressing its button once and diffing the frame:
   `learn_cyclic_successor` orders the changed tile cells into their cyclic loop
   (nearest-neighbour tour) and votes the global rotation direction by colour
   agreement — correct-by-construction as a single n-cycle, robust to the few
   adjacent same-colour tiles whose swap is invisible (`complete_cycle` closes
   any residual gap).
3. **Plan** with `plan_token_assignment`: BFS over goal-token positions
   (snapped to the learned ring lattice) to the destination cells. On L2 this is
   the 264-state / 8-move search proven against the real engine.
4. **Execute** the control sequence; a per-ring self-test (the learned map must
   predict the observed goal displacement) gates the plan, and any failure
   (detection, self-test, empty plan) hands off to the sweep so the L1 floor is
   never lost.

**Verification trail.** The mechanism was first proven by driving the real
`Lp85` engine offline: goal (21,3)→…→(6,3) confirmed the goal (not the target)
rides ring A; the 8-move plan `[A_R,C_R,A_R,A_R,A_R,C_R,C_R,C_R]` replayed
through the engine cleared L2 (score 1→2). The frame-only learner was then
validated to predict both goals' real moves before being wired into the adapter.

**The one obstacle that was solved, not banked:** ring cells carry multi-coloured
tiles (9/1/10/2/15) so rotation is usually visible, but a few ADJACENT cells
share a colour (ring A 3 pairs, B 2, C 0) and same-colour swaps leave no diff.
Greedy colour-matching fractured into bogus short cycles; the tour + direction-
vote reconstruction fixes it (one clean n-cycle regardless of local ambiguity).

**Generic asset.** `kernels/permute.py` — "learn cyclic permutation operators
from single-press diffs (with geometric cycle completion) + BFS a composition to
a target assignment" — is reusable for any rotation/ring puzzle (see [[TR87]]).
Remaining LP85 depth (L4–L8) re-arms the same planner per level; where a level's
structure differs the planner self-tests, fails closed, and the sweep takes over.

## L3 SOLVED (2026-07-15): multi-marker-class generalization

L3 is the same ring machinery as L2 with ONE new structural axis: **two distinct
marker colour classes** (an ordinary `goal`/`target` pair in one colour and a
second `goal-o`/`target-o` pair in another) that BOTH must be placed to win.
The L2 planner hard-coded a single marker colour (`_MARKER_COLOR = 11`), so it
could neither detect nor jointly place the second class. Three bounded changes
generalized it (all frame-only, no game-internal reads):

1. **Marker classes are DISCOVERED, not fixed** (`_detect_marker_colors`): any
   colour that appears BOTH as a solid ≥3-px block AND as a hollow 4-corner
   target frame is a class. Requiring a real corner frame is what stops ordinary
   coloured ring tiles from being mistaken for markers. L2 → {11}, L3 → {11,12}.
2. **Detection / movers / dests are class-tagged** (`_detect_movers`,
   `_detect_dests` return `(colour, cell)`), and the solvability gate now checks
   **per-class** mover-count == dest-count, so a full placement must exist for
   every class before the planner arms.
3. **The BFS is class-aware** (`plan_token_assignment(..., labels, goal_labels)`):
   a token only satisfies a SAME-class goal, so one class's token can never
   cross-satisfy the other's target. Without labels the interchangeable-token
   search would "solve" a board that isn't actually solved.

A fourth fix keeps the ring MAPS complete under the harder L3 layout:
`_planner_background` now excludes the **top-two** frame colours (backdrop +
panel/chrome) so the second backdrop can't be misread as a token class; and
`learn_cyclic_successor(..., candidate_cells=...)` splices a **fully-invisible
ring cell** (one sharing a colour with both neighbours, so absent from the diff)
back into its tour's oversized gap geometrically — without it a ring learns one
cell short and a multi-step plan drifts off.

**Measured through the real scoring harness** (`scripts/script25.py --games lp85
--max-actions 2000`): **3/8 levels, game_score 0.1637** (2× the L2-era 0.0803),
per level — L1 18a/17human = 0.892 (sweep), **L2 17a/38human = 1.0** (capped,
ring planner), **L3 24a/31human = 1.0** (capped, multi-class planner). The L1
floor and L2 clear are preserved; on L4 the planner self-tests, fails closed, and
the sweep runs out the budget (L4 is a new structure, not yet modelled).

**Where the planner stops at L4 — BANKED with the exact divergence (probed
2026-07-15, planner-internals trace).** Detection is NOT the wall and neither is
the BFS: driving the engine to L4 offline, `_detect()` returns True with the same
class discovery working — bg `[3,4]`, **20 button controls** (up from 7 at L3),
`marker_colors {11,12}`, 2 movers / 2 dests with matching per-class counts. The
planner then enters the learn phase, presses all 20 buttons, and learns 16 rings
(4 inert / off-viewport, skipped) — but the **per-ring self-test fails 8 times**:
the learned successor map does not predict the observed goal displacement. The
gate `if self._selftest_fails >= 2: return None` then correctly **fails closed to
the sweep** at action 81, and the 3/8 floor is preserved (final `levels_completed`
= 3).

So the wall is the **single-press cyclic reconstruction breaking down on L4's 20
denser, more-overlapping rings** — `learn_cyclic_successor` mis-orders the changed
cells when many rings share cells and colours, and the self-test (rightly) rejects
the wrong maps. **This is a NEW STRUCTURE, not a bounded tweak.** Explicitly do NOT
"fix" it by raising the self-test threshold — the 8 failures are REAL (the maps are
wrong); a looser gate would ship a bogus plan that either wastes budget or breaks
the L1–L3 floor. The self-test gate is doing its job.

### R59 (2026-07-16) — the L4 failure DIAGNOSED from the engine: it is TWIST TOPOLOGY, not same-colour ambiguity

Drove the real engine at `set_level(3)` (L4) and read the ground-truth ring maps
(`uopmnplcnv[level_name][id]["qcmzcjocmj"]`, the numbered ring positions R rotates
n→n+1). The bank's "20 controls / 16 rings" was the ADAPTER's view (it detects ~20
button REGIONS and learns bogus maps from the spurious/inert ones); the engine truth
for L4 (`ihpokmcrjm`, 57×57, StepCounter 150) is **exactly 2 rings — A and B, each
size 20, sharing 4 cells** (their 4 crossing points). So most "16 learned rings" are
detection noise the self-test rejects; the real problem is that even the **2 genuine
rings fail geometric reconstruction**.

**Root cause — the rings are TWISTED loops, and geometry cannot recover a twist.**
Ring A's true cyclic order runs DOWN column 4 (rows 2-6,12-16) then DOWN column 14
(rows 2-6,12-16) — both sides same-direction — so the true cross-gap links are
`(16,4)→(2,14)` and `(16,14)→(2,4)` (diagonally FAR). The nearest-neighbour tour
(`_cyclic_order`) instead links `(16,4)→(16,14)` (the geometrically-near
simple-RECTANGLE order). Measured: the tour recovers **0 of 2** rings' true cyclic
order. This is NOT the same-colour-adjacency problem the earlier bank assumed —
same-colour ties are a red herring here; the tour is topologically wrong even with
perfectly distinct colours, because a twisted loop's connectivity is undetermined by
cell geometry alone.

**Fix IMPLEMENTED — OBSERVATION-FIRST successor in `kernels/permute.py` (R59).**
`learn_cyclic_successor` now builds the successor from the OBSERVED colour movement
first: a cell whose before-colour is UNIQUE on the ring maps directly to the (single)
cell showing that colour after the press — recovering the true successor even across
the far twist gap — and only same-colour ties fall through to the geometric tour.
`_close_cycle` weaves these authoritative observed links into one Hamiltonian cycle,
bridging the remaining short same-colour gaps (incl. a spliced fully-invisible cell)
by tour adjacency. Unit-validated: a synthetic twisted-loop (the exact L4 geometry —
two same-direction columns, far cross-gap link) that the nearest-neighbour tour gets
wrong is now recovered exactly (`test_learn_recovers_a_twisted_loop_via_observed_successors`);
all 9 permute tests pass, incl. the previously-failing invisible-cell test.

**BUT L4 still 3/8 @ 0.1637 (measured @2000) — a SECOND gap, banked.** The kernel fix
is correct, generic, and non-regressing (L1-L3 floor held), but does not by itself
clear L4. The remaining wall is FRAME DETECTION on L4's dense 57×57→64×64 render: the
adapter detects ~20 button regions of which only 2 are real rings (A, B), and the
observation-first learner needs the frame to expose CLEAN per-cell region colours for
those 2 rings to pin the twist — which the dense render + ~18 spurious/inert button
presses (budget waste + self-test churn) do not reliably provide. The next increment
is a DETECTION pass (identify the 2 genuine ring-controls and read their ring cells
as distinct-colour regions on the dense frame), not a further kernel change. The
observation-first kernel is kept as that build's validated base.
⛔ Do NOT pursue "multi-press for same-colour adjacency" as the primary lever —
measured, the tour failure was TWIST topology (now fixed observation-first); the open
lever is frame detection of the 2 real rings, not disambiguation.

## Lessons Learned

- **Verify the moving object before writing the mechanic down.** The
  2026-07-15 bank first said "rotate the TARGET onto its goal." Driving the real
  engine showed the opposite: the target is FIXED and the GOAL token rides the
  ring (L1: goal (21,3)→…→(6,3)=target+1, target never moves). A source read
  alone got the shape (ring rotation) right but the moving object wrong;
  observing one real press corrected it. Prefer live driving over static reads
  for "what actually moves".
- **A coincidental heuristic is not a mechanic.** "Click the rare pixel"
  cleared L1 and got written down as the game's rule; the source shows the real
  mechanic is ring rotation, and the heuristic only worked because L1 is tiny.
  Reading the win condition and effect function from the source (dev-time)
  before generalising would have caught this at L1, not L2.
- **Near-human at L1 ≠ scalable.** The 18-vs-17 clear is real efficiency on a
  13-press level, but it is stumble-luck against a small ring set, not a solver
  — it carries zero information about which ring to rotate. Depth needs a plan.
- Even a gold trace can be a dead end: `data/traces/lp85.npz` never solves L2,
  so imitation/replay is unavailable here — the mechanism had to come from the
  source. [[../lessons/frame_diff_as_probe]]
