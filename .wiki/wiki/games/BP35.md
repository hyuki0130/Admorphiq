# BP35 — Gravity Platformer (move + click-destroy)

> Move the player horizontally and click destructible blocks so gravity drops it toward a fixed `+`-shaped exit marker; win = the player reaches the exit. Physics is DETERMINISTIC and per-action (gravity resolves within a step).

## Current Status

- **v1** (bp35-0a0ad940): legacy `bp35_platformer` 1/9 (L0 in 16 actions,
  internals-tuned); generic R23 8B 0/9. Only one API version.
- R56 namespace-safe MOVE+CLICK transition-graph explorer: **0/9** at the
  1000-action smoke (and 0 at 10000). **BANKED** — and per the R56b dynamics
  correction (Mechanics Hypothesis), the wall is deeper than "deep target":
  BP35 has HIDDEN velocity, so the frame-key graph is aliased, and the exit
  recedes with the player. A gravity-planner reopen was ATTEMPTED and its
  assumptions were falsified — not built (see Notes).

## Observations

- `available_actions = [3, 4, 6, 7]` (background colour 5). ACTION3/ACTION4
  move the player horizontally (then it falls to rest); ACTION6 clicks a
  destructible block to remove it; ACTION7 undoes.
- Terrain (colour 10, large regions), a grid of destructible blocks (colour
  14 / colour 3, small same-size clusters), the player (colour 9, ~6 cells),
  and a `+`-shaped EXIT marker (colour 11, ~2 cells).
- HUD: a bottom-row step counter (colour 0, row 63) — edge-pinned, masked.

## Mechanics Hypothesis

**R56b CORRECTION (2026-07-15)**: BP35 is a MOMENTUM platformer with HIDDEN
velocity, not the fixed-step "reach a fixed exit" gravity puzzle first
assumed. A proper dynamics probe of the available controls showed:
- ACTION3/ACTION4 are momentum moves: pressing ACTION4 repeatedly displaced
  the player by 2,6,6,6,6,3 cells (ACCELERATION) — the same action from the
  same visible position gives different displacement depending on accumulated
  velocity, and velocity is NOT in the frame.
- The `+` EXIT RECEDES: it stays a fixed 2 cells ahead of the player as it
  moves (player col 20→22→28…, exit col 22→24→30…), so it is not a fixed goal
  to route toward.
- Clicking the colour-14 block centroids is inert (no player/exit change), so
  the "destroy-then-fall" model is unconfirmed.
WIN = the engine's own signal. Because velocity is hidden, the same masked
frame transitions differently under the same action — the frame-key
transition graph is ALIASED (a hidden-state game, R53 "dealias" territory).

## Solution Pattern (frame-only, no clear)

Generic MOVE+CLICK transition-graph exploration re-expressed through
namespace-safe kernels, with a HYBRID action alphabet:
1. Mask the edge-pinned HUD, then canonicalise the masked board into a
   stable state key ([[../concepts/frame_hashing]]).
2. Candidate actions at a state = the available moves PLUS a click on each
   salient region centroid ([[../concepts/sprite_cluster]]) — a bounded set,
   not the 64×64 click space.
3. Record every observed `(state, action, next_state)` transition; take an
   untried action at the current state, else route to the nearest state with
   an untried action.

**Why it does not clear**: even though L0's optimal solve is short (16
actions), the hybrid alphabet has ~10-17 candidates per state (2 moves +
every block/marker centroid) and the winning destroy-then-fall-then-navigate
route is a specific deep sequence; blind frontier search branches too widely
to hit it at the smoke budget. It is a valid graph, just a deep target.

## Notes / Refactor Plan

- Reopen pointer (REVISED after R56b — harder than the original): the
  original "learn fall dynamics + `configuration_path` to a fixed exit"
  pointer is FALSIFIED (fixed exit, fixed displacement, droppable blocks all
  disproven) and must NOT be built as-is. Since this is a momentum platformer,
  a solver must FIRST recover the hidden velocity state (an R53 dealias-style
  hash augmentation that folds in recent motion, not just the current frame),
  then model the acceleration dynamics + the receding-exit relation before any
  planner. Attempting the planner on the visible frame alone is building on a
  falsified model.

## Lessons Learned

- **A determinism probe is only as good as the action it exercises**: the
  original "determinism confirmed, gravity is per-action" finding was WRONG —
  it issued ACTION1, which is not in this game's `available_actions`
  ([3,4,6,7]), i.e. a no-op that trivially reproduces (it only ticks the step
  counter). It never touched the real controls. A proper probe of ACTION3/4
  later revealed momentum + hidden velocity. Lesson: a repeat-probe must use
  an action that is actually AVAILABLE and actually MOVES the agent, or it
  proves nothing about the dynamics.
- **Hidden state hides from a single frame**: BP35's velocity is not visible,
  so the "same frame" can behave differently — a frame-key graph is aliased.
  Verify observability (does the visible frame fully determine the next
  transition?) before trusting a `(frame, action) -> frame` model.
- The legacy `bp35_platformer` is internals-tuned (0/9 generic) — a short
  L0 solve is not evidence a generic search will find it.
