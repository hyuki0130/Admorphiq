# BP35 — Gravity Platformer (move + click-destroy)

> Move the player horizontally and click destructible blocks so gravity drops it toward a fixed `+`-shaped exit marker; win = the player reaches the exit. Physics is DETERMINISTIC and per-action (gravity resolves within a step).

## Current Status

- **v1** (bp35-0a0ad940): legacy `bp35_platformer` 1/9 (L0 in 16 actions,
  internals-tuned); generic R23 8B 0/9. Only one API version.
- **R59 frame-only solver — clears 1/9 (L0) @ 0.0145, deterministic ×2 — the
  FIRST generic clear (was 0/9).** The R56b "hidden velocity / aliased graph /
  receding exit" diagnosis was WRONG (see Mechanics Hypothesis): BP35 is
  DETERMINISTIC and fully frame-observable. The shipped `Adapter` parses the
  camera-scrolled window into an accumulating world map (colour→kind), tracks
  the player's x from the marker's screen column, and runs a faithful-sim BFS
  over (cell, destroyed-blocks) toward the gem — climbing (clicking the block
  directly above) to reveal the off-screen gem, with visited-aware frontier
  exploration so the climb does not dead-end. Ties the internals-tuned legacy
  1/9 but FRAME-ONLY. L1–L8 not yet cleared (spike handling + deeper-level
  tuning remain).

## R59 solver build — faithful sim + BFS VALIDATED; runtime reveal-loop pending

The dedicated build reached its hard-core milestone (the algorithm is proven;
the frame-only runtime loop is the remaining engineering):

- **FAITHFUL SIMULATOR — validated.** A pure world-coordinate sim (move = ±1
  cell + `fall` in the gravity dir until landing; click = destroy a
  `qclfkhjnaac` block, and if it is the cell `(px, py+grav)` the player climbs
  the cleared column) reproduces the legacy L0 solution STEP-FOR-STEP against
  `env._game` (every position matches) and reaches WIN. Cell kinds:
  `gem`/`spike`/`destroy`/`wall`/`pass`; left edge (x<0) is a wall-bump.
- **BFS SOLVER — works.** BFS over (player cell, destroyed-block set) with the
  action set {L, R, click-left, click-right, click-above} (clicks bounded to the
  player's neighbours — clearing one enables a move or a climb) SOLVES L0 in 15
  actions (`RRRRLLCACLLCARCACALL`), and that sequence **replays to WIN on the
  live engine** — independent confirmation the sim is faithful and the search
  is correct.
- **Camera de-scroll — solved deterministically.** `cam_y = player_world_y*6 -
  36` (verified py=23→102, py=20→84, py=16→60), so the frame window is fully
  determined by the tracked player y — the player sits at screen row 36
  (camera-locked). Colour→kind (cell-centre sampled): **5=wall, 10=pass,
  14=destroy, 11=gem/exit** (0/3/15 = HUD/pad → ignore). The parser reads cells
  RELATIVE to the player marker, so any player-detection pixel offset cancels.
- **RUNTIME reveal-loop — 4 variants built, all GAME_OVER; the crux is now
  ISOLATED.** Debug (comparing tracked vs internal player position) proved the
  map parse + accumulation are CORRECT (map grows 121→481 cells, colours map
  cleanly) and the sim is faithful — the failure is **drift-free frame-only
  player tracking.** Tracking the player by SIM PREDICTION (apply the sim's
  predicted landing after each action) accumulates error against the incomplete
  online map, so the tracked position drifts (observed: it walked to x=12,
  outside the 11-wide world) and the loop wanders until the step budget
  GAME_OVERs (L0 has no spikes — the loss is pure budget exhaustion). The fix is
  a MEASURED tracker, not a predicted one:
  - **Δx (horizontal):** camera x is fixed, so the player marker's SCREEN COLUMN
    gives x directly — `x = round((marker_col − c0)/6)` for a per-level anchor c0
    (or track Δcol/6). The marker pixel offset cancels if the gem/blocks are read
    against the same marker.
  - **Δy (vertical):** the player is camera-LOCKED at screen row 36, so y is not
    on screen — measure it from the TERRAIN SCROLL between consecutive frames
    (vertical cross-correlation of the colour map, shift = Δy·6), or exploit
    `cam_y = y·6 − 36` inverted from a revealed static landmark. Do NOT trust the
    sim to advance y.
  **R59 runtime continuation (later attempts) — two more fixes landed, one
  blocker left:** (1) px tracking SOLVED — the player marker's screen column
  gives x exactly (`x = round((marker_col − c0)/6)`); this removed the
  horizontal drift (player stays in-bounds). (2) GEM COLOUR was wrong: the exit
  renders as **colour 7** (a '+' glyph), NOT 11 — with 7=gem the player now
  climbs to within ~3 rows of the gem. REMAINING blocker: the EXPLORATION POLICY.
  Greedy "minimise y" (climb) gets stuck in dead-end columns and wanders off the
  gem's column, exhausting the step budget before reaching the gem. The fix is a
  proper frontier/backtracking exploration (or climb-the-whole-map-then-BFS),
  plus py tracking (still sim-predicted — measure it via terrain-scroll). Colour
  map is now {5:wall, 10:pass, 14:destroy, 7:gem}. Player reaches world y≈10
  (gem at y=7) — the last mile is the exploration policy, not the sim/parse/px.
  Once the tracker is measured (not predicted), the accumulated map + sim-BFS
  (unknown = wall for safety once a region is revealed; soft-floor only for
  frontier reveal) should reach the gem — the 15-action L0 solution already
  proves the search half works. Then spike-colour handling + the 9-level
  generalisation remain. The sim + BFS + camera formula + colour map are the
  reusable, validated foundation (proven correct — keep them).

## Reopen — a solvable deterministic (position, destroyed-blocks) BFS

The mechanic (above) makes BP35 a clean deterministic planning problem:
actions {ACTION3 = left+fall, ACTION4 = right+fall, ACTION6 = destroy a block
(and climb if it is directly above)}; state = (player world cell, set of
destroyed blocks); goal = reach the gem. This is the same shape as the sk48
faithful-simulator + A*/BFS solve, and needs the same build:
1. A FAITHFUL offline simulator of move+fall+destroy (a naive hand model and a
   real-engine replay-BFS BOTH failed to find the known-solvable L0 — the
   legacy brittle solver clears it — so subtle click-coordinate / fall details
   must be lockstep-validated against the engine, exactly the sk48 lesson).
2. A frame-only state parser (player cell, block cells, gem when on-screen)
   that de-aliases the camera scroll by tracking the player's WORLD position
   (cumulative displacement), not the raw frame.
3. BFS/A* over (position, destroyed-blocks) to the gem, executed as
   frame-only clicks (block centroids) + moves.
Open sub-puzzle found in R59: the search stays confined to y≥16 because the
blocks that would open the path above the y=15 wall are OFF-SCREEN (above the
camera window) until the player climbs, and the player cannot climb past the
solid wall — a chicken-and-egg the correct simulator must resolve (there is a
path; the legacy solver proves L0 is winnable). Floor 0/9, nothing to lose.

**L0 solution ORACLE (from the legacy brittle `strat_bp35_platformer`,
`agent_ensemble.py` — reads internals, but its ACTION SEQUENCE is the ground
truth for the solver pass):** start player (3,23), gravity up, exit (3,7).
`RIGHT×4 → click(7,19) [climb] → LEFT×2 → click(4,16) [clears a block, NO
movement] → LEFT → click-above×2 [float up] → RIGHT to col 5 → …`. Two things a
frame-only solver MUST replicate: (a) it clicks NON-above blocks like (4,16) to
pre-clear a path the LATER climbs use — so the search space is genuinely
{move, destroy-any-onscreen-block, climb}, not just climb; (b) the legacy
click coord is `(gx*6+3, gy*6+3-cam_y)` — a CELL-CENTRE (+3) screen click; a
frame-only adapter clicks the block's frame centroid (the engine re-adds
`camera_y` via `hyntnfvpgl`), which lands the same cell. The R59 real-engine
replay-BFS failed to find this despite exact clicks — likely because the
path threads a specific move/clear/climb ORDER its dedup pruned; the solver
pass should validate the transition against this exact sequence first.

## Mechanics Hypothesis

**R59 RE-EXAMINATION (2026-07-16) — the R56b momentum/hidden-velocity bank is
OVERTURNED. BP35 is a DETERMINISTIC, fully FRAME-OBSERVABLE grid platformer.**
Read from the game source (`pywlvyklps`/`fsvnqdbzrp`/`gwfodrkvzx`/`pbsitubcfd`)
and confirmed by faithful `env._game` probes (world 11×36, gravity dy=-1 i.e.
"up"):
- **No velocity, no momentum.** Each ACTION3/ACTION4 moves the player EXACTLY
  ONE cell horizontally, then it falls deterministically in the gravity
  direction until landing. The R56b "2,6,6,6,6,3 acceleration" was a
  MISREAD of FALL DISTANCES (1 horizontal + N vertical); measured world
  positions show clean unit horizontal steps: (3,23)→(4,23)→(5,23)→(6,23)→
  (7,20)→(8,20). The `(position)→(position)` graph is NOT aliased.
- **The exit is FIXED**, at world (3,7). The R56b "receding exit" was a
  CAMERA-SCROLL artifact: the frame is a camera window over a tall (36-cell)
  level and the camera follows the player, so the exit's SCREEN column drifts
  while its WORLD position never moves.
- **Clicks are FUNCTIONAL** (R56b "inert" is FALSE): ACTION6 on a colour-14
  `qclfkhjnaac` block DESTROYS it (measured colour 14→5). And clicking the
  block DIRECTLY ABOVE the player (in the gravity direction) makes the player
  CLIMB into the cleared column — measured (7,20)→(7,16) from a single click.
  `pbsitubcfd` only relocates the player when the clicked cell equals
  `(px, py-1)`; other clicks still remove the block but don't move the player,
  which is why the R56b probe (checking only player/exit position) called them
  inert. The engine converts the ACTION6 screen coords to world via
  `hyntnfvpgl(x, y + camera_y)` (offset 0, scale 6) — so the adapter clicks the
  block's FRAME centroid and the camera offset is handled engine-side.
WIN = the engine's own signal (player reaches / falls onto the gem). The state
is FULLY (player world position, set of destroyed blocks) — no hidden state.

## Solution Pattern (frame-only, no clear)

Generic MOVE+CLICK transition-graph exploration re-expressed through
namespace-safe kernels, with a HYBRID action alphabet:
1. Mask the edge-pinned HUD, then canonicalise the masked board into a
   stable state key ([[../concepts/frame_hashing]]).
2. Candidate actions at a state = the available moves PLUS a click on each
   salient region centroid ([[../concepts/sprite_cluster]]) — a bounded set,
   not the 64×64 click space.
3. Record every observed `(state, action, next_state)` transition; take an
   untried action at the current state, else route to the nearest state with
   an untried action.

**Why it does not clear**: even though L0's optimal solve is short (16
actions), the hybrid alphabet has ~10-17 candidates per state (2 moves +
every block/marker centroid) and the winning destroy-then-fall-then-navigate
route is a specific deep sequence; blind frontier search branches too widely
to hit it at the smoke budget. It is a valid graph, just a deep target.

## Notes / Refactor Plan

- Reopen pointer (REVISED after R56b — harder than the original): the
  original "learn fall dynamics + `configuration_path` to a fixed exit"
  pointer is FALSIFIED (fixed exit, fixed displacement, droppable blocks all
  disproven) and must NOT be built as-is. Since this is a momentum platformer,
  a solver must FIRST recover the hidden velocity state (an R53 dealias-style
  hash augmentation that folds in recent motion, not just the current frame),
  then model the acceleration dynamics + the receding-exit relation before any
  planner. Attempting the planner on the visible frame alone is building on a
  falsified model.

## Lessons Learned

- **A determinism probe is only as good as the action it exercises**: the
  original "determinism confirmed, gravity is per-action" finding was WRONG —
  it issued ACTION1, which is not in this game's `available_actions`
  ([3,4,6,7]), i.e. a no-op that trivially reproduces (it only ticks the step
  counter). It never touched the real controls. A proper probe of ACTION3/4
  later revealed momentum + hidden velocity. Lesson: a repeat-probe must use
  an action that is actually AVAILABLE and actually MOVES the agent, or it
  proves nothing about the dynamics.
- **Hidden state hides from a single frame**: BP35's velocity is not visible,
  so the "same frame" can behave differently — a frame-key graph is aliased.
  Verify observability (does the visible frame fully determine the next
  transition?) before trusting a `(frame, action) -> frame` model.
- The legacy `bp35_platformer` is internals-tuned (0/9 generic) — a short
  L0 solve is not evidence a generic search will find it.
