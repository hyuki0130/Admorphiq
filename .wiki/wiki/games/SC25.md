# SC25

> A TWO-PHASE spell game per level: click a 3×3 grid to toggle cells until the
> pattern EXACTLY matches an (auto-selected on L0–L2) target spell — which
> AUTO-CASTS — then walk the player into an exit. Both the R57 "T5/T6 vs T1"
> ambiguity and the wiki's old "click 3×3 slots" note are resolved by this:
> it is pattern-match THEN navigate (source-read + live-verified R56 2026-07-15).

## Current Status

- **script25 adapter** (`adapters25/sc25.py`, R56 2026-07-15): **3/6**,
  game_score **0.0427**. Clears L0/L1/L2. L1 in **9 actions** (human baseline
  6 → per-level RHAE **0.44**, near human-efficient). Reads the DISPLAYED
  target pattern (colour-marked preview) and clicks precisely the differing
  cells, then BFS-navigates to the exit. Generic; beats the brittle 2/6.
  (Earlier blind-search version was 1/6 / 1.8e-05 — the target-reading step
  was the unlock.)
- **Legacy** `spell_cast` (`agent_ensemble.py`): 2/6, but reads sprite names
  (`sptivk-*`) — brittle, does not transfer to unseen games.

## Mechanics (R56 2026-07-15 — source read + live verified)

`available_actions = [1,2,3,4,6]`. Each level:

1. **Pattern phase.** An interactive 3×3 grid of toggle cells (9 equal-size
   regions in a lattice at fixed pixel positions) + a target-pattern preview.
   ACTION6-clicking a cell flips it. When the grid EXACTLY matches the target
   spell's 3×3 pattern, the game **auto-casts** — no separate cast click.
   Levels 0–2 auto-select the spell; L3+ require clicking a spell sprite first.
2. **Navigate phase.** After the cast, move the player (ACTION1-4) into an
   exit cell to complete the level.

A per-level **click/action budget** (right-edge fill bar; L0=50, L1=25, …)
rises each action; overrun = GAME_OVER, resetting position + grid (not lives).
Gold solutions are short: L0 = 4 toggles + ~12 moves; L1 = 3 toggles + 2 moves.

### script25 adapter design (R56)

**Pattern phase — read, don't search.** The colour-marked target-preview
widget beside the grid is read into an `rows×cols` boolean via
`kernels.template_occupancy` (mark centroids binned over the preview block's
extent). The matched display = `base XOR target` (`base` = parity-0 cell
colours, captured on the settled frame AFTER the first action — every level's
first click is eaten by an intro/settle redraw, so that frame is settled AND
parity-0). The adapter clicks exactly the cells whose shown colour differs
from that target display, predicting each toggle so the post-click cursor
colour can't cause a re-click loop. Efficient (≈ toggle count) AND lands on
the EXACT match (genuine cast, not a near-match false positive — the game
highlights near-matches, which defeated the earlier blind-search version).

**Navigate phase.** One frame-keyed BFS-from-start (the [[LS20]] planner) over
the move graph. Per-key action split: pre-cast keys offer CLICKS (player can't
move → clean toggle space), post-cast keys offer MOVES. State key = live-region
signatures minus the left/right edge UI strip (budget bar). **death-artifact
discard**: a budget-overrun move that resets to start is not recorded/tried so
a fresh-budget life re-attempts it (without this, nav plateaus at 19 states).
**cast detection** = a click redrawing >1 grid cell, kept as confirmation.

## Lessons Learned

- **2026-07-15 (R56) — the mechanic is pattern-match THEN navigate, not
  "click slots".** Reading the source settled the R57 ambiguity: the win check
  is `jsdgfdkecx` (exact 3×3 equality vs the target) → auto-cast → then walk
  the player sprite (`pluyoo`) into the exit. Frame-keyed BFS with a per-key
  click/move split clears L0 generically without decoding any of this.
- **2026-07-15 (R56) — near-match highlighting is why you READ the target
  instead of searching for it (RESOLVED, was a wall).** Blind toggle-search
  reaches SOME multi-cell redraw first, but the game HIGHLIGHTS near-matches (a
  within-one-cell toggle also redraws several cells), so a search commits to a
  non-winning near-match state (1/6). The fix — the "read the win condition off
  the frame" move — is to read the DISPLAYED colour-marked preview into a 3×3
  boolean (`kernels.template_occupancy`) and click exactly the differing cells,
  landing on the EXACT match. This took SC25 from 1/6 (0.00002) to 3/6 (0.043),
  L1 near-human (9 actions). Two measured gotchas were load-bearing: (a) the
  target must be read on a SETTLED frame (the level-entry frame still shows the
  previous level's preview until the first action redraws it → require two
  equal reads); (b) `base` (parity-0 cell colours) must be captured on the
  frame AFTER the first action, which every level eats without toggling
  (intro/settle), so it is settled AND parity-0.
- **BANK (remaining) — navigation efficiency + L3 spell-selection. TWO
  attempts, both reverted to the 3/6 floor; the tension is now precisely
  understood.** The pattern phase is cheap, but the post-cast navigate-to-exit
  is a blind BFS (L0 ≈ 460, L2 ≈ 1380 actions).
  - **Attempt 2 — DECOUPLED navigator (2026-07-15).** Per the greedy bank's
    own recommendation, moved post-cast navigation to a self-contained module
    (own move-only frame-graph, `_in_nav` phase flag, cast entry by event or
    key-membership). L0/L1 preserved, but **L2 regressed** (did not clear in
    3000+): after the FIRST cast on L2, later lives fail to RE-ENTER
    navigation. Root cause (the load-bearing insight): the committed COUPLED
    version clears L2 because the cast STATE is a persistent node in the
    shared graph (`_post_cast_keys`), so every life the pattern BFS routes
    straight back to that known cast key and hands to nav — cross-life cast-
    state recognition for free. Decoupling loses it: re-entry then needs
    either the cast EVENT re-firing (needs the exact match-click transition
    re-observed) or state membership (but L2's cast frame VARIES life-to-life
    from the cast animation), and neither reliably re-triggers, so L2 dies
    unnavigated on later lives. **So L2's clear structurally DEPENDS on the
    coupled whole-graph cross-life recognition — which is exactly what greedy
    needs to NOT touch. The real reopen is a pattern-phase robustness fix:
    make the pattern re-solve deterministically reach a STABLE, recognised
    cast state each life (mask the cast animation out of the cast key), so nav
    re-entry is reliable in isolation; only then does the decoupled navigator
    hold L2.** Reverted; floor intact at 3/6.
  - **Attempt 1 — greedy bolt-on (2026-07-15).** Detecting the player (identity-by-movement) + exit
  (the LARGER static region of the player's own colour — SC25 draws both in
  one colour: 9 on L0/L1) and moving greedily toward it is MEASURED to clear
  L0 in **34 actions (was 461)** and keep L1 fast — a ~13x win. BUT it
  regressed L2: L2's post-cast board is NOT an open room, the same-colour
  player/exit are ambiguous, and the greedy measures an incoherent move→delta
  map (a diagonal `(-8,8)` "left"). Falling back to the BFS nav proved
  intractable to bolt on because the two share machinery: the per-key
  `post_cast` tag gates BOTH the pattern-solver's directed clicking AND the
  BFS's clicks-vs-moves label choice, and the transition graph is shared —
  so greedy's moves either POLLUTE the BFS graph (20 greedy steps on L2 →
  213 fragmented states, BFS stalls) or, if isolated, un-tag the nav states
  and let directed clicking hijack them. **Reopen with a DECOUPLED nav
  controller**: once the cast fires in a life, hand the rest of the life to a
  SELF-CONTAINED navigator with its OWN move-only frame-transition graph
  (a mini [[TU93]]), never touching the pattern-phase graph or `post_cast`
  tags; greedy-first with that controller's own BFS as fallback. That
  separation is the real fix; the bolt-on is a dead end. L3+ additionally
  need spell-icon selection clicks (L0–L2 auto-select the spell).
- Frame-only (grid detected as an equal-cell lattice, target read from the
  preview) → the adapter transfers across version hashes, unlike the legacy
  `spell_cast` which reads `sptivk-*` sprite names. See
  [[../lessons/hardcoded_is_anti]].
