# LF52 — Cursor-Move + Click-to-Connect Puzzle

> Move a cursor and click game objects to LINK them; a level wins on an internal completion flag, within a per-level action budget. First characterised in R56 (was "Unknown post-regression").

## Current Status

- **v1** (lf52-271a04aa): agent regression 0/10 (a lone 1/10 existed only at a
  50000 ensemble budget via `adaptive_c2`, never transferred). Only one API
  version.
- R56 namespace-safe move+click transition-graph explorer: **0/10** at the
  1000-action smoke. **BANKED** — but this is the FIRST generic
  characterisation of the mechanic (below).

## Observations

- **Two frame LAYERS that are BYTE-IDENTICAL** (same histogram, same
  per-action diff) — the second layer is redundant; keying on layer 0 loses
  no state. (This resolves the long-standing "2-layer structure matters"
  question: here it does not.)
- `available_actions = [1, 2, 3, 4, 6, 7]` (background colour 10, live board).
- `ACTION1..4` move a CURSOR one cell (a ~1-pixel diff — a small marker
  relocates). `ACTION6` clicks: on a game object it triggers a CONNECT/LINK
  (a ~21-pixel diff); in the bottom-left corner (x<16, y>48) it triggers a
  redraw. `ACTION7` undoes.

## Mechanics Hypothesis

Source names a click→link operation (`dghsidbuet` → `xpcuvjyrgu` walks
neighbours and attaches via `oyzpaylqco`); WIN is an internal completion flag
(`iajuzrgttrv`), LOSE is a fail flag or a per-level ACTION-COUNT budget
scaling with level (`asqvqzpfdi` vs 64 / 64*5 / 64*10).

**R56b validation probe (2026-07-15) — the controllable-link premise is
FALSIFIED.** A validate-first probe (run BEFORE building a link planner, per
the bp35 lesson) found the click effect is deterministic and frame-observable
(two fresh envs clicking the same object → byte-identical frames; re-clicking
is idle, diffs [21,1,1], so no hidden accumulation) — BUT it is
INPUT-POSITION-INDEPENDENT: an ACTION6 click grows a fixed colour-9 region at
the SAME game-determined location (+20 cells at grid (17-20,16-21))
regardless of WHERE it clicks (all four directions + far-apart coordinates
identical) AND regardless of any preceding ACTION1-4 cursor moves (which do
not shift the growth). So there is no POSITIONAL click→link operator to learn
and no cursor steering — the observable draw is a predetermined side-effect
animation, not a player-controlled link. The R57 "pairwise matching" guess is
NOT supported by the observable dynamics.

## Solution Pattern (frame-only, no clear)

Generic MOVE+CLICK transition-graph exploration (the `bp35` hybrid-alphabet
pattern):
1. Mask any HUD, then canonicalise the masked layer-0 frame into a stable
   state key ([[../concepts/frame_hashing]]).
2. Candidate actions at a state = the available moves PLUS a click on each
   salient region centroid ([[../concepts/sprite_cluster]]).
3. Record every observed `(state, action, next_state)` transition; take an
   untried action, else route to the nearest state with an untried action.

**Why it does not clear**: per the R56b probe, there is no frame-derived
positional operator to plan over — the observable click effect does not
depend on click position or cursor state, so neither the explorer nor a
positional planner can steer toward the win.

## Lessons Learned

- **The "2-layer frame" mystery is resolved**: LF52's two layers are
  byte-identical (redundant), so the long-standing worry that state-keying
  must combine layers does not apply here — layer 0 is sufficient.
- A game left "Unknown post-regression" for months was characterisable in one
  pass by reading the source (cursor-move + click-to-connect, internal win
  flag, level-scaled action budget) rather than only bisecting regressions.
- **Silent regression root cause (2026-04-21): budget starvation, not a
  broken strategy** — raising the ensemble `total_budget` to 50000 restored
  the lone 1/10.
