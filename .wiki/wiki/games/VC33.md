# VC33

> Frame-observation solver; L0 cleared super-human-efficiently by picking the winner of two decoy-paired regions via its smaller containing panel and committing to it exclusively.

## R56 iteration 2 — L0 efficiency (2026-07-15)

VC33 shows two identically-sized colour-9 regions: a WINNER (~3 clicks clears
the level) and a DECOY (clicking it INFLATES the winner's requirement). The
prior adapter probed every candidate once (touching the decoy → inflation)
then round-robined → L0 in 54 actions. **Fix, VERIFIED LIVE:** the winner is
the region nested in the SMALLER containing panel (368 vs the decoy's 848) —
clicking ONLY it clears L0 in exactly 3 clicks, never touching the decoy.
`_region_candidates` now orders by ascending containing-panel size (nested
targets first, winner leads; non-nested candidates keep their old rarest-
colour order), and a lead-commit phase clicks `candidates[0]` exclusively
before probing anything else. **L0: 3 actions vs a 7-action human → score 1.0
(capped), game_score 0.0006 → 0.0357 (60x).** Floor preserved: if the lead
doesn't clear, it falls through to the original probe-all recycle.

**L1+ banked (no gold oracle):** L1 is also a two-colour-9 layout but the
3-click lead doesn't clear it (human baseline 18 vs 7). The game source shows
the real mechanic is a CONNECT/ALIGN puzzle (`ielczunthe`: win = all tokens
aligned to matching slots via connector clicks); the L0 "click 3x" is a
surface case (one already-aligned connector). `data/traces/vc33.npz` covers
only L0, so L1's connector-chain sequence has no oracle — the documented
reopen, not chased blind.

## L1 investigation (R63, 2026-07-16) — DETECTION+MECHANIC gap, not a policy tweak; closed for the sprint

Bounded investigation of the failure (floor 1/7 @ 0.0357, env vc33-5430563c,
@1000, deterministic ×2). Faithful passive reads (drove the real adapter to L1,
read `env._game`), coordinate-validated. **Verdict: the failure is DETECTION +
WRONG-MECHANIC, not a "how many clicks to commit" POLICY issue — and clicking
the actual controls still cannot reach a win in the observable state space, so
L1 is a genuine sequence/alignment puzzle far outside the click-counter model.**

**True L1 mechanic (from the served source, `vc33-5430563c`).** `step()` responds
to exactly two sprite classes: `0022jvmlspyigc` (clicked → `iootdyzbwv` → a mapped
token move / direction set) and `0004sttgkofqwb` (a board connector → an animated
token move). L1 starts with **4 `0022jvmlspyigc` buttons on the TOP ROW (grid row
1, cols 9/13/19/23; display clicks (2,18)/(2,26)/(2,38)/(2,46), all get_sprite_at-
verified) and ZERO `0004sttgkofqwb`**. Win = `ielczunthe` (each target token
`0016uciqlhjlom` colour+row aligned with a slot `0025yfyiswdvoh` via a connector
`0043nzrtobajqi`). Click budget = `heczcoeosi.current_steps` = **50**; it
GAME_OVERs when exhausted.

**DETECTION gap (the primary failure).** The adapter's `_region_candidates`
(find_regions on the canonical frame, colour-region centroids) returns board
regions at rows 0–46, cols 28–62 — it **never surfaces the 4 top-row buttons
(row 1, cols 9–23)**, the ONLY elements `step()` reacts to at L1 start. So on L1
the adapter spends its whole 50-click budget clicking non-interactive board cells
(pure no-ops), GAME_OVERs, and makes zero progress — regardless of the
commit/sustain POLICY. The click-counter model (winner region + decoy penalty)
is also simply the wrong mechanic for an alignment puzzle.

**Even correct button-clicking cannot win (measured).** A full-state BFS over the
4 coord-verified buttons — state = every non-HUD sprite's (tags, x, y, rotation,
colour-sig) PLUS the `dwwmpxqsza` move-direction register, `level_reset`-faithful
(verified state-restoring), HUD excluded so the click counter doesn't pollute
dedup — reaches only **48 distinct states, none satisfying `ielczunthe`** (also:
random 40×60 clicking = 0 wins; single-button ×20 = 0 wins). So the 4 top-row
buttons alone are a dead end: L1's solution must also involve the `0004sttgkofqwb`
board connectors, which are ABSENT at L1 start — they must be produced by an
interaction this pass did not decode (likely a button sets direction, then a
board-connector click executes the aligned move). Decoding that + a search over
the combined action set, with NO L1 gold oracle, is a from-scratch L1 solver —
beyond a bounded pass and not a small gated fix.

**Probe-validity note (why the first BFS was wrong).** The first solvability BFS
used engine SPRITE coords as click coords and found "1 reachable state / no win";
that was a coordinate-scaffold artifact — engine grid coords ≠ display click
coords. Brute-forcing the camera inverse (`display_to_grid`) so `get_sprite_at`
verifiably hits each button changed the reachable set to 48. Lesson reused:
[[../lessons/probe_validity_20260715]] — a probe whose result contradicts
known-good behaviour (the adapter clears L0 by clicking) is measuring its own
scaffold; validate the click actually lands before trusting a null result.

**Closed for the sprint.** L1 needs a bespoke solver (detect the top-row button
control set + board connectors, model the alignment win + direction register,
search the combined-action sequence) with no oracle — out of scope for a bounded
investigation, and the score lever is modest (L1 weight 2 of the 1..7=28 sum; a
clear near the 18-action human would add ~2·(18/agent)²/28). Floor 1/7 @ 0.0357
held (no code change, deterministic ×2). Scratch probes this session:
`/private/tmp/.../scratchpad/vc33_l1_{probe,solvable,coords,bfs2}.py`.
