     exactly 1 content region; every real frame checked has >= 2).

## Observations

- Items at the bottom of the frame must be swapped into target slots
- ACTION5 scans/verifies; ACTION6 clicks to select or swap; ACTION7 undoes
- Frames can contain portals that redirect to other frames

## Mechanics Hypothesis (confirmed 2026-07-13, was "unknown" detail before)

**Not** a simple reference-row / pool-row colour match. It's a **portal-graph
traversal puzzle**: the board has TWO+ FRAMES (rendered as bordered boxes,
each border colour is the frame's own identity), each exposing N slots
(N = the frame's own slot count). A slot holds either a plain colour item or
a **portal** that redirects traversal to a different frame (matched by that
frame's border colour). The level clears when a **DFS traversal starting at
frame[0]**, following portal links slot-by-slot, visits plain-item slots
whose colours match the target sequence in traversal order (not screen
left-to-right order) — a "revisit" (portal loop back to an already-visited
slot) must match the colour seen on FIRST visit rather than consuming a
fresh target. Difficulty scales via more frames / more portals / longer
traversal chains, not just more colours.

### L4 SOLVED (script25, 2026-07-15) — the portal is a POOL PIECE to place

The prior bank (below, kept for provenance) chased a phantom: it assumed L4's
portal was an ICON already inside a frame (like L3's) that mysteriously "needed
a click". Reading the GAME SOURCE offline (`environment_files/sb26/*/sb26.py`,
never imported) settled it decisively — the true L4 mechanic:

- **The portal is a POOL PIECE** (source sprite `vgszefyyyp`, a draggable
  `lngftsryyw`+`sys_click` item), NOT a fixed in-frame feature. The player must
  PLACE it into a hub slot like a colour item. That is the "extra click" the
  prior bank observed but mis-modelled.
- **ACTION5 runs a DFS from frame 0** (`dbfxrigdqx`/`rfdjlhefnd`): each slot is
  an ITEM (checked against the target sequence in traversal order) or a PORTAL
  (`vgszefyyyp`, redirects to the frame whose border colour = the portal's
  interior colour). The portal slot does NOT consume a target — it is a pure
  zero-action jump; the level clears when the DFS reads the target sequence.
- **Measured L4 board** (engine-verified via a gold replay + `rfdjlhefnd`
  introspection): hub `nyqgqtujsa5` (root, 5 slots, border 8), leaf
  `pcrvmjfjzg3` (3 slots, border 14). Leaf slot 0 is PRE-PLACED colour 14; all
  other target slots are empty spots. Pool = 6 solid colour swatches
  {11,8,12,15,9,6} + 1 hollow portal (interior colour 14 = leaf border).
  Targets `[11,8,14,9,6,12,15]`. Placing the portal at hub slot 2 makes the DFS
  read `hub[0]=11, hub[1]=8, [jump] leaf[0]=14, leaf[1]=9, leaf[2]=6,
  hub[3]=12, hub[4]=15` = the target sequence exactly. The pre-placed leaf item
  (14) PINS the only consistent portal position.

**Frame-only discriminators (all verified, no internal reads at runtime):**
- The pool portal is a **hollow ring** — `closed_frames` detects it in the
  BOTTOM pool band (below every interactive frame); its border colour names the
  destination frame. Solid colour swatches are not rings. This is the signal the
  prior bank said didn't exist: it exists, but only visible once you know to look
  for a *placeable* portal, not an in-frame icon.
- The target sequence is the row of hollow-ring swatches ABOVE the frames; read
  each ring's border colour via `closed_frames` (a plain colour read also grabs
  the ring's interior hole colour — the R48-era bug re-encountered and avoided).
- The pool renders piece colours ONE FRAME AFTER the level loads (a level-entry
  transient), so planning retries (bounded) until the settled board reads.

**Solver** (`_plan_sb26_pool_portal`, gated — returns None unless a hollow pool
portal is present, so L1-L3 are byte-identical): try each empty root slot k for
the portal; the induced DFS order `root[0..k-1] + dest[all] + root[k+1..]` must
read the target sequence, with every pre-filled slot's fixed colour agreeing;
place the portal then each remaining colour in DFS order, then ACTION5.
**Measured: L4 clears in 21 actions (human 19 → RHAE 0.819), game_score
0.1446 → 0.2355, L1-L3 unchanged, deterministic ×2.**

### L5-L8 SOLVED (script25, 2026-07-15) — N-portal DFS placement solver

Extending L4's pool-portal spine to N portals with a FAITHFUL DFS SIMULATOR
(`_simulate_portal_dfs`) cleared the whole game: **8/8, game_score 0.846, 170
actions**. The simulator replays the game's exact traversal (source
`dbfxrigdqx`/`rfdjlhefnd`) as an iterative walk BOUNDED by the target count:
slots visited left-to-right, a PORTAL descends into its destination frame (zero-
target jump) and RETURNS to the next slot afterwards, an ITEM consumes the next
target; frames may be RE-ENTERED (the game wins the instant the last target is
filled, so a cycle just runs until targets exhaust), with a step cap that
rejects a non-productive loop (the game FAILs those). `_plan_sb26_multi_portal`
exact-searches portal placements over empty slots (never a portal's own dest
frame), simulates each, assigns the target sequence to the item-visit order, and
accepts the first placement where each slot's colour is consistent across its
(possibly repeated) visits, pre-filled slots agree, and the pool supplies the
empties. Gated on ≥2 pool portals (L4's single-portal solver is separate), so
L1-L4 stay byte-identical.

The four deeper shapes, each a different way portals lengthen the target
sequence beyond the physical slot count — all handled by the SAME simulator:
- **L5** (0.819→**1.0**, 23a vs 31 human): hub with TWO portals both to one
  leaf → the leaf is traversed twice; targets `[6,14,8,8,14,8,8,11,15]` (the
  `[14,8,8]` leaf read appears at two windows). A pre-placed pin is NOT needed —
  the repeated-colour target sequence itself selects the one valid placement.
- **L6** (**0.846**, 25a vs 23): an all-portal ROOT (3 portal slots) → three
  leaves visited once each; `[9,11,11, 12,15,15, 14,6,6]`.
- **L7** (**1.0**, 23a vs 58 — super-human): same family, deeper.
- **L8** (**0.612**, 23a vs 18): a MUTUAL-portal CYCLE — frame8 ends in a
  portal→frame9, frame9 ends in a portal→frame8 — so the walk cycles
  A→B→A→B, reading the 6-item loop twice; the 12-target band WRAPS onto TWO
  rows, which must be read top-row-then-left-to-right (`_read_target_sequence`),
  not globally by column (that interleaves the rows into `[8,8,11,11,…]`).

The whole game is now frame-only with zero runtime internal reads — the third
fully-conquered game after [[FT09]] and [[CD82]].

### Prior L4 bank (superseded 2026-07-15 by the source read — kept for provenance)

The board is a 2-frame hub-and-leaf, structurally identical in SHAPE to L3's
colour-matched-icon mechanic (no physical connector pipe — `connectors()`
returns zero links). Two hypotheses were tested and falsified from FRAME
observation alone: (1) *"always click every colour-matched icon"* broke L2's
efficiency and mis-ordered L4; (2) *"an icon whose colour has a matching pool
swatch is a required click"* was falsified since colour14 (L4) and colour9 (L3)
both have pool swatches. The bank concluded "no structural signal discriminates
needs-a-click from free". The error: it modelled the portal as an in-frame icon.
The portal is a POOL piece (a hollow ring in the pool band) — reading the game
source, not more frame-diffing, is what exposed this. LESSON: when repeated
frame-only falsification finds "no signal", the model itself (not the signal)
may be wrong — read the source to re-found the model.

### Frame-only attempt (R48 `sort_match.py`) — why it clears L1 but not L2

`sort_match.py`'s `detect_match_layout` models the board as a top
"reference" row (colour-bordered frames, assumed to show the target order
left-to-right) + a bottom "pool" row (matching swatches), and
`plan_match_placement` clicks each pool swatch then clicks the mid-band cell
at the reference frame's own column (`placement_y` = arithmetic midpoint
between the two rows' y-values). This has **never actually delivered a
swatch anywhere** — live-traced 2026-07-13: 9 candidate y-values at a
reference column produced zero effect. L1 clears anyway because its board
happens to have only ONE portal-frame with 4 slots, and the naive
`placement_y`/`ref_x` guess coincidentally lands close enough to that single
frame's slot positions (verified: L1's true slots form a 2x2 grid the
current detector still doesn't correctly separate from box-corner
decoration — a lingering bug even in the "it happens to work" L1 path). On
L2 (two frames, 6 colours, 7 slots), the coincidence breaks: 0 of 9
candidate clicks land on anything, and even manually clicking on the REAL
slot markers (confirmed via `connected_components` — small uniform "22"-
coloured 2x2 clusters in the mid-band, distinct from both rows) and trying
both natural screen-order slot-fill sequences never clears the level,
because screen order is not traversal order and no portal was ever placed
by either attempt.

## Refactor Plan (Phase 8 Step 2, original 2026-04-20 note — CONFIRMED
CORRECT DIRECTION, not yet fully realized by `sort_match.py`)

This page's original refactor note said "detect portals via frame-level
jumps after clicks" — that turned out to be exactly right, but the R48
frame-only rewrite (`sort_match.py`) was built without consulting it and
modeled SB26 as ordinal colour-matching instead. A real frame-only fix
needs, at minimum: (1) frame + slot detection as an entity separate from
any "reference/pool" framing (the "22"-marker + border-colour approach
measured working 2026-07-13, reusable), (2) portal-vs-plain-item
disambiguation among pool pieces (no working frame-only signal found yet —
may need a probe-then-observe approach: place a candidate piece in a slot,
see whether OTHER slots' visited-order shifts), (3) the true
traversal-consumed target order (no frame-only equivalent found for
`game.wcfyiodrx` yet), (4) a permutation/traversal solver over portal
placements (mirror the brittle solver's `itertools.permutations` + DFS
simulate-then-commit shape, just fed from detected entities instead of
internals).

## Lessons Learned

- Current solver is brittle — v1 works, v2 untested (not served by API as of
  2026-04-20). See the linked lessons for the underlying pattern.
- **2026-07-13**: the frame-only `sort_match.py` rewrite modeled the WRONG
  mechanic (ordinal reference/pool matching instead of portal-graph DFS
  traversal) despite this page already flagging portals in April — a
  records-first gap: the newer module wasn't checked against this page
  before being built. Full live-traced diagnosis, both falsified mapping
  hypotheses, and the legacy-solver mining that revealed the true mechanic:
  [[../rounds/r53_unified-harness]] "sb26 build cycle" section.
- **2026-07-15 (R56 script25 track)**: two GENUINELY DIFFERENT shape
  defects look superficially similar ("a frame closed_frames rejects") but
  need opposite fixes -- extra same-colour cells (fused appendage) vs
  missing cells (foreign-colour occlusion). Conflating them would have
  meant only ever fixing one frame of L2's two-frame board. See
  [[../lessons/ft09_glyph_decode_20260715]] for the SAME "don't assume one
  fusion shape covers every case" lesson on a different game (FT09),
  independently reaching the analogous conclusion the same session.
- **2026-07-15**: raw pixel-distance proximity is not just imprecise, it
  can be actively WRONG in a way that looks confident -- L2's real portal
  source frame is genuinely farther (by pixel distance) from the connector
  path than the wrong frame is, because the wrong frame happens to have a
  real item slot column-aligned with the connector. A signal that
  identifies structure (something drawn INSIDE the correct frame) beat a
  signal that merely measures distance.
- **2026-07-15**: a filter tuned on ONE board's "real frames are all
  roughly the same size" pattern silently breaks on a DIFFERENT board
  whose real frames are legitimately different sizes (a hub with portal
  icons vs plain leaves) -- the fix (content-count >= 2) already existed
  elsewhere in the SAME file as a more semantically correct signal;
  size-based clustering was redundant with it and less robust.
- **2026-07-15**: an "obvious" generalization (always click every
  colour-matched icon) can be DISPROVEN, not just imperfect -- it degraded
  a working board's efficiency while still failing to fix the target
  board, because BOTH the trigger condition and the insertion semantics
  were wrong simultaneously. Reverted rather than banked as a partial
  win. See the L4 open question above for the full falsification.
- **2026-07-15 (L5-L8 solved)**: once the MECHANIC is a small state machine (a
  portal-graph DFS), the highest-leverage move is to SIMULATE it faithfully and
  search placements, not to special-case each level. One iterative simulator
  bounded by the target count — allowing frame re-entry and capping runaway
  loops — covered every deeper shape (double-to-one-leaf, all-portal root,
  mutual cycle) with no per-level code. Two non-obvious details each cost one
  measured failure: (a) a recursive path-guard WRONGLY rejects the L8 mutual
  cycle (the game terminates by target exhaustion, not by a visited-set) — the
  simulator must be a bounded walk, not a tree DFS; (b) a wrapped multi-row
  target band must be read row-major, not by global column (that interleaves the
  rows). Simulate-then-search generalizes; per-level heuristics do not.
- **2026-07-15 (L4 solved)**: repeated FRAME-ONLY falsification that concludes
  "no structural signal discriminates case A from case B" can mean the MODEL is
  wrong, not that the signal is absent. The prior L4 bank exhausted frame-diff
  hypotheses under a wrong model (portal = in-frame icon). Reading the GAME
  SOURCE offline (dev-time understanding only; the adapter stays frame-only)
  revealed the portal is a POOL PIECE to place — after which the discriminator (a
  hollow ring in the pool band) was obvious and the solve fell out. When
  falsify-before-build keeps returning "no signal", read the source to re-found
  the model before spending more frame-diff budget.
