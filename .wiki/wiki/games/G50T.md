# G50T

> A full *Adventures of Lolo* / Sokoban-with-logic puzzle: navigate a player to a hidden goal through a wall maze, using button→gate→toggle-block circuits, past DETERMINISTIC wall-following patrol enemies, within a scroll-timer budget — with an ACTION5 record-replay "ghost" mechanic. NOT a simple "reactive sokoban", and NOT "explore-interact".

## L1 multi-ghost DECODE (2026-07-17) — ACTION5 supports N-1 CONCURRENT ghosts; L1 needs 2 + a perception fix (NOT built this pass)

Bounded pass on L1. The load-bearing question — does ACTION5 support two
concurrent ghosts, or does a second recording replace the first? — is **DECODED
(source-verified) and answered: ghosts ACCUMULATE, up to `N-1` concurrent, where
`N` = the number of `gpkhwmwioo` waypoint sprites on the level.** L1 has **3
waypoints → 2 concurrent ghosts** (L0 had 2 → 1, which is why L0 needed exactly
one). So the L1 plan shape is **two-ghost seating**, not sequential single-ghost
legs.

**Source mechanism** (`qxlodtievc`, `environment_files/g50t/5849a774/g50t.py`):
`rloltuowth` is a **dict** `{ghost: recorded_path}` (not a single slot). Each
ACTION5 (`pmlawcgvcp`) rewinds the current player's path to start, then in
`step()` increments the waypoint counter `rlazdofsxb` and, **if
`rlazdofsxb < len(drofvwhbxb)`**, BANKS the current player as a new ghost keyed
into `rloltuowth` (accumulate — prior ghosts untouched) and CLONES a fresh
player at start. When `rlazdofsxb == N` the Nth press instead CLEARS every ghost
and resets. So presses 1..N-1 each add a ghost; press N wipes. All ghosts replay
in LOCKSTEP with the current recording-phase move index (`move()` steps every
ghost by `path[htixxywyfp]`), rewind together on ACTION5, and once a ghost's path
is exhausted it STAYS put (holds its plate). Same `moves > Lg_i` seating fencepost
as L0, per ghost.

**Plan the machinery already supports:** bank ghost-A (record a walk onto plate
A → ACTION5), bank ghost-B (record a walk onto plate B → ACTION5), then a final
`kernels.configuration_path` over `(cell, moves)` with TWO barriers, each
`barrier_i` passable iff `moves > Lg_i`. The (cell, moves) formulation
generalises directly (both ghosts seat permanently, so both barriers stay open
after their own Lg) — NO `ghost_phase` dimension needed, exactly as L0.

**Why NOT built this pass — the real L1 blocker is PERCEPTION, not the planner.**
Live at L1 (after clearing L0): the goal is the STATIC colour-9 blob at cell
(3,4) (source `gilbljmfbc` (24,18)→frame, matches), but the L0 single-moving-
blob player identity BREAKS — there are MULTIPLE moving colour-9 entities (the
player near the top-right ~cell (4,8), PLUS at least one non-player mover from
`nqtslsoqvv`/`rinmohgkoo`, source tags `rsrdfsruqh`/afbbgvkpip built in
`__init__`), and probes show blobs displacing in ways inconsistent with a single
one-cell player. So L1 needs (a) robust multi-entity player-vs-other-vs-goal
identity (per-object motion-correlation across settled frames, rejecting the
non-player mover) and (b) the two-plate wiring decode (which plate opens which
gate + the crossing order) before the two-ghost planner can run. Both are a
dedicated round, not a bounded extension. **L0 floor is byte-identical (1/7 @
0.0357 ×2 before/after this pass — no code changed).** Recommended next round:
perception-first (nail L1 player identity + goal + the two barriers), then wire
the two-ghost seating with the existing (cell, moves) gate machinery. See
[[m0r0]] (multi-entity joint identity + momentary gates) for the perception
pattern to borrow.

## L0 CLEARED (2026-07-16) — FIRST g50t clear, via the ACTION5 GHOST the reopen brief said to avoid

`adapters25/g50t.py` now clears **L0 = 1/7 @ game_score 0.0357** (deterministic
×2 @1000; ~29 actions to WIN vs a human baseline of 78, so L0 scores the full
per-level 1.0 and the game caps at 1/28 = 0.0357 by completion). This is the
**first-ever g50t clear** and it **REFUTES the reopen brief's model** (commit
81bf415: "plate LATCHES the gate open, BFS to goal, AVOID ACTION5"):

- **The plate is MOMENTARY, not latching** (live-verified: the barrier cell's
  colour flips 8→5 while the player stands on the plate, 5→8 the instant it
  steps off; source `qxlodtievc.ayhgaxoxce` presses on-settle and
  `move`→`ayhgaxoxce(player, False)` releases on move-out). With a SINGLE
  player, a momentary single-cell barrier is impassable by walking alone.
- **So ACTION5 (record-replay ghost) is REQUIRED, not avoidable.** `pmlawcgvcp`
  rewinds the whole path to start and banks it as a GHOST that replays it in
  lockstep with the player's later moves, then STAYS at its final recorded cell.
  Recipe: record a walk ONTO the plate, press ACTION5 (ghost seats on the plate,
  holds the barrier open), then walk the reset player through the now-open
  barrier to the goal. Proven live end-to-end (scratchpad probe, 20 actions).
- **Movement is ONE cell / `env.step`** (not a slide, not multi-step animated —
  the prior adapter's `_ANIMATING_DIFF` "hold through animation" model was
  wrong). ACTION1=up, 2=down, 3=left, 4=right. A blocked move only ticks the
  ~1px HUD scroll timer.
- **Two load-bearing timing facts** (both cost a debug cycle): (a) Lg = ALL
  genuine player displacements since level start INCLUDING the identify probe,
  so Lg must count that move or it undercounts by 1; (b) the ghost seats at the
  END of the player's Lg-th move and the engine validates the player's move
  BEFORE the ghost's replay in the same step, so a barrier cell is enterable
  only from the **(Lg+1)-th move** onward (`moves > Lg`, never `>=`).

**Adapter pipeline (all generic — no hardcoded cells):** identify the player by
motion (the moving colour-9 blob; the static colour-9 region is the goal) →
parse the colour-5 floor at the player-derived 6px cell phase → if the goal is
walled off, discover the plate (frontier colour-8 cells adjacent to the
reachable chamber, tried farthest-from-goal first = the plate on L0; the one you
can ENTER and whose entry EXPANDS the floor is the plate, the newly-opened cells
are the BARRIER) → press ACTION5 → plan the route with
`kernels.configuration_path` over `(cell, moves)` with barrier passable iff
`moves > Lg` → drive closed-loop (re-issue each hop until the observed player
cell reaches it; a blocked/absorbed step never advances the ghost, keeping
lockstep). See [[../lessons/faithful_offline_simulator_20260715]] (learn the
operator, then PLAN) and [[m0r0]] (the sibling momentary-gate joint planner).

**L1 note (probed, NOT built this round):** L1 keeps the same one-cell grid +
plate/gate/toggle mechanic but adds a **SECOND** plate→gate circuit (source L1:
2 plates `medyellngi`, 2 toggle-blocks `kjrcloicja`, gates `oanvksd3/4`); no
patroller enemy sprite (`vtwcsmdoqp`) is in the L1 list, so L1 is enemy-free
like L0 but likely needs TWO ghosts (or one ghost holding one plate while the
player operates the other) — a real multi-ghost round, banked for later. The
adapter degrades to a bounded explorer on L1+ (0/7 there, no regression).

## L0 re-verification (2026-07-16) — mechanic mis-read CORRECTED, L0 REOPENED

A live settled-probe pass against L0 (the FIRST playable level) REFUTES the "banked
DEEP — state not frame-readable / faithful frame-only sim infeasible" verdict below,
for L0 specifically. It is a ka59-style mechanic mis-read: **L0 is a clean,
deterministic, frame-readable grid maze**, and the blocker for a first clear is
PLANNING (operate the plate→gate circuit), NOT frame-readability. Source + live agree.

Measured facts (all live, `g50t-5849a774`, no adapter change; floor unchanged 0/7 @1000):

- **Movement is one-cell grid, 6 px/cell** — NOT sliding, NOT "reactive". A single
  action steps the player exactly one cell: measured DOWN = row 10→16→22→28→34 (one
  +6 step per action), then blocked by a wall. UP/LEFT are blocked from the start.
- **The player is frame-identifiable** — a distinct 5×5 **color-9** blob; the floor is
  **color-5** (880 cells); walls are the absence of floor. `find_regions` isolates the
  player cleanly (nearest-blob tracking through moves).
- **L0 has NO enemies** — source-confirmed (level-0 sprite list has zero enemy/track
  entities: the `utmhrglxzq` patroller group and `umziwqcvfy` wall-track group are both
  empty) and live-confirmed (nothing moves without a command except the scroll timer).
  So the "joint (player, enemy) reactive state" framing does NOT apply to L0.
- **The maze is frame-readable and the frame agrees with the live engine** — a BFS over
  the color-5 floor from the player reaches EXACTLY the same 11-cell chamber that a
  live DFS drive reaches: `{(10,16),(10,22),(10,28),(10,34),(16,16),(16,28),(22,16),
  (22,22),(22,28),(28,16),(34,16)}`. The frame model and the engine match.
- **The circuit is frame-VISIBLE** — the player is confined to that 11-cell chamber by a
  CLOSED gate (the goal, a color-9 blob bottom-right ~ (52,46), is NOT reachable on the
  initial frame). Operating the circuit produces a visible frame change (a large color-0
  region appears mid-exploration). So the gate/toggle STATE is observable, not hidden.

**Win/lose decoded from source** (`environment_files/g50t/5849a774/g50t.py`): WIN when the
player reaches `(goal.x+1, goal.y+1)` (goal = `gilbljmfbc`); passability = destination is
on the floor mask AND not on a VISIBLE toggle-block; DEATH = the player's `pddqxjztas`
flag (gate/block crush). Circuit wiring: plate `medyellngi` → gate `oanvksd0` →
toggle-block `kjrcloicja`. ACTION5 IS the record-replay ghost (confirmed live: it spawns
a second color-9 blob), so the "undo" note in Observations below is wrong — keep the
ghost reading.

**THE ONE BLOCKER for a first clear = GHOST-coordination planning (corrected below —
NOT a simple (player,gate) BFS).** Not detection (player, floor, goal, gate all
frame-readable), not frame-readability (refuted above), not a joint enemy state (no
enemies on L0). The player is walled into an 11-cell chamber; the goal is across a closed
gate that opens only while the plate is held down.

**Correction (same-round follow-up) — the plate is NOT directly reachable, so the
ACTION5 ghost is required.** Using the source→frame coordinate map (frame ≈ (y+3, x+3),
verified on player source (13,7)→frame (10,16) and goal source (42,48)→frame (51,45)):
plate `medyellngi` (source 37,7) → frame **(10,40)**, one cell RIGHT of the chamber edge
(10,34) and blocked; gate `oanvksd0` → frame (13,19) (inside); toggle `kjrcloicja` →
frame (40,16) (below chamber); goal → frame (51,45). Visiting ALL 11 reachable chamber
cells produced NO gate-opening frame event and the goal stayed unreachable — the player
alone cannot press the plate. Since ACTION5 is a record-replay ghost (confirmed live: it
spawns a 2nd color-9 blob), the intended solution is the classic *Lolo* pattern: **record
a path that parks a GHOST clone on the plate (holding the gate open), then walk the
rewound player through the opened gate to the goal.** So the plan state is NOT
`(player, gate_open?)` — it includes the ghost's banked replay + the momentary
plate→gate coupling.

**What is solid (refutes the DEEP bank) vs what's harder than first written:**
- SOLID: L0 is frame-readable + deterministic + one-cell grid + no enemies. The
  "state not frame-readable / faithful frame-only sim infeasible" verdict is wrong;
  the maze, player, goal, plate, gate, and gate-state changes are all frame-observable
  (frame BFS == engine reachability). So this is NOT the un-simulable game the bank claimed.
- HARDER: a clear needs the ACTION5 record-replay ghost to hold the (unreachable-by-the-
  player) plate. My initial "simple (player,gate) BFS" note was an overclaim, corrected here.

**Build path (a real adapter round, not a bounded ship — banked, not attempted):**
(1) parse the color-5 floor grid + player/goal/plate/gate via the (y+3,x+3) map;
(2) probe the plate→gate coupling and whether it is momentary (held) or latching, and
measure the ghost replay semantics (how ACTION5 banks + replays a recorded path);
(3) plan two coordinated paths — a ghost path that reaches+holds the plate, and a player
path through the opened gate to `goal+(1,1)` — searching over
`(player_cell, ghost_phase, gate_open)`; (4) gate on the L0 signature, deterministic ×2.
Tractable and frame-simulable, but a genuine ghost-coordination solver — not the trivial
maze BFS the first draft implied. (Higher levels add enemies + more circuits; re-verify
per level rather than inheriting the blanket "infeasible".)

## R56 iteration 2 — COMPLETE decode from source; banked DEEP (2026-07-15)

The prior bank called G50T a "reactive sokoban — model the joint (player,enemy)
state." A full source read (`environment_files/g50t/5849a774/g50t.py`, 7 levels,
controller `qxlodtievc` + ~13 entity classes) + a validate-first live probe show
it is substantially deeper, and the load-bearing state is **not frame-readable**:

- **Enemies are DETERMINISTIC wall/track-following PATROLLERS, not chasers**
  (`utmhrglxzq.oymsmftmdy`: first of [keep, turn, turn, reverse] that stays on
  the enemy's own track; never reads the player). Death = an enemy ending a
  move overlapping the player. Enemy paths depend on track geometry + heading +
  move count — but are also blocked by gates, so they couple to the circuit.
- **Button → gate → toggle-block CIRCUITS** (`lqtxaumfed` plates →
  `alyzsfkumg` gates → `yyzqramdhd` toggle-blocks). Even level 1 has a plate +
  a toggle-block: it is a circuit puzzle, not free navigation.
- **ACTION5 is a RECORD-REPLAY GHOST mechanic, not a single-step undo**
  (`pmlawcgvcp`→`tqzseunaxh`): it rewinds the whole path to start, banks it as
  a replaying ghost clone, and advances a waypoint phase. The prior wiki/adapter
  calling ACTION5 a cheap "undo back-edge" was wrong.
- **Collision is per-pixel SPRITE-MASK** (`esidlbhbhw` reads `sprite.pixels`
  with rotation). Walls, enemy tracks, gates and the plate→gate wiring are
  bitmaps + object references — a flat colour frame cannot recover them (a
  wall, a walkable track and a closed gate can share a colour).

**Validate-first probe (40 exploratory moves, level 1):** the player IS
identifiable by action-correlation (a small region shifts one cell with
left/right — reopen #1 is solvable); no region moves without a command except
the scroll timer (confirming enemies are absent / static-hazard on L1); the
player dies on a static hazard while boxed in a circuit-gated corridor. So L1 is
a plate-gate-hazard puzzle — not a coverage or joint-enemy problem.

**Why banked DEEP:** a faithful frame-only simulate-and-search is infeasible
because passability = circuit state + sprite masks, none frame-readable; solving
needs the sprite bitmaps + circuit topology (source-only, which the runtime
adapter must not read). Measured 0/7 @1000, game_score 0.0, deterministic.

## Observations

Measured from the live frame + the game source (dev-time read only; the
adapter acts frame-only):

- `available_actions` = `[1,2,3,4,5]`, **no ACTION6/click**. ACTION1-4 move a
  single player piece one logical cell; the render pitch is **6 px/cell**
  (`jarvstobjt=6`). **ACTION5 is UNDO** — it reverts the last move (the
  controller pops its move history), not an interact.
- A move is **animated over ~4-5 engine steps**; inputs are ignored
  mid-animation. Measured: mid-move frames change 48-105 cells, a
  settled/blocked frame changes only by a ~1-2px scroller tick.
- A **left-scrolling timer sprite** advances one pixel every ~2 actions; the
  level is LOST if it exits the left edge (a global move budget). It moves
  independent of the command — a decoy for movement-based player ID.
- Enemies/hazards **react to the player's moves** (they step when the player
  steps); touching one loses the level.

## Mechanics Hypothesis

Navigate the player through a wall maze (walls are a solid colour) to a hidden
GOAL cell (source: win when the player reaches the goal sprite offset by
(+1,+1)); the goal has no frame-distinguishable label. Because enemies react to
each move, the same player cell is safe or fatal depending on enemy phase — the
state is the joint (player, enemies), not the player cell alone. See
[[../game_types/sokoban]] and [[../concepts/frame_hashing]].

## Solution Pattern

The R56 adapter is a best-effort hazard-learning explorer composed from
`kernels.find_regions` + `kernels.transition_shortest_path` /
`kernels.reachable_frontier`: identify the player by movement, record settled
`(cell, action) -> next_cell` transitions, mark a transition FATAL when it
precedes a death (memory compounds across lives), and drive toward the nearest
unexplored safe edge. It scores 0/7 (see below).

## Notes / Refactor Plan (banked wall)

Two measured obstacles, both real research increments (not tuning):

1. **Player identification is ambiguous from frames** — the player shares its
   colour with larger static structures, and the scroll-timer auto-moves every
   action, confounding movement-based identity. **Reopen** with per-object
   `kernels.track_objects` across settled frames, correlating each object's
   displacement with the issued action's axis.
2. **SUPERSEDED by the R56 iteration-2 deep bank above.** A joint (player,
   enemy) state is necessary but NOT sufficient: passability also depends on the
   button→gate→toggle circuit state, and the circuit wiring + walls + tracks +
   gates are per-pixel sprite masks / object references, not frame-readable. And
   ACTION5 is a record-replay ghost mechanic, not a cheap undo edge. So the game
   cannot be faithfully simulated frame-only — banked DEEP, not a bounded fix.

No hardcoded coordinates/sequences were added; the adapter runs to budget as a
clean 0/7 best-effort. The complete mechanic writeup above is the banked
deliverable (the prior wiki had "unknown", then "reactive sokoban").

## Lessons Learned

- A "hybrid explore-interact 1/7" label hid a fully-structured reactive Sokoban
  with UNDO, animation, a hidden goal, and a scroll timer. Re-derive mechanics
  from the frame + source, don't inherit a vague tag. See
  [[../lessons/frame_diff_as_probe]].
- Movement-based player identification fails when a decoy sprite (the timer)
  auto-moves every step; require the player to respond to *varied* command
  directions, and prefer per-object tracking over largest/smallest-per-colour.
