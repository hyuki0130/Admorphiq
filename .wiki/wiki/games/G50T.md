# G50T

> A full *Adventures of Lolo* / Sokoban-with-logic puzzle: navigate a player to a hidden goal through a wall maze, using button→gate→toggle-block circuits, past DETERMINISTIC wall-following patrol enemies, within a scroll-timer budget — with an ACTION5 record-replay "ghost" mechanic. NOT a simple "reactive sokoban", and NOT "explore-interact".

## R56 iteration 2 — COMPLETE decode from source; banked DEEP (2026-07-15)

The prior bank called G50T a "reactive sokoban — model the joint (player,enemy)
state." A full source read (`environment_files/g50t/5849a774/g50t.py`, 7 levels,
controller `qxlodtievc` + ~13 entity classes) + a validate-first live probe show
it is substantially deeper, and the load-bearing state is **not frame-readable**:

- **Enemies are DETERMINISTIC wall/track-following PATROLLERS, not chasers**
  (`utmhrglxzq.oymsmftmdy`: first of [keep, turn, turn, reverse] that stays on
  the enemy's own track; never reads the player). Death = an enemy ending a
  move overlapping the player. Enemy paths depend on track geometry + heading +
  move count — but are also blocked by gates, so they couple to the circuit.
- **Button → gate → toggle-block CIRCUITS** (`lqtxaumfed` plates →
  `alyzsfkumg` gates → `yyzqramdhd` toggle-blocks). Even level 1 has a plate +
  a toggle-block: it is a circuit puzzle, not free navigation.
- **ACTION5 is a RECORD-REPLAY GHOST mechanic, not a single-step undo**
  (`pmlawcgvcp`→`tqzseunaxh`): it rewinds the whole path to start, banks it as
  a replaying ghost clone, and advances a waypoint phase. The prior wiki/adapter
  calling ACTION5 a cheap "undo back-edge" was wrong.
- **Collision is per-pixel SPRITE-MASK** (`esidlbhbhw` reads `sprite.pixels`
  with rotation). Walls, enemy tracks, gates and the plate→gate wiring are
  bitmaps + object references — a flat colour frame cannot recover them (a
  wall, a walkable track and a closed gate can share a colour).

**Validate-first probe (40 exploratory moves, level 1):** the player IS
identifiable by action-correlation (a small region shifts one cell with
left/right — reopen #1 is solvable); no region moves without a command except
the scroll timer (confirming enemies are absent / static-hazard on L1); the
player dies on a static hazard while boxed in a circuit-gated corridor. So L1 is
a plate-gate-hazard puzzle — not a coverage or joint-enemy problem.

**Why banked DEEP:** a faithful frame-only simulate-and-search is infeasible
because passability = circuit state + sprite masks, none frame-readable; solving
needs the sprite bitmaps + circuit topology (source-only, which the runtime
adapter must not read). Measured 0/7 @1000, game_score 0.0, deterministic.

## Observations

Measured from the live frame + the game source (dev-time read only; the
adapter acts frame-only):

- `available_actions` = `[1,2,3,4,5]`, **no ACTION6/click**. ACTION1-4 move a
  single player piece one logical cell; the render pitch is **6 px/cell**
  (`jarvstobjt=6`). **ACTION5 is UNDO** — it reverts the last move (the
  controller pops its move history), not an interact.
- A move is **animated over ~4-5 engine steps**; inputs are ignored
  mid-animation. Measured: mid-move frames change 48-105 cells, a
  settled/blocked frame changes only by a ~1-2px scroller tick.
- A **left-scrolling timer sprite** advances one pixel every ~2 actions; the
  level is LOST if it exits the left edge (a global move budget). It moves
  independent of the command — a decoy for movement-based player ID.
- Enemies/hazards **react to the player's moves** (they step when the player
  steps); touching one loses the level.

## Mechanics Hypothesis

Navigate the player through a wall maze (walls are a solid colour) to a hidden
GOAL cell (source: win when the player reaches the goal sprite offset by
(+1,+1)); the goal has no frame-distinguishable label. Because enemies react to
each move, the same player cell is safe or fatal depending on enemy phase — the
state is the joint (player, enemies), not the player cell alone. See
[[../game_types/sokoban]] and [[../concepts/frame_hashing]].

## Solution Pattern

The R56 adapter is a best-effort hazard-learning explorer composed from
`kernels.find_regions` + `kernels.transition_shortest_path` /
`kernels.reachable_frontier`: identify the player by movement, record settled
`(cell, action) -> next_cell` transitions, mark a transition FATAL when it
precedes a death (memory compounds across lives), and drive toward the nearest
unexplored safe edge. It scores 0/7 (see below).

## Notes / Refactor Plan (banked wall)

Two measured obstacles, both real research increments (not tuning):

1. **Player identification is ambiguous from frames** — the player shares its
   colour with larger static structures, and the scroll-timer auto-moves every
   action, confounding movement-based identity. **Reopen** with per-object
   `kernels.track_objects` across settled frames, correlating each object's
   displacement with the issued action's axis.
2. **SUPERSEDED by the R56 iteration-2 deep bank above.** A joint (player,
   enemy) state is necessary but NOT sufficient: passability also depends on the
   button→gate→toggle circuit state, and the circuit wiring + walls + tracks +
   gates are per-pixel sprite masks / object references, not frame-readable. And
   ACTION5 is a record-replay ghost mechanic, not a cheap undo edge. So the game
   cannot be faithfully simulated frame-only — banked DEEP, not a bounded fix.

No hardcoded coordinates/sequences were added; the adapter runs to budget as a
clean 0/7 best-effort. The complete mechanic writeup above is the banked
deliverable (the prior wiki had "unknown", then "reactive sokoban").

## Lessons Learned

- A "hybrid explore-interact 1/7" label hid a fully-structured reactive Sokoban
  with UNDO, animation, a hidden goal, and a scroll timer. Re-derive mechanics
  from the frame + source, don't inherit a vague tag. See
  [[../lessons/frame_diff_as_probe]].
- Movement-based player identification fails when a decoy sprite (the timer)
  auto-moves every step; require the player to respond to *varied* command
  directions, and prefer per-object tracking over largest/smallest-per-colour.
