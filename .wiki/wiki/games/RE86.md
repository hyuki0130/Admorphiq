# RE86

> A delivery + colour-assignment puzzle: cover matching-colour target boxes with colour-coded movable crosses (routing through recolour tiles). R56 = the first generic clear (1/8, was 0/8).

## Current Status

- **v1** (`re86-4e57566e`) / **v2** (`re86-8af5384d`): the brittle
  `re86_analytical` cleared 6/8 by reading sprite tags `vzuwsebntu` (targets),
  `vfaeucgcyr` (movables), `ozhohpbjxz` (changers); every generic attempt is
  0/8. R56 **decoded the mechanic** and shipped a kernels-only covering-offset
  adapter that cleared **1/8** (L1). **R59 clears 2/8** (game_score 0.033,
  deterministic ×3): L2 falls to the SAME covering spine once two frame-only
  perception bugs are fixed (see Refactor Plan). No new mechanic, no hardcoding.

## Observations

Measured from the live frame + game source (dev-time read only; the adapter
acts frame-only):

- `available_actions` = `[1,2,3,4,5]`, no ACTION6. ACTION1-4 move the SELECTED
  movable one 3px cell (`ilmaurgzng=3`, sign measured). **ACTION5 CYCLES the
  selection** — the active movable's centre carries the selection marker
  (colour 0). Level 1 has exactly **two movables** (measured colours 9 and 11).
- **Targets** = static colour-bordered boxes (a colour-4 border around a
  coloured centre) painted on a backdrop canvas.
- **Changers** = static coloured lines; a movable of a different colour that
  overlaps one is RECOLOURED to the changer's colour (animated, spreading
  across the movable over several steps).

## Mechanics Hypothesis

Bipartite colour-assignment scored by position (typology T3 variant). Each
target box requires a movable pixel of its OWN colour at its position; the win
check (`cdjxpfqest` in source) stamps every movable onto the backdrop canvas
and requires each target's coloured pixels to be covered by a matching-colour
movable pixel. A movable whose colour matches no target must be routed through a
changer to recolour it first. See [[../concepts/sprite_cluster]] and
[[../game_types/transform]].

## Solution Pattern

The R56 adapter (`adapters25/re86.py`) composes `kernels.find_regions` +
`kernels.covering_offsets`: locate the active movable via its selection marker
(colour 0), read its colour + shape, enumerate matching-colour target boxes, and
`covering_offsets(shape, targets)` for a translation covering them; step toward
the nearest reachable offset with measured move directions, switching axis on a
walled move, and NEVER disturbing a movable already placed at offset (0,0) —
cycling ACTION5 to work the other one until both are covered. Clears L1 (1/8).

**Level 1 SOLVED** (R56): marker-anchored + gap-bridged (`find_regions(gap=1)`)
FULL-movable extraction, locking targets per colour while the scene is clean,
`covering_offsets` to a single covering translation, axis-switch on walled

the other instead of un-covering the first.

**Level 2 SOLVED** (R59) — the SAME spine, once two frame-only perception bugs
are fixed. The earlier "banked wall" was NOT a mechanic gap. Ground truth was
read from the game source win-check (`jeiavrvavi`: every non-border target-map
cell must be covered by a matching-colour movable pixel) and confirmed
frame-for-frame against the gold replay (`data/traces/re86.npz`, replays 6/6
live). L2 has three movables — colour-12 X, colour-13 diamond OUTLINE, colour-9
plus — and ten gates (colour-9 ×4, colour-12 ×3, colour-13 ×3). Covering places
the centres at colour-9 → (48,27), colour-12 → (48,18), colour-13 → (12,21),
each DERIVED by `covering_offsets` from the frame-read gates (they match the
gold win frame exactly), never hardcoded.

Two prior beliefs FALSIFIED by live observation:

- **"colour-13 is invisible"** — it is fully visible during play (35–39 px every
  frame). The earlier read failed only on a STALE first frame; no footprint-probe
  or shape recovery is needed.
- **"compound colour-11 gate / off-grid colour-12 target / recolour"** — none
  exist. The true gate colours are 9/12/13; L2 has no changer and no wall, so
  there is no recolour. The prior "12 colour-9 + 12 colour-11 gates" reading came
  from the stale first frame, not the real scene.

The two fixes (both generic, no game constants):

1. **Settle before locking targets.** A level LOAD renders a transient
   camera-transition frame — shifted, showing two colour-9/-11 crosses and 24
   phantom gates — before the engine snaps to steady world coordinates after ONE
   env-step. Locking targets on that first frame captured the phantom gate set.
   `_decide` now defers the lock one step (a selection cycle settles the render
   without moving a piece).
2. **Select by centroid, not by size.** The marker sits at the selected
   movable's centre, so `_active_movable` returns the centroid-nearest region.
   The old "largest region touching a marker neighbour" rule returned the big
   colour-12 X whenever its sparse body overlapped the colour-13 diamond's
   marker, so the planner drove the X while the engine moved the diamond — an
   endless oscillation.

**Residual (efficiency, not correctness)**: the hollow colour-13 diamond's
gap-bridged extraction jitters ±1–2 px under occlusion, so `covering_offsets` is
non-stationary and the greedy wanders (~140 actions vs the gold's 36). The clear
is reliable and deterministic; a stable hollow-outline extractor is the open
efficiency lever.

**Level 3 SOLVED (R60) — separation-by-motion + per-piece gate-claiming.**
3/8 @ game_score **0.1162** (deterministic ×3), up from 2/8 @ 0.0328. Ground
truth (settled playing frame): ONE merged colour-8 region of 132 px (three
overlapping movables — an X, a diamond outline, a 1×43 LINE bar) and **8
colour-8 gates** at (6,6),(6,45),(15,51),(21,21),(27,9),(30,48),(33,33),(39,21).
The R59 bank was right that this is a separation problem; the R60 pass built it:

- **Separation is by MOTION, not by colour.** Only the SELECTED movable moves
  per action, so a probe move perpendicular to the merge seam isolates it. New
  generic kernel `admorphiq.kernels.separate_by_motion(before, after,
  background)` returns the moved object's after-cells from the motion delta
  (leading/trailing edges) + connectivity — even while the object is merged
  same-colour with the static ones. Measured live: an UP move cleanly isolates a
  48 px piece from the 132 px blob (a move PARALLEL to the line over-includes,
  so the controller separates with a VERTICAL move only).
- **Gate-claiming, piece by piece.** All 8 gates + 3 pieces share colour 8, so
  the win is a geometric set-cover no single piece can satisfy. New kernel
  `admorphiq.kernels.max_coverage_offset(shape, points)` returns the ONE
  translation covering the most points (unlike `covering_offsets`, which returns
  a multi-offset SET). The controller: separate the active piece (anchor its
  shape to the selection marker), drive it to the max-coverage offset over the
  still-UNCLAIMED gates, freeze those gates, record the placed footprint, cycle
  ACTION5 to the next piece — never re-driving a placed one. The 1×43 line is
  handled by the same shape-agnostic covering (no special line geometry needed).
- **Gated on level index (>= 2)** so L1/L2 stay byte-identical (floor 2/8 @
  0.0328 held; the full clear is 3/8 because all three levels clear). Adapter
  holds only the composition; the separation/coverage primitives live in
  `kernels/`. See `src/admorphiq/adapters25/re86.py:_decide_multi`.

**Level 4 SOLVED (R61) — multi-piece recolour-routing FSM. 4/8 @ game_score
0.2273 (deterministic ×2 @1000, `re86-8af5384d`), up from 3/8 @ 0.1162.** The
CHANGER mechanic decoded in R60 (below) is real; R61 built the two-piece
orchestration on top of the covering spine. `Adapter._decide_l4` (gated on level
index >= 3 so L1/L2/L3 stay byte-identical) frame-parses the scene, assigns each
movable a gate colour, recolours BOTH first, then covers both:

- **Scene parse (frame-only)**: gates via `_target_boxes` (colour-4 boxes, by
  colour); changer stations via `_station_boxes` (colour-2 boxes → `{swatch
  colour: centre}` + box bboxes, composed from `find_regions`); movables via
  `_l4_movables` (colour regions that are NOT gates/stations/HUD, gate cells
  SUBTRACTED so a recoloured movable is not merged with its same-colour gates).
- **Two-piece tracking (the R60 wall)**: identity by OPTIMAL (min-total-distance)
  centroid assignment, NOT colour — a recolour changes colour but not position;
  colour is updated only to a KNOWN colour (gate colour or original), so identity
  survives the flood's transient mixed colours. Greedy per-piece matching swapped
  identities and was the bug.
- **Selection under overlap**: the selected movable's marker (colour-0 centre) is
  OCCLUDED when the two pieces overlap, so selection is tracked by count (ACTION5
  cycles it) with a marker re-sync when visible. Overlap is AVOIDED by phase
  order: recolour BOTH pieces first — they end at opposite-edge stations,
  separated — so the cover phase never overlaps and the marker stays visible.
- **Recolour routing**: `_l4_recolour_want` aligns the COLUMN first (horizontal,
  in the station-free interior) then moves VERTICALLY along the target's column
  into it — every station sits on an edge row, so this provably avoids
  re-recolouring against a wrong-colour station en route.
- **Assignment**: `_l4_assign_pieces` picks the permutation where BOTH movables
  FULLY cover their gate colour (`max_coverage_offset` full-cover test) — colour-10
  covers gates-14 3/3 but gates-12 only 2/3, so the assignment is forced.
- **Cover (the R59 spine)**: MARKER-anchored (the marker is the sprite's exact
  centre; a parse centroid quantises 1 px and stalls on the 3-px move grid), drive
  the locked shape to cover ALL its gates; a piece covering all its gates holds
  while the other is worked — the engine win-check needs both covering
  SIMULTANEOUSLY (source `jeiavrvavi`: each gate's coloured centre pixel must be
  covered by a matching-colour movable pixel on the shared stamped canvas). See
  `src/admorphiq/adapters25/re86.py:_decide_l4`.

Two porting bugs cost the most: (1) the L4 dir-measuring PROBE drove the wide
colour-10 movable up into station-12, recolouring it to a colour it can only
cover 2/3 of — fixed by reusing the level-invariant move map measured on L1-L3
(`_dir_global`, never reset) instead of probing at L4; (2) a persistent
`claimed` set masked a piece displaced by a mis-attributed move (claimed=6 but no
win) — fixed by re-evaluating coverage from live state each visit.

## Lessons Learned

- The 6/8-vs-0/8 gap was pure sprite-tag dependence; decoding the tags
  (`vzuwsebntu`=targets, `vfaeucgcyr`=movables, `ozhohpbjxz`=changers) into
  frame roles (bordered boxes / marker-carrying movers / recolour lines) is the
  prerequisite for any generic solve. See [[../lessons/hardcoded_is_anti]],
  [[../lessons/v2_hash_obfuscation]], [[../lessons/brittle_tells]].
- A same-colour changer line fragments the movable under plain connected-
  components; movable extraction must be anchored on the selection marker and
  gap-bridged, not colour-segmented naively.
