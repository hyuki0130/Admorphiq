# TR87

> A token-rewrite-grammar puzzle (NOT a geometric rotation puzzle, NOT a
> visual dial-match) — a static bar1 row is greedily parsed against six
> rule-table rewrite rules to derive the editable bar2 row's target, then
> a bracket-and-dial control scheme edits bar2 to match, column by column.
> Win rule CRACKED and SOLVED frame-only for the no-flags levels (R56,
> 2026-07-15) — 0/6 to 3/6, every cleared level at the human-efficiency cap.

## Observations (superseding the earlier "target in a corner" note — WRONG, see below)

- `avail = [1, 2, 3, 4]` — NO `ACTION6` at all. This alone rules out the
  click-only rotation-puzzle handling in `src/admorphiq/rotation.py` (that
  module is gated on click-only boards); TR87's control scheme is the
  opposite shape.
- The upper checkerboard grid (rows4-28, a 3-row x 4-col arrangement of ~12
  small multi-colour pattern blocks) is **100% decorative** — verified
  byte-identical across 8+ mixed actions. This is what earlier notes
  ("target visible in a corner") mistook for the puzzle; it is not part of
  the mechanic at all.
- The REAL interactive structure is a lower control panel with two stacked
  horizontal bars, each holding exactly 5 glyphs at IDENTICAL column ranges
  (cols 15-19, 22-26, 29-33, 36-40, 43-47):
  - **bar1** (top, colour10 background, rows41-45) — confirmed **100%
    static** across the entire trace (35+ dial presses). Reads as "the
    target" a dial must be spun to match.
  - **bar2** (bottom, colour7 background, rows52-56) — the EDITABLE row.
- A colour0 bracket (a 28-cell two-piece border, top half rows48-49 + bottom
  half rows59-60) surrounds exactly one bar2 column at a time.
  `ACTION3`/`ACTION4` move it between the 5 columns in opposite directions,
  wrapping cleanly (measured: `ACTION3` sequence 15-19 -> 43-47 -> 36-40 ->
  29-33 -> 22-26 -> 15-19 -> ...).
- `ACTION1`/`ACTION2` act on whichever bar2 column is currently bracketed.
  They are **NOT a geometric rotation** — before/after colour-5 cell counts
  differ (14 vs 15 on the measured first press), and `np.rot90`/transpose/
  flip all fail to match. They step a **7-STATE CYCLIC DIAL**, exact
  inverses of each other (verified: 7x either action returns byte-identical
  to the starting state; the other action then reverses one step at a
  time).
  **`ACTION2` is the FORWARD (+1) step, `ACTION1` is BACKWARD (-1)** —
  correcting this page's earlier (WRONG) claim that `ACTION1` was forward.
  Confirmed directly from source: `environment_files/tr87/cd924810/
  tr87.py:1006`'s `step()` `ACTION1`/`ACTION2` branch reads
  `pxdsteijos = -1 if self.action.id == GameAction.ACTION1 else 1` — i.e.
  `ACTION1` maps to `-1`. Found 2026-07-15 (R56 tr87 gate round, commit
  `a3a6644`) while building a disposable oracle-assisted level-advance
  script (`scripts/_tr87_capture_l1.py`, verification-only internal read,
  never touched by any shipped solver); using the OLD claimed direction
  made that script clear ZERO columns until corrected.
- A row-63 move/attempt counter is present (colours `{1, 4}`, growing) — TR87
  is in the move-limited "row-63 counter class" alongside s5i5/wa30/bp35/
  dc22/g50t (see `.wiki/wiki/rounds/r53_unified-harness.md`, "Wall anatomy
  #2-8"), so any live retry strategy must be plan-first, not exploratory.

## Mechanics Hypothesis

**Superseded (R56, 2026-07-15 — CONFIRMED, not just a corrected hypothesis;
see [[../rounds/r56_generic-kernels]] for the gold-trace-verified provenance).**
The R53-era "visual dial-match, win rule unknown" framing was wrong not
because the STRUCTURE was wrong (bar1 static, bar2 editable, both hold
per-column glyph tokens) but because it was missing an entire layer: THREE
upper row-bands (previously dismissed as "100% decorative checkerboard
grid" — they are not decorative, they are the RULE TABLE) each hold 2
rewrite rules (`LHS_tokens -> RHS_tokens`, 6 rules total). bar1 is not "the
target" a dial visually matches — it is the SOURCE token sequence a
grammar derivation is run over. The real win rule: greedily parse bar1
left-to-right against the six rules (first matching rule in list order
wins, no backtracking — `kernels.rewrite.greedy_parse`, chosen over the
BFS-search `derive_rewrites`/`find_derivation` specifically because the
real game's own `bsqsshqpox()` win-check, verification-only source read,
is this exact deterministic single-pass algorithm); the concatenated RHS
tokens ARE bar2's target, checked column by column. bar1's own glyphs are
themselves rule-table tokens rendered at a DIFFERENT on-screen ROTATION
(measured: translation-only matching finds only 1/5 of bar1's glyphs in
the rule table; C4 rotation-invariant matching finds 5/5 — rotation
invariance is not optional for this game, it is required).

Two further structural findings, measured while building the adapter, that
correct implicit assumptions this page never stated but earlier work
carried anyway:

- **bar1 and bar2 have INDEPENDENT column counts, not a paired 1:1
  relationship.** Measured across all 3 captured levels: L0 bar1=5
  columns/bar2=5, L1 bar1=4/bar2=7, L2 bar1=8/bar2=7. bar1's length is
  however many source tokens the level's rule table happens to derive
  from; bar2's length is a property of the level's own board layout,
  unrelated.
- **Not every one of bar2's 7 possible dial states is necessarily NAMED
  by a given level's 6 rules.** The dial is a measured CLOSED 7-state
  cycle (`docs/tr87_frame_only_grammar_design_20260715.md` §2 — every
  column shares the identical set of 7 canonical shapes), but a level's 6
  rules only reference SOME of those 7 states as LHS/RHS tokens. bar2's
  CURRENT (pre-edit, unnamed) dial value on a column can therefore be a
  state with no matching rule-table name at all — measured on L0 (1 of 5
  columns) — without that being an extraction defect: the adapter never
  needs to NAME the current state, only to dial-step until it becomes the
  (always-named) target.

Flagged levels L3-L5 (0-indexed; `alter_rules`/`tree_translation`/
`double_translation`, per the design doc's level/flag table) are NOT
measured and NOT handled by the current adapter — its own board-shape
structural gate (exactly 3 rule bands with the measured gap signature,
exactly 2 bar bands, a detectable bracket band) causes it to fall back to
a harmless bracket-nudge policy rather than mis-plan against unmeasured
semantics on those levels, "banking the simple slice" per the Codex
ruling's own words rather than guessing.

## Solution Pattern

Strategies that made progress on v1:

| Strategy | Levels | Actions | Type |
|---|---|---|---|
| `tr87_rotation` | 1 | 19981 | brittle |
| `adapters25/tr87.py` (script25, R56) | 3 | 17+35+26=78 (L0-L2) | frame-only, kernel-composed, zero internals |

`adapters25/tr87.py`'s dial executor: bracket-column detection (a short
row-band structurally adjacent to bar2, its own ink projected onto bar2's
measured column lattice) plus a per-column loop that moves the bracket to
each mismatched column and dial-steps until the read matches the derived
target. Neither the bracket-move direction (`ACTION3` vs `ACTION4`) nor
the dial-step direction is hardcoded from the source read above — bracket
direction is calibrated LIVE, once per level (one probe action, observe
which way the detected column index moved); dial-step direction needed NO
calibration at all, since the measured closed 7-state cycle guarantees
that repeatedly pressing ONE dial action reaches any rule-table-derived
target within 7 hops regardless of which way it spins.

## L4–L6 capture-first analysis (BANKED, R56 2026-07-15)

> Per the Codex reruling's step-5 kill criterion — "capture-first for L4-L6;
> if NO frame-visible mapping from editable objects to rule structure, bank the
> simple 3/6 slice rather than contaminating kernels"
> ([`docs/r56_codex_tr87_reruling_20260715.md`](../../../docs/r56_codex_tr87_reruling_20260715.md)).
> Reached each level live and read the win-check (`bsqsshqpox`) source
> (verification-only). Floor 3/6 @ 0.2857 (all L1-L3 at the 1.0 cap) preserved —
> the adapter's `plan_bar2_target` returns `None` (safe fallback) on all three.

The three flagged levels are **independent booleans**, not a mode choice
(measured from each level's `data={...}`): **L4 (index 3) = `double_translation`
only; L5 (index 4) = `alter_rules` only; L6 (index 5) = all three** (but
`bsqsshqpox` tests `tree_translation` with `if` and `double_translation` with
`elif`, so on L6 tree wins and double is DEAD CODE — L6 is effectively
alter+tree).

- **L4 (`double_translation`) — KILLED by the criterion (definitive).** The
  win-check's double-indirection (`lonhgifaes`) chains a matched rule's RHS to
  ANOTHER rule via a `tjaqvwdgkxe`-tagged MARKER sprite: it reads
  `get_sprite_at(LHS[0].x, LHS[0].y, "tjaqvwdgkxe")`, follows its "1"→"2" name
  pairing to a second position, and looks up the rule whose `LHS[0]` is the
  glyph there. **`on_set_level` sets EVERY `tjaqvwdgkxe` marker
  `set_visible(False)` at load** — so the entire rule→rule chaining that
  determines the derived target is INVISIBLE. A frame-only agent cannot compute
  L4's target; there is no frame-visible mapping. This is the kill criterion
  exactly. (L4's board is also structurally harder — variable-width multi-token
  rules and wider bars — so the pipeline would need extension too, but the
  invisible marker alone is decisive.)
- **L5 (`alter_rules`) — CSP CRACKED + VALIDATED (R59, 2026-07-16), but
  UNREACHABLE behind L4 → 0 card payoff, banked.** The mechanic: the player
  dials the RULE-TABLE SIDES, not bar2 — `step()`'s ACTION1/2 edits
  `[side for rule in cifzvbcuwqe for side in rule][cursor]`, shifting EVERY
  glyph in the bracketed side by ±1 together (one closed 7-state cycle per
  glyph, `kjgicbtgrt=7`); ACTION3/4 move the cursor among the sides
  (`% qrkshsinvo`). bar1 and bar2 are FIXED; `on_set_level` applies ONE random
  offset PER SIDE (not per glyph — the whole side shifts, relative pattern
  preserved). Win = `bsqsshqpox()` = `greedy_parse(bar1)` (matching by glyph
  NAME = (base, digit)) == bar2, confirmed the exact single-pass greedy.
  - **The CSP is small and unambiguous, NOT the "large search" the earlier bank
    feared.** greedy matches on LHS ONLY, so brute-force the per-rule LHS
    offsets (`7^(#rules)`; L5 has 4 rules → `7^4 = 2401`), run greedy, then the
    RHS offset of each fired rule is FORCED by the bar2 segment it must produce
    — check it. Measured on the live L5: 4 rules, bar1 all base-A (5 tokens),
    bar2 all base-B (5 tokens), **2 valid offset assignments found; applying
    either and calling the REAL `bsqsshqpox()` returns True**
    (`scripts/_tr87_csp` dev-time validation).
  - **Frame-only is feasible**: the C4-canonical signature is a CLEAN BIJECTION
    to (base, digit) on L5 — 10 distinct sigs ↔ 10 distinct tokens, 0
    collisions — so the win-check's name-equality is reproducible by sig
    equality, and every rule side dials to a concrete target sig read off
    bar1/bar2 (all 4 rules fire, so every side's target is a concrete slice; no
    cycle-order learning needed).
  - **⛔ The decisive blocker (measured R59): L5 = level INDEX 4 is UNREACHABLE.**
    Levels play sequentially; the current adapter clears L1–L3 (indices 0–2) and
    STALLS at index 3 = **L4 (`double_translation`)**, which is frame-unsolvable
    (invisible `tjaqvwdgkxe` markers, killed above) — confirmed: a full live run
    maxes at `levels_completed == 3`. So clearing L5 yields **0 card
    improvement** (tr87 stays 3/6 @ 0.2857) unless L4 is ALSO cracked first.
    Building the L5 executor now is unreachable dead code. **Banked as validated
    knowledge**: if L4 ever falls, L5 is a fast clear (CSP + sig-bijection both
    proven). Reopen order corrected: **L4 double FIRST (the gate), then L5 is
    cheap.**
- **L6 (`alter_rules` + `tree_translation`) — L5's CSP + tree re-expansion,
  hardest.** `tree_translation` re-expands each RHS glyph as another rule's
  `LHS[0]` (frame-visible, unlike double's markers), layered on top of the L5
  edit-the-rule-table search. Build after L5.

**Decision: bank L4-L6.** L4 fails the kill criterion outright (invisible
double-indirection markers). L5/L6 are a frame-visible but large alter_rules-CSP
build the Codex reruling itself deprioritized (it favored FT09's depth over
TR87's flagged levels). The 3/6 simple slice stays clean; kernels uncontaminated.
See [[../lessons/tr87_dial_match_hypothesis_falsified_20260713]] for the
companion "win-condition falsification" arc.

## Lessons Learned

- The v1 brittle solver still works on `sb26_sort`-style internal reads;
  the frame-only track is now `adapters25/tr87.py` (script25, 3/6), not
  the earlier `sort_match`/R23-generic 0/6 dead end. See the linked
  lessons below for the underlying pattern and refactor path.
- [[../lessons/hardcoded_is_anti]]
- [[../lessons/brittle_tells]]
- [[../lessons/tr87_dial_match_hypothesis_falsified_20260713]] — the R53
  win-rule elimination table. **Superseded, not obsolete**: the five
  falsified hypotheses it records (visual dial-match and its variants)
  were genuinely wrong, and that finding is exactly what redirected the
  search toward the correct rewrite-grammar model (R56) — read this page
  for the CORRECT current model, but the falsification table remains the
  evidence for why the naive reading doesn't work.
- **Level-transition frame-layer transient reproduces here too** (2026-07-15,
  R56 tr87 gate round, commit `a3a6644`) — right at a level-clear
  transition, `obs.frame` briefly carries many layers (measured: 37,
  level0→level1) and `frame[0]` is STALE (still shows the prior level's
  partially-used move counter) while `frame[-1]` is the settled current
  frame. Same class as [[../lessons/size_floor_and_settle_reads]]'s
  "Trap 2" (measured there on SB26 ~118 layers / CD82 ~16 layers) — read
  `frame[-1]` (`canonical_layer`), or retry until `n_layers == 1`, before
  trusting a just-transitioned frame for TR87 too. `adapters25/tr87.py`'s
  own settle-wait uses ACTION3 (a bracket move) as the wait action, not a
  throwaway, since TR87 has NO idle action (`avail=[1,2,3,4]` only, every
  one has a real side effect) and bracket movement never touches
  win-check state.
- **A background-gap segmenter can mistake an ink-free column WITHIN one
  glyph for the gap BETWEEN two glyphs** (R56, step 3) — measured on L2's
  bar1 (a C4 glyph fragmented into 3 sub-runs) and on bar2 generally (L1:
  11 messy runs instead of 7 clean glyphs). Fixed by a LATTICE split
  (`kernels.parse.split_runs_by_pitch` over the bar's own measured
  extent, positional, not background-gap-based) — see
  [[../rounds/r56_generic-kernels]]'s "TR87 gate arc" step 3 for the full
  before/after token tables. The RULE-TABLE side deliberately keeps the
  original background-gap grouping (unchanged, proven correct there) —
  the fix is bar1/bar2-specific, not a wholesale kernel swap.
