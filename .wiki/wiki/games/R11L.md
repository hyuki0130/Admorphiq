# R11L — Click-Driven Drag-Assembly Puzzle

> The only action is ACTION6 (click): select a creature's leg, then click to drag it; each body follows the CENTROID of its own legs, and a level wins when every creature's body is arranged onto its matching target nest — NOT a repeat-count or symbol sequence.

## Current Status

- **v1** (r11l-aa269680): 1/6. **v2** (r11l-495a7899): 1/6. Same result —
  frame-only, no internals read.
- The R57 typology flagged R11L as an unresolved T7/T8 ("~11 consecutive
  ACTION6") case. Reading the source RESOLVES it: it is neither repeat-count

- The R56 namespace-safe click-frontier explorer clears **1/6**, more

## Observations

- `available_actions = [6]` only — every decision is a click.
- Each CREATURE has a BODY, a set of small clickable LEGS, and a TARGET
  nest. The engine keeps one SELECTED leg (auto-selected nearest the origin
  at level start; the selected leg is recoloured — colour 0 vs colour 3 for
  unselected on the live board).
- Large corner regions act as HAZARDS: placing a leg colliding with one is
  refused; 5 bad placements → GAME_OVER. A step-counter is edge-pinned HUD.

## Mechanics Hypothesis

Click-drag assembly (confirmed from the game source, dev-time only):
clicking ON a leg selects it; clicking empty space drags the selected leg
there (animated), unless blocked by a hazard. After each move the body is
repositioned to the CENTROID of its legs, so bringing a body onto its
target means arranging ALL of that creature's legs so their mean sits on the
target. WIN = every body overlaps its target. This is a coverage/arrangement
condition ([[../concepts/merge_mechanic]]-adjacent), NOT a repeat sequence —
which is why the legacy `seq_repeat`/`seq_search` "worked" only by stumbling
onto a valid click order, not by understanding the mechanic.

## Solution Pattern (frame-only, partial)

Generic click-frontier exploration re-expressed through namespace-safe
kernels, with the action alphabet bounded to frame-derived clicks:
1. Mask the edge-pinned HUD, then canonicalise the masked board into a
   stable state key ([[../concepts/frame_hashing]]).
2. The candidate clicks at a state are that frame's salient region centroids
   ([[../concepts/sprite_cluster]]) — a bounded set, not the 64×64 space.
3. Record every observed `(state, click, next_state)` transition; take an
   untried click at the current state, else route to the nearest visited
   state with an untried click.

**Why it only partially generalizes**: winning is a CONTINUOUS
centroid-placement problem — the target leg configuration is rarely any
single existing region centroid — so a frontier search over "click an
existing region" cannot construct it except by luck, and each wrong
placement risks one of 5 collision strikes before GAME_OVER. L0's short
click order is findable; deeper multi-creature levels are not.

## Notes / Refactor Plan

- The "11 clicks" observable is a red herring for a repeat mechanic: it is
  the select/place cadence of dragging legs, not a threshold count.
- Reopen pointer: a generic "click-drag operator" motion kernel (infer, from
  observed click→leg-move transitions, the drag map and the
  body-follows-centroid rule) feeding a `configuration_path` plan toward a
  target-covering leg arrangement — same shape as the existing
  `learn_point_operators` / `plan_overwrites` pair, generalised to click-drag
  assembly. Until it exists, R11L stays banked at the L0 plateau.
