# R11L — Click-Driven Drag-Assembly Puzzle

> The only action is ACTION6 (click): select a creature's leg, then click to drag it; each body follows the CENTROID of its own legs, and a level wins when every creature's body is arranged onto its matching target nest — NOT a repeat-count or symbol sequence.

## Observations

- `available_actions = [6]` only — every decision is a click.
- Each CREATURE has a BODY, a set of small clickable LEGS, and a TARGET
  nest. The engine keeps one SELECTED leg (auto-selected nearest the origin
  at level start; the selected leg is recoloured — colour 0 vs colour 3 for
  unselected on the live board).
- Large corner regions act as HAZARDS: placing a leg colliding with one is
  refused; 5 bad placements → GAME_OVER. A step-counter is edge-pinned HUD.

## Mechanics Hypothesis

Click-drag assembly (confirmed from the game source, dev-time only):
clicking ON a leg selects it; clicking empty space drags the selected leg
there (animated), unless blocked by a hazard. After each move the body is
repositioned to the CENTROID of its legs, so bringing a body onto its
target means arranging ALL of that creature's legs so their mean sits on the
target. WIN = every body overlaps its target. This is a coverage/arrangement
condition ([[../concepts/merge_mechanic]]-adjacent), NOT a repeat sequence —
which is why the legacy `seq_repeat`/`seq_search` "worked" only by stumbling
onto a valid click order, not by understanding the mechanic.

## Solution Pattern (frame-only)

**Primary — centroid-assembly planner** (one shot per level, explorer
fallback):
1. Detect the creature from frame structure ([[../concepts/sprite_cluster]]):
   the clickable LEGS are the compact (high bbox-fill) pieces; the BODY and
   TARGET nest are a same-colour ring pair, disambiguated by the mechanic's
   own invariant — the BODY sits on the legs' centroid, so the ring color is
   the one with a region at that centroid (this rejects the thin leg-to-body
   connector lines, which also form two regions). Hazards are the large
   colour-2 wall regions.
2. Compute leg destinations with `points_with_centroid(target, num_legs,
   is_free, current=leg_centres)` — a generic geometry kernel that returns
   cells whose floor centroid equals the target, preferring the fewest moves,
   else a symmetric straddle. `is_free` demands a clear-background
   neighbourhood so the legs land separated (overlapping placements collide
   and burn the 5-strike budget).
3. Execute select→place clicks, re-issuing the place until the masked board
   settles (the drag animates). On a strike/GAME_OVER, abandon the plan and
   defer to the explorer.

**Fallback — generic click-frontier exploration** (the prior primary, kept
for levels the detector does not recognise): HUD-masked `canonical_key`
state, candidate clicks = salient region centroids, `transition_shortest_path`
routing to the nearest state with an untried click.

**Coverage vs efficiency**: the planner clears L0 at near-optimal efficiency
(4 actions). Deeper MULTI-creature levels (multiple leg groups + target
pairs) are not yet detected — the single-creature detector returns None and
the explorer runs (0), so coverage stays 1/6. Per-creature grouping is the
next lever for deeper levels.

## Notes / Refactor Plan

- The "11 clicks" observable is a red herring for a repeat mechanic: it is
  the select/place cadence of dragging legs, not a threshold count.
- The centroid-assembly planner (above) is BUILT — L0 is a super-human
  efficient clear via `points_with_centroid`.
- **Multi-creature DETECTION is DONE (R56c) — L1 EXECUTION banked on a
  transition-instability wall.** `_analyze_creatures` detects N creatures:
  bodies are the high bbox-fill ring pieces (legs ~0.48 fill, bodies ~0.8),
  each leg assigned to the NEAREST body (self-labelling, since a body sits on
  its own legs' centroid) with a centroid-consistency check. Verified on
  synthetic 1- and 2-creature boards (tests) and on the live L1 (two
  creatures: a 3-leg colour-12 and a 2-leg colour-15). **L1 still does not
  clear**: after the L0 win the board passes through a STABLE-LOOKING
  intermediate (a lone 2-leg "creature" of leftover/spawning pieces) that
  holds several frames BEFORE the real 5-leg layout finishes animating in, so
  any one-shot "plan when settled" fires on the transient and builds a stale
  plan the board then morphs under. Guards (creature-signature settle,
  place-timeout, leg-present validation) prevent crashes and preserve the L0
  clear but cannot find a clean planning moment. **(Superseded 2026-07-15: the
  continuous re-planner below removed the transient dependency entirely and L1
  STILL did not clear — so the transient was not the true wall; see the
  Reopen note for the body-collision root cause.)**
- **CONTINUOUS re-planning was BUILT and MEASURED (2026-07-15) — still 1/6;
  banked and reverted to the committed one-shot adapter.** A per-decision
  loop (`_continuous_step`) that re-detects every cycle and moves exactly ONE
  leg (select→place, verified from the settled frame), gated on multi-creature
  detection so L0 stayed byte-identical, was implemented, ruff/lint/pytest
  clean. Measured `--max-actions 1000`, deterministic ×2: L0 still clears in 7
  actions (game_score **0.0476**, unchanged floor); **L1 never clears** across
  this build and every teammate iteration (`replan1/2`, `mc`, `planner` rounds
  all 1/6 @ 0.0476). Two findings were banked before reverting:
  1. A real DETECTION bug was found+fixed en route: the edge-pinned
     step-counter column at col 0 shares colour 0 with a real leg, so without
     excluding HUD bands from the piece set it is mistaken for that colour's
     BODY and aborts the whole detection (returns None) on the live L1. The
     fix (drop `_is_hud_band` regions from pieces) was reverted with the rest
     but is the first thing to re-apply on reopen.
  2. **The true L1 wall is NOT level-entry timing — it is the win/collision
     mechanic itself.** From the source (`r11l.py` lines 1740–1785): a strike
     fires when the BODY, repositioned to its legs' new CENTROID, `collides_with`
     a `defgjl*` obstacle sprite mid-animation; 5 strikes → lose. The planner's
     frame-only `is_free` predicate only checks the destination LEG cell is
     clear of hazards; it cannot model the body's swept TRAJECTORY to the new
     centroid passing through an obstacle. Continuous re-planning does not help
     because each individually valid leg placement can still drive the body
     through a wall. L1 therefore needs learned body-trajectory (config-space)
     collision modelling, not a better planning-moment — the same
     `learn_point_operators` / `plan_overwrites`-shaped reopen the module
     docstring already points to, now sharpened to "model the body's centroid
     path vs obstacle sprites", plus re-applying fix (1).
- **LEVEL→OBSTACLE MAP (2026-07-15, source-authoritative — CORRECTS the
  point-2 attribution above).** Reading `environment_files/r11l/495a7899/r11l.py`
  in full: `levels = [Level1, Level3, Level5, Level7]` in that order = player
  **L0 / L1 / L2 / L3**. The two obstacle systems are `wakneh-*` (leg-placement
  REFUSAL, no strike — checked in `gabrtablhx`) and `defgjl-*` (BODY-collision
  STRIKE, 5 → lose — checked at lines 1740–1785). Their per-level placement:
  - **L0 (Level1)** — 1 creature (2-leg `pumlzd`); obstacles off-screen.
  - **L1 (Level3)** — 2 creatures (3-leg + 2-leg); `defgjl-Level3` at (-3,22)
    AND `wakneh-Level1` at (-6,-10) are BOTH OFF-SCREEN → **no in-play
    collision/strike hazard**. So the point-2 "L1 wall = body-swept-path
    collision" claim is WRONG: no strike can fire on L1. The real L1 blocker
    is arrangement/execution within the 60-action internal budget (transient
    handling + transit-ordering of the drags), NOT collision. Collision
    modelling is not what L1 needs.
  - **L2 (Level5)** — 2 creatures (4-leg `grhcew` + 2-leg `pumlzd`);
    `defgjl-Level5` at (-2,-2) OFF-SCREEN → also a pure free-space arrangement,
    harder than L1 only by leg count (a 4-leg centroid arrangement).
  - **L3 (Level7)** — multi-creature (`dirwzt` variants); `defgjl-Level7`
    IN-PLAY at (25,22, board centre) → the ONLY level where the body-collision
    strike is real. The learned body-trajectory / config-space collision
    modelling in point 2 is an **L3-specific** lever, not an L1/L2 one.
  - **Reopen order for r11l** (sharpened): (1) re-apply the HUD-column
    detection fix; (2) L1/L2 = continuous re-planner + transit-ordering +
    adequate budget (no collision model needed); (3) L3 only = add
    body-centroid-path vs `defgjl` collision modelling.
