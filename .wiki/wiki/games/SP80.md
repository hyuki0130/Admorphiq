# SP80 — Water-Routing / Spill-Coverage Puzzle

> Place deflector/block pieces during a CHANGE phase, then a SPILL phase drops water from a fixed source; a level wins only when the flow covers EVERY target region without hitting a hazard — NOT a reach-the-goal maze.

## Current Status

The R56 flow-kernel adapter now **clears BOTH L0 and L1 at efficiency score
1.0** (L0 10 actions vs 39 human; L1 16 actions vs 58 human), lifting
game_score to **0.1429** (2/6, deterministic ×2, 2026-07-15,
`scripts/rounds/script25_sp80_l1v1`). game_score 0.1429 = (1+2)/Σ1..6 = 3/21,
the completion cap for clearing L0+L1 of 6. Both clears are super-human, so the
lever from here is DEPTH (L2+), not efficiency.

The path: L0 was already an efficient single-deflector coverage clear
(game_score 0.000638 blind → 0.0476 via `plan_flow_coverage`). **L1 added the
multi-piece build** (`plan_flow_coverage_multi` + a select/execute layer),
taking game_score 0.0476 → 0.1429 (≈3×). L2+ still fall back to graph
exploration: they add angled-deflector sprites (`odioorqnkn`/`trurgcakbj`),
a second flow rule the current perpendicular-spread model does not cover.

**L1 build — four components, all frame-only (2026-07-15):**
1. **Multi-piece detect + classify** — after the single-piece plan fails
   (`plan_flow_coverage` returns None because one block can't cover 3 targets),
   the adapter select-probes each downstream candidate region: clicking a
   movable piece makes it the selected colour (a ka59-style frame-verify),
   which splits the deflector pieces from the static targets WITHOUT reading
   any colour constant.
2. **ACTION6 select — the two blockers solved.** (a) The engine renders this
   level ROTATED 180° (level `dojfslwbg=180`) and converts a click via
   `camera.display_to_grid`, so selecting a piece = clicking its OWN rendered
   centroid (the game un-rotates internally). (b) `env.step` must pass the
   coordinate: the runner uses `env.step(action, data=action.action_data.model_dump())`
   for complex actions — clicking WITHOUT that data kwarg silently sends
   (63,63) and selects nothing. The scale is a plain 4 px/cell
   (`min(64//grid, ...)`, no letterbox at grid 16), recovered live from the
   piece's per-action displacement.
3. **Joint 3-piece placement search** — `plan_flow_coverage_multi` BFS over the
   joint `(anchor_0..n)` state; on this level it finds a covering layout in
   ~0.3 s / 5–7 moves (e.g. piece0 right ×3, piece2 right ×2), far under the
   58-action human baseline.
4. **Clean-board restore** — the delta-probe displaces the auto-selected piece,
   and a re-spill RE-ARRANGES every piece unpredictably (merged/degenerate
   detections). So instead of spilling, the adapter walks ONLY the probe-moved
   piece back to its clean pre-probe snapshot, then classifies/plans/executes
   on that stable board. Gated on piece-count>1 so L0 stays byte-identical.

**Key observability finding**: the spill exposes its ENTIRE animation as the
observation's successive frame LAYERS (one layer per tick, water descending
one grid cell per layer) at the moment of commit. So a SINGLE sacrificial
spill reveals the whole trajectory — no tick-by-tick stepping needed — and a
failed spill returns to the change phase in ~1 tick, making the learning spill
cost ~2 actions and 1 of the 4 allowed attempts.

  - HUD: a top row (colour 14) and a bottom band (colour 1, shared with the
    hazard colour) — both edge-pinned, masked before hashing.
- `ACTION1..4` move the selected piece one fixed cell (collision-checked).
- `ACTION5` commits the layout → spill phase. `ACTION6` clicks to select a

- Only 4 spill attempts, then GAME_OVER; a per-level step budget also loses.

## Mechanics Hypothesis

Water-routing coverage (confirmed from the game source, dev-time only): the
spill drops water from the source, splitting/deflecting off placed pieces;
each target that the settled flow covers is marked satisfied (recoloured to
13). WIN = every target satisfied AND no hazard hit. This is a
[[../concepts/merge_mechanic]]-adjacent coverage condition over a simulated
fluid flow, NOT navigation — which is why the two earlier hypotheses below
were correctly falsified.

**Falsified (2026-07-15, gold trace + live probe)**: (a) "transform requires
delivering the piece onto/near a target" — the two colour-11 regions are
byte-identical before/after the win, and the win fires nowhere near them;
(b) "the win is a transform COUNT" — a 149-transform run cycled 3,3,2,2 then
GAME_OVER without ever advancing. Both are consistent with the real
mechanic: it is the water FLOW reaching targets, not piece position or
transform count.

## Solution Pattern (frame-only — learned flow model)

Compose the fluid-flow motion kernels (`learn_flow_operators` /
`simulate_flow` / `plan_flow_coverage`, the fluid analogue of the
`learn_point_operators` / `plan_overwrites` and reflection pairs):

1. **Learn** — commit ONE sacrificial spill; read its stacked animation
   layers; `learn_flow_operators` recovers the fall direction (down) + the
   source emit cells from them.
2. **Probe** — measure the movable piece's per-action displacement (the
   cluster that rigidly translates under an ACTION1-4 probe is the piece).
3. **Detect roles** — the goal regions are the static clusters DOWNSTREAM of
   the source in the fall direction (this excludes the upstream emitter);
   the movable piece is the probed cluster.
4. **Plan** — `plan_flow_coverage` searches piece placements, simulating the
   flow (fall; spread perpendicular around the obstacle; interior-hit
   satisfies a target) for each, until one covers EVERY target; execute the
   moves and commit the winning spill.

Fallback: no flow model, no movable piece, or no covering placement (multi-
piece levels needing ACTION6 selection, angled deflectors) ⇒ the same generic
transition-graph frontier explorer the previous build used, so depth never
regresses below that baseline.

## Lessons Learned

- **ACTION6 coordinates need the `data=` kwarg on `env.step`.** The runner
  issues complex actions as `env.step(action, data=action.action_data.model_dump())`;
  a bare `env.step(click_action(x, y))` sends no coordinate and the game reads
  (63,63). A dev probe that omitted this looked like "pieces are unselectable"
  for six rounds of investigation — the adapter itself is fine (the runner does
  pass `data=`), but any offline click probe MUST replicate the runner path.
- **A level can render ROTATED; click the piece where you SEE it.** This level
  carries `dojfslwbg=180`, so the board is rendered 180° and the engine applies
  the inverse to a click before `camera.display_to_grid`. Net effect: to select
  a piece, click its OWN rendered centroid — no manual un-rotation needed. Moves
  are likewise measured in rendered-frame terms, so the flow kernels (which work
  in rendered coords) need no rotation awareness.
- **A reset-spill RE-ARRANGES pieces; don't plan across one.** A failed spill
  does not restore the exact level-start layout — it re-arranges the deflectors
  (sometimes into merged/degenerate positions). So detect + plan + execute must
  all happen on ONE stable board with no spill between them. The multi-piece
  build restores only the probe-displaced piece (the sole thing that moved)
  instead of spilling to "reset".
- **The spill's whole trajectory is one multi-layer frame** — but only YOUR
  spill's. On entry to a deeper level the previous level's winning-spill
  animation is still playing (multi-layer, OPPOSITE fall direction); learning
  from it fits the wrong flow. Learn only from the sacrificial spill you commit
  in the change phase. A single sacrificial spill reveals the entire flow
  (~2 actions).
- **The flow-around-obstacle rule is generic, not game physics.** Water falls,
  spreads perpendicular along an obstacle's face, and resumes falling off the
  edges — parameterised only by the learned fall direction. A pixel-space
  droplet sim of this matched the engine's WIN/lose on all 7 tested L0
  placements.
- **Downstream filtering separates targets from the emitter.** The source
  emitter is a static cluster too; excluding clusters upstream of the source
  (opposite the fall direction) keeps it from being mistaken for a target the
  flow can never cover.
- A working single-level BFS clear can hide a non-navigation mechanic:
  SP80's L0 clear was assumed to be a movement puzzle until the source read
  + gold/live characterization found a water-routing coverage win. Don't
  infer full mechanic understanding from one strategy's partial success.
