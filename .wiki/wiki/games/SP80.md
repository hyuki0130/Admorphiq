# SP80 — Water-Routing / Spill-Coverage Puzzle

> Place deflector/block pieces during a CHANGE phase, then a SPILL phase drops water from a fixed source; a level wins only when the flow covers EVERY target region without hitting a hazard — NOT a reach-the-goal maze.

## Current Status

- **v1** (sp80-0ee2d095): 1/6. **v2** (sp80-589a99af): 1/6. Same result —
  frame-only, no internals read.
- Legacy `strat_bfs_state_space` cleared L0 in 2058 actions. The R56
  namespace-safe re-build (`script25` quarantined adapter, generic
  transition-graph explorer) also clears **1/6**, more efficiently — L0 in
  337 actions at the 1000-action smoke (game_score 0.000638). **BANKED**
  there: deeper levels are a water-flow spatial-reasoning wall, not a
  reachability gap.

## Observations

- Two-phase controls (v2 board, background colour 12):
  - CHANGE phase: a movable BLOCK/DEFLECTOR piece (the selected one is
    recoloured — colour 9 on the live board, an 80-cell block), a fixed
    WATER SOURCE near the top (colour-4 emitter + colour-6 spout, ~col 36),
    and two TARGET regions (colour 11, 80 cells each, bboxes `(52,16,59,27)`
    and `(52,40,59,51)`).
  - HUD: a top row (colour 14) and a bottom band (colour 1, shared with the
    hazard colour) — both edge-pinned, masked before hashing.
- `ACTION1..4` move the selected piece one fixed cell (collision-checked).
- `ACTION5` commits the layout → spill phase. `ACTION6` clicks to select a
  different piece; the engine auto-selects the origin-nearest piece at level
  start and after each failed spill.
- Only 4 spill attempts, then GAME_OVER; a per-level step budget also loses.

## Mechanics Hypothesis

Water-routing coverage (confirmed from the game source, dev-time only): the
spill drops water from the source, splitting/deflecting off placed pieces;
each target that the settled flow covers is marked satisfied (recoloured to
13). WIN = every target satisfied AND no hazard hit. This is a
[[../concepts/merge_mechanic]]-adjacent coverage condition over a simulated
fluid flow, NOT navigation — which is why the two earlier hypotheses below
were correctly falsified.

**Falsified (2026-07-15, gold trace + live probe)**: (a) "transform requires
delivering the piece onto/near a target" — the two colour-11 regions are
byte-identical before/after the win, and the win fires nowhere near them;
(b) "the win is a transform COUNT" — a 149-transform run cycled 3,3,2,2 then
GAME_OVER without ever advancing. Both are consistent with the real
mechanic: it is the water FLOW reaching targets, not piece position or
transform count.

## Solution Pattern (frame-only, partial)

Generic state-space search re-expressed through namespace-safe kernels:
1. Mask the edge-pinned HUD bands (top strip, bottom counter) via
   [[../concepts/frame_hashing]]-style region detection, then canonicalise
   the masked board into a stable state key.
2. Record every observed `(state, action, next_state)` transition (moves +
   the spill-commit ACTION5).
3. Explore systematically: untried action from the current state first, else
   route over the recorded transitions to the nearest state with an untried
   action.

**Why it only partially generalizes**: the search is BLIND to the water
flow, so it can only stumble onto a winning layout, and each wrong spill
burns one of just 4 attempts before GAME_OVER (forcing a reset). L0 is
solvable by moving the single auto-selected piece then spilling (gold:
`[move, move, move, spill]`, 4 actions), so the explorer finds it.
Multi-piece levels additionally need TARGETED selection (an ACTION6 click on
a specific piece), an unbounded coordinate space the click-free explorer
does not enter.

## Notes / Refactor Plan

- L0 clear is not evidence of a navigation mechanic (the earlier lesson):
  BFS finding the spill action does not mean it understands water flow.
- Reopen pointer: a generic "learned flow operator" motion kernel (infer,
  from observed spill frames, how water propagates past each block type)
  feeding a `configuration_path` layout plan — same shape as the existing
  `learn_point_operators` / `plan_overwrites` pair, generalised to fluid
  propagation. Until it exists, SP80 stays banked at the L0 plateau.

## Lessons Learned

- A working single-level BFS clear can hide a non-navigation mechanic:
  SP80's L0 clear was assumed to be a movement puzzle until the source read
  + gold/live characterization found a water-routing coverage win. Don't
  infer full mechanic understanding from one strategy's partial success.

  from frames without internals
