# WA30 — Pick-Carry-Drop Delivery Puzzle

> A single worker moves on a grid and uses one context-interact action to pick up items and deliver them to target zones; a level wins when EVERY target zone is satisfied — a multi-item delivery, not a single-goal navigation.

## Current Status

- **v1** (wa30-ee6fef47): legacy brittle `wa30_analytical` 2/9 (reads sprite
  tags — non-transferable); generic R23 8B agent 0/9. Only one API version.
- R56 carry-delivery rebuild (2026-07-15): **L0 clears in 30 actions with
  efficiency score 1.0** — SUPER-HUMAN vs the 71-action human baseline —
  lifting game_score 0.0 → **0.0222** (`scripts/rounds/script25_wa30_carryN`).
  The first generic WA30 clear (the brittle legacy 2/9 read sprite tags; the
  generic path was 0/9). Deeper levels stay graph-fallback → 1/9, no
  regression. game_score 0.0222 is the completion cap for clearing L0 of 9
  (weight 1 of Σ1..9 = 45), so the lever from here is DEPTH.
- The earlier `plan_delivery` (route-adjacent) build was 0/9 — it exposed the
  carry-follow/facing mechanic underneath the subgoal wall. Closing THAT with
  offset-routing (`plan_carry_delivery`) + a facing nudge is what cleared L0.

## Observations

- `available_actions = [1, 2, 3, 4, 5]` — NO coordinate action (background
  colour 1 on the live board).
- A single WORKER (colour 9, starts carrying a colour-2 item). Several TARGET
  zones (colour-4 and colour-14 blobs, ~12 cells each) and PICKUP items.
- HUD: a bottom-row step counter (colour 7, row 63) — edge-pinned, masked.
- `ACTION1..4` move the worker one cell (diff ~32 px/move); `ACTION5` is a
  context interact (no-op when nothing is adjacent).

## Mechanics Hypothesis

Pick-carry-drop delivery (confirmed from the game source, dev-time only):
`ACTION5` next to a pickup grabs it (the item disappears / the worker's
pixels change to show carrying — the R57 typology's "colour 2 vanishes"),
and `ACTION5` next to a matching target delivers it. WIN (`ymzfopzgbq`) =
every target zone satisfied. This is a multi-item coverage/delivery
condition ([[../concepts/merge_mechanic]]-adjacent), requiring several
pick→carry→deliver subgoals to be chained.

## Solution Pattern (frame-only — carry-aware delivery)

The mechanic (measured offline): a box picked while the worker FACES it
(ACTION5, box one cell away in the facing direction) attaches and FOLLOWS the
worker at a fixed offset = that facing vector; ACTION5 while carrying drops it
in place; WIN = every box on a goal cell.

1. **Detect roles** (logical ÷4 grid): worker = colour-14 singleton; boxes =
   the uniform-size same-colour class (colour-4); goal slots = the large
   colour-9 delivery pad tiled into box-sized cells.
2. **Compose `plan_carry_delivery`** with the measured carry offset
   `(-1, 0)` (facing up → box rides one cell above): to seat a box on goal
   `G` the worker routes to `G - offset`, so every pickup/delivery leg is a
   pure translation, chained min-cost via `grid_shortest_path`.
3. **Insert a facing nudge** (a blocked step into the box that only sets
   rotation) before each pickup interact — the one game-specific refinement on
   top of the generic planner.
4. Execute; fall back to graph exploration on deeper levels.

Measured: L0 in 30 actions vs 71 human → score 1.0.

## L1 Divergence — BANKED (2026-07-15): autonomous cooperating agent, non-stationary board

L1 was probed live (clear L0 with the adapter, then diagnose the L1 board and
single-step-probe every action). The L1 blocker is **not** a detection or
carry-offset tweak — it is a **genuinely new mechanic**, so per the stop rule
it is banked with the divergence rather than force-fit.

**What L0 assumes** (and why it clears super-human): exactly one mover (the
worker), a static board except the worker's carried box, and a precomputable
static carry-delivery plan.

**What L1 introduces** (measured, source-confirmed):

1. **A second, AUTONOMOUS agent.** The level adds a `kdweefinfi`-tagged sprite
   (colour 12, `byigobxzpg`; L0 has none). Every step, `ynmgxjqkgh` makes each
   `kdweefinfi` agent pick up a box and carry it toward a `fsjjayjoeg` win-zone
   ON ITS OWN, independent of the player's action. The single-step probes show
   colour 12 moving on EVERY action — right on "up", right on "left", up on
   "A5", left on "down" — i.e. it follows its own BFS clock, not the command.
   It also relocates boxes (colour-4/9 clusters shuffle every step). **The
   board is now non-stationary**, so any static precomputed plan desyncs
   immediately. This is the decisive blocker; it is orthogonal to detection.
2. **Worker identity is confirmed but detection is confused.** The true worker
   is the colour-14 `wbmdvjhthc` sprite (`wppuejnwhl`, present in BOTH levels;
   probes: it is the only region that moves one cell in the commanded
   direction). But L1's extra singletons (the colour-12 agent, the colour-9
   `doijajrgdi` zone) break `_detect_roles`: it returned `goals == worker ==
   (8,7)` — the pad picker collides with the worker cell. This IS a detection
   bug, but fixing it alone does **not** clear L1 (see #1), and reworking
   `_detect_roles` risks the L0 super-human clear, so it is left untouched.
3. **Tight budget.** StepCounter drops 200 (L0) → 70 (L1), 5 boxes not 3.
   An idle player (bump-wall or repeat-A5) does **not** let the agent finish:
   measured GAME_OVER at step 70 both ways. So the player must actively
   cooperate — deliver some boxes itself while the agent delivers others —
   within 70 steps on a board the agent keeps reshaping.

**Precise reopen** (a real build, not a tweak): a REACTIVE cooperative-delivery
planner that (a) IDs the colour-14 mover empirically via a one-cell probe
(don't trust size heuristics against the colour-12 agent), (b) re-reads box and
agent positions EVERY step (they move), (c) re-plans the nearest un-delivered
box's pickup+delivery each step and yields boxes the autonomous agent is
already delivering, (d) routes around the moving agent. This is non-stationary
multi-agent planning — a new kernel composition, well beyond the L0
static-plan model. Deprioritised under diminishing-returns discipline; L0
stays 1/9 @ 30a (floor verified `scripts/rounds/script25_wa30_L1probe`).

## Lessons Learned

- **The carry twist is offset-routing, not a second brain.** Seating a
  fixed-offset follower on a target is pure geometry: route the worker to
  `target − offset`. That crystallised into the generic `plan_carry_delivery`
  kernel — the game-specific part shrank to one measured constant (the offset)
  + a facing nudge, both in the quarantined adapter, none in the kernel.
- **Closing one wall exposes the next.** The `plan_delivery` (route-adjacent)
  build routed correctly but scored 0/9 because it didn't seat the CARRIED
  box on the goal; adding the offset (carry-follow) + facing closed that and
  cleared L0 super-human. Subgoal composition was necessary but not
  sufficient; the carry geometry on top was the last mile.
- A structurally well-fit generic explorer still fails when the win is a
  CHAINED multi-subgoal plan, not single-goal reachability — the same class
  as [[SK48]]'s shape-matching wall. Blind search covers states; it does not
  compose subgoals.
- The legacy solver is brittle — v1 works via internals, generic is 0.
