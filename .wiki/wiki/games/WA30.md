# WA30 — Pick-Carry-Drop Delivery Puzzle

> A single worker moves on a grid and uses one context-interact action to pick up items and deliver them to target zones; a level wins when EVERY target zone is satisfied — a multi-item delivery, not a single-goal navigation.

## Current Status

- **v1** (wa30-ee6fef47): legacy brittle `wa30_analytical` 2/9 (reads sprite
  tags — non-transferable); generic R23 8B agent 0/9. Only one API version.
- R56 delivery-kernel rebuild (2026-07-15): the adapter now DETECTS the roles
  correctly and COMPOSES the generic `plan_delivery` kernel (min-cost
  pickup→target assignment + per-leg `grid_shortest_path` routing) into a
  valid pick→deliver action chain — but still **0/9** at the 1000-action smoke
  (`scripts/rounds/script25_wa30_deliveryN`). **BANKED with a precise
  divergence** (below): the generic route-and-interact plan does not model
  WA30's carry-follow/facing mechanic, so the boxes do not land on the goal
  cells; the graph explorer fallback preserves the prior 0/9 baseline (no
  regression). The generic kernel itself is validated independently on
  synthetic delivery scenarios (`tests/test_kernels_paths.py`).

## Observations

- `available_actions = [1, 2, 3, 4, 5]` — NO coordinate action (background
  colour 1 on the live board).
- A single WORKER (colour 9, starts carrying a colour-2 item). Several TARGET
  zones (colour-4 and colour-14 blobs, ~12 cells each) and PICKUP items.
- HUD: a bottom-row step counter (colour 7, row 63) — edge-pinned, masked.
- `ACTION1..4` move the worker one cell (diff ~32 px/move); `ACTION5` is a
  context interact (no-op when nothing is adjacent).

## Mechanics Hypothesis

Pick-carry-drop delivery (confirmed from the game source, dev-time only):
`ACTION5` next to a pickup grabs it (the item disappears / the worker's
pixels change to show carrying — the R57 typology's "colour 2 vanishes"),
and `ACTION5` next to a matching target delivers it. WIN (`ymzfopzgbq`) =
every target zone satisfied. This is a multi-item coverage/delivery
condition ([[../concepts/merge_mechanic]]-adjacent), requiring several
pick→carry→deliver subgoals to be chained.

## Solution Pattern (frame-only, no clear)

Generic transition-graph exploration re-expressed through namespace-safe
kernels — a good STRUCTURAL fit (the whole delivery state, including
carry-state, is visible, and the alphabet is 5 simple actions):
1. Mask the edge-pinned HUD, then canonicalise the masked board into a
   stable state key ([[../concepts/frame_hashing]]).
2. Record every observed `(state, action, next_state)` transition (moves +
   interact).
3. Explore systematically: untried action at the current state, else route
   to the nearest state with an untried action.

**Why it does not clear**: the win requires CHAINING several deliveries
(L0's human baseline is 71 moves), and blind frontier search covers states
breadth-ish without composing the ordered pick→deliver subgoals before the
per-level step budget resets the attempt. The generic explorer clears
single-goal reachability (as on AR25/SP80/R11L level 0) but not multi-subgoal
delivery planning.

## Notes / Refactor Plan

- The reopen pointer is now PARTIALLY realised: the generic delivery planner
  `plan_delivery` exists in `src/admorphiq/kernels/paths.py` (min-cost
  `assign_pairs` + per-leg `grid_shortest_path` + `path_to_moves`,
  catalogued in `docs/r56_kernel_catalog.md`) and the adapter composes it.
  What remains for a WA30 CLEAR is the game-specific carry/facing layer —
  see the banked divergence.
- **Banked divergence (measured 2026-07-15)**: role detection is correct
  (worker = colour-14 singleton, boxes = the uniform-size colour-4 class,
  goals = the colour-9/2 pad's logical cells) and `plan_delivery` emits a
  valid 23-action chain for L0, but executing it does NOT deliver the boxes
  onto the goal cells. Root cause: WA30 is not a clean "walk adjacent →
  interact" delivery — a box ATTACHES and FOLLOWS the worker (carry-follow),
  and pickup depends on the worker's FACING (rotation) and a coarse 4-px
  alignment. The generic route-and-interact kernel deliberately models
  neither (that would be a game-specific "second brain" the codex verdict
  keeps out of the namespace). A future WA30 adapter iteration needs a small
  carry-simulation layer (route so the carried box ends ON the goal cell,
  and face the box before ACTION5) composed on top of the generic planner.

## Lessons Learned

- **Generic subgoal composition is necessary but not sufficient for a carry
  delivery.** The chained-plan wall (blind search can't compose ordered
  pick→deliver subgoals) is genuinely closed by `plan_delivery` — the
  assignment + routing now compose correctly. But WA30 adds a SECOND
  mechanic on top (carry-follow + facing) that the generic route-and-interact
  model does not capture, so the composed plan routes correctly yet doesn't
  win. Closing the subgoal-composition gap exposed the carry-physics gap
  underneath it.
- A structurally well-fit generic explorer still fails when the win is a
  CHAINED multi-subgoal plan, not single-goal reachability — the same class
  as [[SK48]]'s shape-matching wall. Blind search covers states; it does not
  compose subgoals.
- The legacy solver is brittle — v1 works via internals, generic is 0.
